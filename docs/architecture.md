# Knot v1: architecture

Draft for review · 2026-11-18

This file says how Knot v1 is built. What it does is in [product-spec.md](product-spec.md). How the work is organised is in [PLAN.md](../PLAN.md). Decision IDs (D1) and package IDs (WP-10, SP-1) refer to PLAN.md.

## 1. Fixed choices

| Choice | Value | Why |
|---|---|---|
| Minimum OS | 27 on iOS, iPadOS, macOS and watchOS | D17. It brings handwriting recognition, new App Intents and a better on-device model. |
| Language | Swift 6, strict concurrency complete, warnings are errors | Many agents write this code, and the compiler is the cheapest reviewer. |
| UI | SwiftUI. AppKit or UIKit only where SwiftUI cannot do the job: the Mac panel and hotkey, the PencilKit canvas. | D20 |
| Local store | SQLite through GRDB | The one third-party dependency (D30). |
| Sync | CloudKit private database through CKSyncEngine | D11 |
| Watch transport | WatchConnectivity | It works with sync off (D18) and fits "no phone, no notes" (D5). |
| Speech | Apple SpeechAnalyzer with SpeechTranscriber | English only in v1 (D4), on-device. |
| Cleanup | Apple Foundation Models, the on-device model | D6 |
| Ink | PencilKit with PKStrokeRecognizer | D7 |
| Project file | XcodeGen from `project.yml`. The generated project is not committed. | Parallel agents never conflict on a project file. |
| Dependencies | GRDB only. No analytics, no UI libraries, no MCP SDK. | D18, D30 |
| Toolchain | Xcode 27.x through a command-scoped `DEVELOPER_DIR`. Never change `xcode-select`. | Other projects on the machine keep their own toolchain. |

Modules depend on KnotCore's ports, not on each other. Only KnotApp knows the concrete types. KnotSync is the one exception: it uses KnotStore directly, because it needs database-level access. It never issues SQL itself. KnotStore gives it one interface of six operations, listed below, and that interface keeps revisions, the change counter, history and the search index right for a remote change as for a local one. KnotAgent is written against the `NoteStore` port, so its commands can be built and tested on the fake before the store exists, and the `knot` executable is where the real store is wired in.

The six operations come from the code half of SP-4 (docs/notes/SP-4.md). By CKSyncEngine's headers, which it read and did not run against a server, the engine hands its state over in an event of its own, after the changes that state covers, so a fetched batch and the engine's state cannot share a transaction. A kill between the two costs a fetch of the same changes again, so applying a batch must change nothing the second time.

1. Apply a fetched batch in one transaction, idempotently. It returns the records the merge made or settled, already queued for upload (§11). The batch's deletions of notes are recorded as held, in the same transaction, and not applied.
2. Save the engine's state in a transaction of its own, when the engine hands it over.
3. Read the next pending records for the current send, in order and at most a given number, never one already handed out in that send. The headers do not say whether a batch's sent event comes before the engine asks for the next batch, so the store keeps a set of the records it handed out, cleared when a send begins and when it ends.
4. Record a sent batch: keep the system fields of each saved record, and remove a `change_log` row only when the saved values are still the stored ones (§7).
5. Settle at the end of a fetch, given whether every zone's fetch completed (§11). It counts the held deletions of the whole fetch, then applies them, or pauses sync and asks when they would delete more than the set share of the local notes (§11).
6. Report a record over the size limit, and keep it apart (§11).

The held deletions come from the review of this change, not from SP-4's note. A fetch's deletions come across several batches, and each batch is applied as it arrives, so a share counted per batch could never reach the limit. The deletions are held in the store and not in memory, so that a second pass after a kill changes nothing.

Each of the six operations carries the generation of the sync run and the account generation, and the store refuses an input from an older one. That is how an event that arrives after a stop or a change of account never reaches the notes (§5, §11).

KnotExport never downloads. It exports the recordings and drawings that are on this device, writes a line in the note's Markdown for a file that is on another device, and returns the list of what it left out. It can also say what an export would leave out before it writes anything. KnotExport takes a drawing's image from its caller, through a provider of KnotCore types that the caller passes in: with an image it exports the drawing as that image, and without one it writes the drawing's stored data file under its ID and names it in the list it returns. Export therefore never drops a drawing, and `knot export`, which cannot reach KnotInk, still exports everything (§10). The app's export first downloads those files through `AssetFetcher`, then exports, and shows that list (product spec §8). `knot export` downloads nothing and asks KnotExport first: when a file is on another device it refuses and writes nothing, or with `--skip-missing` it exports the rest and prints the list (product spec §10).

Three things in KnotCore exist so that a rule has one home. `CaptureManifest` is the one file format for a recording in progress, an item in `Inbox/` and a file in the watch outbox, with one version number and one set of golden files. `StoreLocations` is the only code that computes where a store, `Inbox/` or the recording state lives. It takes the flavour from the app shell or the tool, and no library target has a default path. `DurableFile` is the only code that places a file: write, sync, rename, sync the folder (§6, rule 7). A store's code reaches it through `StoreFiles`, which `StoreLocations` makes: a store can have two roots, the app's own container and the app group (§7), and `StoreFiles` places each path under the root that holds it and refuses a path under neither. A fourth joined them in the second engineering pass: the rule that a generated title uses only words from its note is one function here, which KnotCleanup calls when it proposes a title and the store calls when a segment leaves a note.

The module table is enforced. The gate builds with `--explicit-target-dependency-import-check error`, so an import the table does not allow fails the build. On a branch that is not a contract branch, the gate also fails when KnotCore's public API differs from `main`. WP-02's own pull requests are the exception until the last of them has merged, because they are the ones that write that API. Its third only adds: once the tracer has started on the API of the second, a change that breaks it goes in a contract branch like any other. The review holds WP-02 to that, because the gate's check lets its branches through.

`AppEnvironment` is declared in KnotCore, with an `.unavailable` value whose ports all report that they are not there yet, apart from the clock and the ID generator, whose live versions are in KnotCore. KnotFakes builds `.preview` and KnotApp builds `.live`. On iOS and macOS, `.preview` is the real capture engine and queue running over the fakes, and WP-05 delivers that part. On watchOS the environment has no engine.

App shells get their environment from one factory in KnotApp. WP-01 writes it so that a debug build asks KnotFakes for the preview environment, which answers `.unavailable` until WP-05 fills it in, so WP-05 edits only its own folder. The first PR of WP-22 makes the factory return `.live`, filling any port that has no implementation yet with the unavailable one. A test compares the unavailable ports of `.live` with a list allowed for the coming milestone. The import of KnotFakes sits behind `#if DEBUG`, and the release script fails when a Release binary holds a KnotFakes symbol or honours the preview launch argument. UI tests select `.preview` with a launch argument that only debug builds honour. The watch app does not use `CaptureEngine`: it composes KnotAudio, KnotLink and KnotUI itself. Each module exposes one live entry point, which returns the unavailable port until its package fills it in, so a package that lands after WP-22 wires itself in without editing KnotApp.

## 4. Domain model

```swift
struct Capture { id; kind: typed | voice | ink; origin: (source, surface); startedAt; endedAt: Date?
                 outcome: open | stored | discardedEmpty | failed(code)
                 launchID                           // the process launch that owns it while it is open
                 placement: window | newNote | named // what was asked for; local
                 shownNoteID: NoteID?               // local: the note the capture surface showed, which a manifest records too
                 revision: Int64                    // the producer's content revision, which orders the saves of one capture; not stamped
                 lastSavedAt: Date?                 // when the store committed the capture's last durable save, by its own clock
                 contentHash }                      // of a finished capture with content, keyed with a secret of the store, to judge a repeated ID. Text is hashed in NFC. None after a discard or a failure

struct Note    { id; createdAt; updatedAt
                 title: String?; titleOrigin: none | generated | user
                 titleEditedAt: Date?               // synced: when the title or its origin last changed, which the rule that a title keeps the later edit compares (§11)
                 lastCaptureEndedAt; closedAt: Date?; deletedAt: Date?
                 revision: Int64 }                  // the store's change counter at this note's last change

struct Segment { id; noteID; kind: typed | voice | ink
                 noteGeneration: Int                // synced: rises each time the segment's note changes
                 origin: device(DeviceID) | cli | mcp
                 startedAt; endedAt
                 text: String                       // shown, edited, searched, exported
                 textOrigin: typed | rawTranscript | cleaned | edited | recognised
                 rawTranscript: String?             // voice only: it only grows, run by run, and is never replaced, shortened or cleared
                 transcription: (engine, locale, osBuild)?   // voice only: what produced the transcript
                 cleanup: (osBuild)?                // voice only: the OS build whose model cleaned the text
                 recognition: (engineVersion, language, osBuild)?   // ink only: what produced the recognised text. WP-02's third PR adds it, with a default
                 processingOwner: DeviceID?         // voice only, synced: the device that runs its jobs
                 ownerGeneration: Int               // voice only, synced: rises each time the work moves
                 arrivedAt: Date?                   // local, not synced: set when a late capture is placed, cleared when its note is opened
                 state: SegmentState; assetID: AssetID?; duration: Duration?
                 conflictOf: SegmentID?; deletedAt: Date?
                 piece: Int                         // synced: its position among the pieces of a capture whose text ran past the size limit, 0 for the first
                 pieceOf: SegmentID?                // synced: for a later piece, the first piece of its capture
                 revision: Int64 }                  // local, never synced: the store's own, which rises each time the text changes and never falls

struct Asset   { id; segmentID; kind: audio | ink; byteCount; sha256
                 availability: local | remote | downloading   // whether the file is on this device
                 upload: localOnly | uploading | published }  // how far its upload has gone

struct Job     { id; segmentID; kind: transcribe | clean | recognise
                 state; attempts; deaths; notBefore; lastErrorCode
                 resumeAt: Duration?                // transcribe only: where the next run starts in the file
                 revision: Int64 }                  // rises with each save; a save names the revision it read
```

IDs are time-ordered UUIDs (version 7) generated in KnotCore. They sort by creation time and never collide across devices. Every capture has a capture row, made once, which holds no content. On the store path it is the capture's first durable write. A recording writes its manifest first, and a capture that falls back to `Inbox/` gets its row when the row can be written (§6). The segment a capture becomes shares its ID. No rule may read an ID's order as time order: a capture ID given on the command line and a note ID derived for a moved segment (§11) are not time-ordered. Time comes from the timestamps. A derived ID is a version 5 UUID, so it can always be told from a fresh one, which is version 7. Text that runs past the size limit continues in further segments of the same capture: the first shares the capture's ID, and each later one has an ID derived from the capture's ID and its position. A repeat of the capture therefore returns the same segments, and the capture row counts once. Each piece records its position, `piece`, and a later piece names the first, `pieceOf`. The pieces of one capture share its start. A note orders its segments by the start of their capture, the pieces of one capture together and in position, and then by ID as a fixed tie-break, never as a time (`SegmentOrder`). Two more IDs are derived, each from a namespace of its own: the transcribe job of a stored recording, `JobID.transcribe(of:)`, from the segment's ID, so the store writes one job and a repeat finds it (§5); and the conflict copy that keeps a late save, `SegmentID.keptSave(of:position:)`, from the capture's ID and the piece's position (§5).

The capture row holds no content, but it records how far the capture's content has come: its content revision, the producer's own sequence that orders the saves of one capture, and `lastSavedAt`, when the store committed the last save that changed the content, by the store's clock. Recovery ends an open typed capture there (§5). The row also records the placement asked for and the note the capture surface showed, as an `Inbox/` manifest does.

The store has an ID and a change counter. Every change to a note or to one of its segments, including one that arrives by sync, gives the note the counter's next value in the same transaction. The `knot` command polls on that value. The store also has a generation, which rises when a kept copy is restored (§7). A cursor names the store, its generation and the counter. A revision that leaves the store, in a result or on the command line, carries the generation too. A restore also gives the store a new store ID, and that is what refuses a cursor or a revision kept from before it as foreign: the generation can repeat, when a restore finds no record of the generation before it (§7). Every read and every write of `NoteStore` returns its revisions stamped that way, except a job's revision, which never leaves the device. A capture's content revision is the one number that is not stamped: it orders the saves of one capture and nothing else. When one save changes segments in several notes, each of those notes takes the counter's value in that transaction.

A segment can leave its note for a new note of its own (product spec §7). The move makes a note with a fresh ID, and every other field of that note comes from the segment: its dates are the segment's, it is not closed and it has no title. A move changes no text, so the segment's revision stays, while both notes take the next values of the change counter. `noteGeneration` rises by one each time the segment's note changes, whether by a move, by a return or by the deleted-note rule of §11. `lastCaptureEndedAt` is recomputed for both notes in the same transaction, and again whenever a change of note arrives by sync. Titles do not move. A generated title must still use only words from its note (§9), so when a segment leaves, the note's generated title is checked again and dropped if it no longer fits. A title of origin `user` is never touched. The clean job proposes a title only for the note that holds its recording when the job finishes, and only if that recording is the note's first segment and the note has no title. A conflict copy (§11) is always in the note of the segment it copies, and moves with it. The pieces of one long capture are one capture: they move together and return together.

A capture that ends empty is discarded, and a note it leaves with no live segment is emptied: hidden (product spec §3, rule 11), reported by `knot changes` as deleted, never marked deleted, and purged with a tombstone once it has been empty and unchanged for 30 days. A finished capture that is already empty when it is first recorded writes its capture row as discarded empty and nothing else: no note, no segment, and no other capture ended.

Job states are queued, running, done and failed. A transcribe job keeps `resumeAt`, where its next run starts, and the store saves it with the run's text in one transaction (§9). A queued job with no resume time has not run yet; a done one with no resume time has finished the file, or ended on a final error. A job's saved state only moves forward: a save names the job's revision it read, and one older than the stored revision is refused; a done job stays done; and its attempts and deaths never fall, except through the retry of a failed job. Five things can stop a job, and they are told apart:

- **An attempt** is an error the step returned. After five, the job is failed and its segment shows a retry action.
- **A deferral** is a step that cannot run now: the model is not ready, the system limits requests, there is no background time left, the device is locked, or, for recognition, the app is not in the foreground. Deferrals are never counted. The job runs again when the app comes forward or the model's availability changes.
- **A death** is a job found running at launch. When background time runs out the queue yields the job cleanly, so a job still marked running means the process died. The job goes back to queued once. After two deaths it fails with its own code, so a recording that crashes the transcriber cannot kill the app at every launch.
- **A yield** is a step that was cancelled, because background time ran out or the queue was asked to stop. Its error is `cancelled`, in a class of its own. It is not counted, nothing from the step is saved, and the job stays queued.
- **A final error** is one that no retry on this device can fix: speech is unavailable here, the audio cannot be read, the drawing cannot be read, the recogniser does not support the handwriting's language, or the cleanup model cannot be used here. The job ends at once as done, with the error's code, and is not tried again. What its segment shows is the error's own: a recording or a drawing kept without text, shown as "Kept, no text", or the raw transcript as its text.

Sizes are bounded in the domain types, and WP-02 fixes the numbers. First values, all estimates: a segment's text holds at most 256 KiB of UTF-8, so that a record stays under CloudKit's limit with its raw transcript beside it; a title at most 200 characters; a manifest at most 64 KiB. The code half of SP-4 read CloudKit's record limit and did not measure it (§20). A segment record at these first values, with 256 KiB of text and a 256 KiB raw transcript, holds 524,451 bytes of field data, counted locally with no server, so they leave about half of the limit free. WP-02 keeps them, and SP-4's report confirms the limit or a contract PR changes them. Typed or piped text beyond the limit continues in a new segment of the same note, and nothing is cut. A file's place on disk is derived from its ID, never from a name inside a manifest or a record.

An asset ID whose row a purge or "Remove recording" removed is retired, in the local table `retired_asset`, and no capture takes it again, so that no acknowledged capture names a file that the removal takes.

The device ID is checked against an install ID kept in the Keychain for this device only. When a store arrives on another device through a backup, the two no longer match. Knot then gives the store a new device ID, resets the sync state and fetches again, so a restored phone never acts as the old one.

A kind, an origin, a state or a field that this build does not know is kept and never dropped, and the segment shows as made by a newer Knot, which is a visible state of its own beside the six of product spec §5. That holds for the database, for synced records and for inbox manifests. A manifest is valid JSON as a whole, or it is unreadable (§6, rule 2). A field of a manifest that this build does not know keeps its value as the original JSON text, and is written back with it.

Segment states:

```
typed   draft ──end──► ready                       (empty draft ──► discarded)
        draft ──killed──► ready at relaunch
        draft ──its save failed──► failed: the text is kept in Inbox/ ──a retry stored it──► ready

voice   recording ──stop──► recorded ──► transcribing ──► transcribed ──► cleaning ──► ready
            │ killed            │ cannot run now            │ no model, or the guard rejects
            ▼                   ▼                           ▼
        recovered ──────► recorded (pending)          ready, with the raw transcript as text
        recording ──a tap-started one, stopped within a second──► discarded
        cleaning ──cannot run now──► transcribed
        speech is unavailable on this device ──► recorded, shown as "Kept, no text" until another device takes the work
        any step fails ──► failed(step, code): the recording is kept and a retry is offered
        recording or recovered ──its save failed──► failed(record, code): the audio is kept ──retry──► recorded

ink     drawing ──end──► recognising ──► ready     (empty canvas ──► discarded)
        drawing ──killed──► recognising at relaunch
        drawing ──its save failed──► failed(code): the drawing is kept ──retry──► recognising
        recognition fails ──► failed(recognise, code): the drawing is kept and a retry is offered
        the drawing cannot be read, or its language is not supported ──► the job ends, and the drawing is kept, shown as "Kept, no text"

watch   onWatch ──transfer──► delivered ──► continues as "recorded" on the iPhone
```

"Kept, no text" for a recording whose work belongs to this device rests on the transcriber's readiness. When speech is unavailable here or the locale is unsupported, speech never runs on this device (`TranscriberReadiness.neverRunsHere`): the recording is kept with no text, and its note does not wait for it. While the model is only not installed or installing, the work is waiting, and the recording shows as "Saved, text on its way".

## 5. Ports

KnotCore declares these protocols. KnotFakes ships a fake for each, except `CaptureEngine` and `ProcessingQueue`, which have one real implementation each in KnotCapture. WP-02 fixes their exact signatures.

| Port | Responsibility |
|---|---|
| `NoteStore` | Predict where a capture lands. Record a capture, save its checkpoints and its end, and reconcile an `Inbox/` item with it. Read a capture's row, the open captures, the store's cursor, notes, segments, assets and jobs. Page the stream. Search. List the notes changed after a cursor. Replace text and titles, delete and restore, remove a recording, and clear the marks of late arrivals. Move a segment to its own note, and return it. Set a segment's state, and save transcription runs, cleanup results and jobs. Purge, naming the files of what it removed. Answer `purged` for a kept inbox item whose segment was purged, and write nothing (§6, rule 2). Publish changes. |
| `AssetStore` | Place, move into place, find, verify and remove recording and drawing files. The same asset ID with other content is refused. A remove keeps a file that a row of the notes still names, its asset row or a segment, and is no error: a caller that must know whether the file went asks `find`. |
| `CaptureEngine` | Begin, update, end and discard captures of each kind. Tell the store where the user wants each one placed and which note its surface showed. Publish capture state. It does not ingest `Inbox/` and does not recover: the composition calls those (below). |
| `Recorder` | Get ready without opening the microphone. Start a recording from a request that carries what its manifest records: the capture, the launch, the origin, the placement asked and the note shown. The start returns a session once the recording is live. The session streams levels, how much of the audio is durable, and the live audio, and it ends with its reason, whether it was stopped or stopped by itself. Stop, which cannot fail or be cancelled and returns once the file is on the drive; two stops at once both wait for it. Discard, after which a stop returns a recording ended as discarded, with no frames and no file. Convert a stopped recording to the stored format and verify it, and remove its working file and manifest once the capture's row points to the stored asset (§8). Recover the orphaned recordings of earlier launches, never one of the current launch. While it records it may leave the recording's level peaks beside the working file, in the format KnotCore holds (§8). |
| `Transcriber` | Report readiness in five states: ready, not installed, installing, unsupported locale, unavailable. Install the model with progress, which only the app does. Transcribe a file in resumable runs: a run reads at most a budget of audio from an offset, ends at the last finished phrase, and returns its pieces with their time ranges and where the next run starts. A first phrase longer than the budget is taken whole, so every run but the last moves on. Stream live text for `Sendable` chunks of samples. |
| `Cleaner` | Report availability in three states: available, not ready, unavailable with its reason. The reason `notInThisBuild` comes only from the unavailable port of `AppEnvironment.unavailable`. Publish its changes. Turn a raw transcript into a body and, when asked, a title, in one call that returns the whole result. A decline is a result, not an error. |
| `InkRecogniser` | Report whether it can read handwriting in a language: available, or unsupported language. Recognise one finished drawing, given as the bytes the canvas saved, into its text and the text's provenance, in one call with no stream. Empty text means the drawing holds no words, and a refusal is never read as no words. |
| `ProcessingQueue` | Run and resume transcribe, clean and recognise jobs. `enqueue` wakes the queue for a segment whose transcribe job the store wrote, and writes no job itself. The clean job is the queue's to write: it writes it when the transcription's last run is saved, and at launch it writes it for a transcribed recording that lacks one, so that a death between the two leaves no transcript without its cleanup. Each drain takes a `BackgroundRunner` and a progress sink from its caller. A drain ends idle, when no job can run now because each is done, deferred or failed, or yielded, when the runner's time ended or the caller cancelled with work still queued. Publish each job each time its state changes. |
| `SyncEngine` | Publish its status: the current one, then every change. Start. Stop, which cancels and drops every later event of the run. Sync now, a fetch then a send, which alone throws, with a sync condition that carries the time to retry when there is one. Answer each question a pause asks (§11). |
| `WatchLink` | Send a capture: write it to the outbox and queue it, which says nothing about delivery. Receive acknowledgements. Publish how many captures wait and how many failed, counted from the outbox and its acknowledgements, never from the session's queue. Resume at launch and on the system's events (§12). Run the Watch's background task until the session has no content pending, within a time limit. |
| `AudioPlayer` | Play, pause and seek a recording. |
| `AssetFetcher` | Bring a recording or drawing made on another device onto this one, with progress. |
| `RecordingStateStore` | Publish whether a recording is running, for controls and widgets in other processes: a synchronous read and write of one value in the app group's defaults. |
| `RecordingActivity` | Start, update and end the Live Activity that keeps an intent-started recording alive, keyed by capture ID, and at launch end every activity that has no recorder. Its errors name ActivityKit's refusal. iPhone and iPad only. |
| `SettingsStore`, `FeatureGates`, `WallClock`, `IDGenerator` | Small supporting ports. The clock port is named `WallClock`, because a `Clock` of KnotCore would shadow Swift's own `Clock` protocol in every module that imports it. |

Of these ports, WP-02's second pull request holds `NoteStore`, `AssetStore`, `Recorder`, `Transcriber`, `Cleaner`, `WallClock`, `IDGenerator` and `BackgroundRunner`, and the protocols of `CaptureEngine` and `ProcessingQueue`. Its third adds the rest.

Implementers: `AudioPlayer` and `RecordingStateStore` in KnotAudio; `SettingsStore` in KnotStore; `AssetFetcher` in KnotSync, with a local-only version in KnotStore for when sync is off; `RecordingActivity` in the iOS app target; `InstallIdentity` and `ProcessNotifier` in KnotStore, by WP-10's second PR; `FreeSpaceProbe` in KnotAudio, by WP-12's second PR, because the Watch's recorder needs it and the Watch composes no KnotStore; `BackgroundRunner` in KnotCapture: the runner that runs work straight through, for the foreground and the Mac, by WP-05, and the iOS runners by WP-15's second PR; `SurfaceRouter` in the iOS and Mac app targets, by the second PRs of WP-30 and WP-33; `CueEmitter` in the iOS, Watch and Mac app targets, by the second PRs of WP-30, WP-32 and WP-33, for what plays, while the recorder decides when a cue may play, so that a start cue is not recorded; `Lifecycle` in KnotApp, by WP-22's second PR, with an adapter for iOS and one for macOS, and in the Watch app target, by WP-32's second PR, if anything there takes the port.

An operation added to a port after its first conformers comes with a default that answers `port_unavailable` (§18). A type that fills in such an operation declares it `async` when the port does. A synchronous method of an actor loses to the port's `async` default when the call is made on the actor itself, which then answers `port_unavailable`; through `any` or a generic the call reaches the method. It was measured with the pinned compiler in the review of pull request 91, where `InMemoryNoteStore.setPeaks` and `peaks(of:)` were the two cases.

No module takes the `Lifecycle` port itself. WP-13's transcriber, WP-15's first PR and the queue all react to the app coming forward, and all may start before the port exists. So the modules expose a call for the app coming forward, the composition makes that call, and WP-22's second PR wires `Lifecycle` to those calls.

SP-1's code half fixed three of these ports:

- `RecordingActivity` holds no `Activity`, because ActivityKit's `Activity` is not `Sendable`. Its implementation finds the activity by the capture ID in its attributes each time, so a new launch ends the activity that a dead one left, through `endAll(except:)`.
- `BackgroundRunner` is not a service the queue calls. Background time from an intent exists only inside that intent's `perform()`, through a method of the intent itself, and every mechanism that gives minutes requires progress reports. So the runner is passed in by whoever holds the time, is scoped to one call, and runs work that reports its progress. The work names the capture it is for, when there is one: an intent that stops a recording runs the work of that capture. `ProcessingQueue` takes a runner and a progress sink for each drain and owns no background time. Which mechanism gives the time waits for SP-1's report.
- Reloading the controls when the recording phase changes belongs to the app shell, with `ControlCenter.shared.reloadControls(ofKind:)`, and not to `RecordingStateStore`, so that KnotAudio needs no WidgetKit.

SP-4's code half shaped `SyncEngine` from the SDK alone, with no server. Its draft of the protocol is in docs/notes/SP-4.md, in the section "For WP-02: the port", and WP-02's third PR fixes the exact signatures:

- **Status.** By the SDK, the engine streams no progress, only the events it hands its delegate one at a time (§20). The adapter derives the status from them: `fetching` and `sending` from the will and did events, and `remaining` from the store's count of pending records. The engine retries transient errors by itself and names no event that reports the error or the wait (§20), so `waiting(until:)` has a time only after a manual sync that threw one.
- **Stop.** `cancelOperations()` is asynchronous, and an operation in flight may finish after it returns (§20). So `stop()` cancels, raises the run's generation and releases the engine, and the store drops every input from an older generation, so an event that arrives after a stop never reaches the notes.
- **Errors.** No method of the port throws an engine error except `syncNow`. Everything else surfaces as a status, as the engine surfaces it as an event.
- **Questions.** Each pause of §11 is a question with the two answers that §11 defines, and the app answers it through the port.

KnotCore also declares two seams that are not ports of `AppEnvironment`: `FileLayer`, under `DurableFile`, which the power-cut layer of KnotTestSupport replaces in tests, and `LogSink`, under the logging facade, for tests that check that no text reaches a log.

KnotLink declares one more seam of that kind, `LinkTransport`, and WP-17 writes it with its fake. Everything in §12 sits behind it. It activates the session and reports its state; queues, lists and cancels file transfers by capture ID; receives a file through a synchronous handler that runs before the system deletes the file and returns the acknowledgement to send; sends acknowledgements; and updates the context. It streams the session's events: a change of state, a file finished, a file cancelled, an acknowledgement and a context. A file finished is not a delivery. The fake transport can lose, repeat and reorder each kind of event, and finish a file that never arrives.

Two operations carry the "nothing is lost" promise and are part of the contracts:

- `NoteStore` records a capture in one transaction: it applies the append rule, writes the capture row and writes the segment. `CaptureEngine` and the `knot` command both use that one operation, so the append rule runs in one place. The store decides. The engine passes only what the user asked for, follow the window, a new note, or a named note, and the note the capture surface showed. The note that a capture surface shows before the first keystroke comes from a store query that calls the same rule, given the capture's kind and surface, and a test checks that the prediction and the decision agree at the same instant. The rules about open captures on a device are checked in that transaction too, against the `capture` table, because two processes share it on the Mac. The same transaction sets a segment's `arrivedAt` when the append rule places its capture as a late arrival (product spec §3, rule 7), and `NoteStore` clears `arrivedAt` on a note's segments when the note view opens it. The mark is local display state: setting it is part of the capture's own write, and clearing it changes neither the change counter nor any revision, so opening a note never brings it back into `knot changes`.
- `CaptureEngine` publishes the state of each capture each time it changes: the note it is in once the store has placed it, and none on the `Inbox/` path; its outcome, open while it is being made; its path; and the revision of the content that is durably saved: a typed capture's checkpoint revision, or a recording's frames that survive a power cut. A drawing's saves are an open point. Tests and the soak harness treat only that revision as acknowledged. The path is the store, through `NoteStore`, or `Inbox/`. A capture takes `Inbox/` whenever the store path does not take it, because the store did not answer in time or because it answered with an error: a capture reaches disk before anything else happens to it, so a refusal falls back as a slow answer does. Its state carries that error's code, or `store_not_open`, and ingest stores it later, where its manifest says. This is what lets `record` stay strict: a typed capture whose named note was deleted under it is refused with `note_deleted`, goes to `Inbox/`, and ingest gives it a new note. When the write to `Inbox/` fails too, the capture has reached no disk. The port does not say what the engine does then, and WP-05 builds it to product spec §4.4: the surface stays open with the text in it and says that it could not save.

The record-a-capture transaction holds these rules too:

- A capture that follows the window goes to the note its surface showed whenever that note can still take it: the note is not deleted, it has a live segment left, and "New note" did not close it before the capture started. So a store call that commits late and the ingest of the same capture's file agree, whichever arrives first. Otherwise the append rule decides.
- "New note" closes the note the window would have joined, at the capture's start (product spec §3, rule 4), in the same transaction.
- Rule 15 of product spec §3 applies in the order the captures began. A capture whose store call commits after a newer capture began on the device, the race of §6 rule 6, never ends that capture. It is recorded as ended at the newer one's start, and it takes its later saves by revision. It is placed by the note it showed, or by the append rule as for a late arrival that started then, so the captures that began after it do not count. Its segment is not marked as arrived. A recording ended this way has no file yet, and its job comes with the file. It holds nothing until its file comes, and its own end applies to it as to an open one: stored with its file, failed with its code, or discarded as empty. It is not open, and `openCaptures` does not return it. Launch recovery never takes it for stored: it finishes it as an open one, and removes a working file only for a row that holds its content, or a discarded one. A late drawing is not settled yet: it comes with WP-11 PR 4.
- A finished capture that is empty when it is first recorded writes its row as discarded empty and nothing else (§4). Its receipt names a note ID that nothing uses, with the reason of its placement: `new_note_asked`, `named_note`, or `no_earlier_capture` for the window.
- Every receipt says why the append rule placed the capture, and the command line reports it: `named_note`, `new_note_asked`, `open_capture_on_device`, `appending_off`, `no_earlier_capture`, `latest_note_deleted`, `latest_note_closed`, `inside_window` or `outside_window`. Tests and diagnostics read the same codes.
- A segment ID that another capture owns, first or derived, is refused as a conflict, and nothing is written. So is a capture whose body does not fit its kind, such as a file whose digest is not 64 hexadecimal digits, a recording or a drawing that starts with its file, or a negative content revision: `record`, `checkpoint` and `end` refuse it with `capture_invalid`.
- A stored recording never lacks its transcribe job. The store writes it, `JobID.transcribe(of:)`, in the transaction that stores the recording, by `record`, `end` or `ingest`, and no caller passes a job. A recording that ends stored with no file is refused with `capture_invalid`.

`NoteStore` has one operation for an `Inbox/` item, `ingest`. It reconciles the finished capture that the manifest gives with the capture's row, whatever state the row is in, in one transaction:

- No row: the row and the segments are made, placed as `record` places them, or as a late delivery by rule 7 (§6, rule 2). A named or shown note that is deleted, emptied or purged gives a new note. The item is never refused for that, and never handed to the window.
- An open row: the item's content is applied by revision, and the capture ends.
- A failed row: it becomes stored, through precedence (below).
- An ended row with the same content: nothing changes.
- An ended row at a lower revision: the item is a later save of the capture (below).
- An ended row at an equal or higher revision with other content: a conflict, and the file is kept.

The result says which content revision is durably stored, and only that lets the caller remove the file. An item whose body does not fit its kind, or that has no end, is written as a failed segment that says so, and an open row it meets fails the same way. The call then fails with `inbox_item_unreadable`, so the file is kept, and the same item ingested again changes nothing. `record` stays strict for every other caller: a repeat with other content fails with `capture_id_conflict`, whatever the state of the row.

At launch, after the recorder has recovered its files (§13), the composition runs two steps in this order: ingest reconciles `Inbox/`, then the open rows of earlier launches end. The two orders give different results. An inbox item reconciled first ends its open row with the item's content, while a row that was ended first is then judged as an ended row. Neither step is on the `CaptureEngine` protocol: the composition calls them itself, through KnotCapture's own types. A typed capture ends at its last durable save, the time the store wrote on its row (`lastSavedAt`, §4). A recording ends at the end of the audio its file holds, which the recorder reads to the last complete frame (`Recorder.recoverOrphans`): an open recording's row has no `lastSavedAt`. Where an open drawing's saves go is an open point (`docs/plan/open-points.md`).

Three more operations serve the command line and are part of the same contracts:

- Recording a capture is idempotent by capture ID. A repeat with the same ID and the same content changes nothing and returns the capture's receipt as the store holds it.
- `NoteStore` lists the notes changed after a given counter value, in pages, deletions included, and says when a value is ahead of the store.
- Replacing a segment's text or a note's title takes the revision the caller read and fails when it is stale. Text replaced through the command line or MCP is kept for 30 days in a local table and can be restored. A replacement names its writer: a person in the app, the processing queue, the `knot` command or the MCP server, and only the last two keep the text they replace.

One operation repairs a grouping, and it is part of the same contracts:

- `NoteStore` moves a segment to a new note of its own in one transaction, and returns it to the note it left in another. A move names the note the caller saw the segment in. If the segment is no longer in that note, nothing moves and the result says where it is, so a repeat is safe even after a later capture has joined the new note. The pieces of one long capture move together and return together. A move is refused for a segment whose capture is open, for a deleted segment, for a conflict copy, and for a capture whose pieces are the only live segments in their note apart from their own conflict copies. Each move appends a row to `segment_history`, kept under the capture's first piece: the note the segment left, the note the move made, the `noteGeneration` it produced and a generated title it dropped. The row stays for 30 days on the device that made the move. A return names the note the caller sees the segment in, and reads the latest row, so only the latest move of a segment can be returned. It is refused, and changes nothing, when the segment is not in that note or its `noteGeneration` has changed since, or when the note it left is deleted, gone, or has no live segment left. The app's undo and `knot move --back` are both a return. Either way the rules of §4 hold: the titles, the two notes' latest-capture times and the conflict copies are settled in the same transaction.

Two operations name files for the caller to remove through the `AssetStore`:

- "Remove recording" (product spec §7) keeps a voice segment's text, removes its recording's row and returns the asset. It is refused while the capture is open, answers `not_found` for a segment with no recording, and is refused with `remove_recording_refused_no_text` until the segment has text, because the recording is then all there is and its transcribe job still needs it.
- The purge (§7) returns the assets whose rows it removed, and the files that `Inbox/` keeps for the kept items whose failed segments it removed, whose names the store forgets in the same transaction. `StorePurge` in KnotCapture removes them, the assets through the `AssetStore`.

One save rule serves every save of a capture that has a row: a checkpoint, an end, the end that rule 15 makes, the retry of a failed capture, and an ingest. It keeps a fallback, a retry or a late save from undoing newer work:

- Saves are ordered by revision. A checkpoint carries the capture ID and a revision, and it never lowers the stored revision. A checkpoint that arrives late, from a slow save or from a file in `Inbox/`, replaces older text and never newer text. The end is a save too. The winning content and revision are chosen first, and only then is the content judged empty, the segments finished and what is stored hashed. A stale end ends the capture with the stored content.
- An ended capture takes a save at a higher revision as a later save of the same capture. When a person replaced its text since, their segment is not touched at all, and the save's content is kept as a conflict copy of it, `SegmentID.keptSave`, piece by piece. A repeat makes the same copy, and a higher revision updates it. This holds for a checkpoint, an end and an ingest alike, and the ingest then answers that the content is stored, so no inbox item waits for ever. An end at the stored revision with other content, of an open capture or an ended one, fails with `capture_id_conflict`, and so does an ingest at an equal or higher revision with other content. A recording or a drawing that rule 15 ended before its file was known takes its file from a later save.
- The retry of a failed capture, by `end` or by `ingest`, stores it through the same precedence. A person's text since the failure stays and is no longer failed, and the retry's content is kept as a conflict copy. A retry whose text is blank makes no copy, and the capture is stored with the person's text.
- A repeated capture ID is judged by the content the ledger accepted for that capture, whatever happened to the segment's text since. The same content changes nothing. Other content at the same revision fails as a conflict, so an agent that reuses an ID learns of it.
- A segment's revision is the store's own. It is never taken from a producer's content revision, and it only rises, for a segment the store makes again too.
- Replacing text checks precedence inside the store: edited beats cleaned beats raw (§11). The queue and sync both call that one operation, so neither carries a check of its own. A typed capture's own text comes only through its checkpoints and its end, so a replacement with the origin `typed` is refused with `illegal_transition`.

WP-02's error taxonomy names these failures by case, and no port throws an untyped error: disk full; store busy; store damaged; store newer than this build; write failed; microphone permission refused; no input device; audio session busy; too little space; conversion failed; audio unreadable; transcription failed, with the engine's code; speech unavailable on this device; cleanup model unavailable; cleanup declined (refusal, guardrail violation, empty or malformed result, guard rejection, text too long for the model, unsupported language, unsupported request); cleanup timed out; recognition failed; drawing unreadable; handwriting language unsupported; inbox item unreadable; checksum mismatch; asset conflict, the same asset ID with other content; capture invalid, a capture or an end that does not fit its kind (§5); "Remove recording" refused while the segment has no text; the pauses of §11: signed out, account changed, zone removed, a large delete, and a restored store waiting for consent; and the errors of the engine that SP-4's code half sorted (docs/notes/SP-4.md): transient, server record changed, zone missing (deleted by the user, or gone after an encrypted-data reset), limit exceeded, quota exceeded, unknown item, and final. Zone missing is the error of a send, and it leads to the zone-removed pause. The engineering review added three cases: text too long; a capture stopped because the disk filled; and a cursor from another store generation. One code covers a cursor from another store and one from another generation of this store, and one code does the same for a revision. The recorder tells a full disk from another failed write by the volume's free space, because the audio file's error does not say. The errors of a step that cannot run now form a class of their own, a deferral (§4): speech model not installed or still installing, cleanup model not ready, requests limited by the system, with the time to try again when the system gives one, system resources limited, no background time, device locked, app not in the foreground, and, for the watch link, link not ready, counterpart missing and counterpart full. The watch link has two more cases: delivery failed, an attempt after which the capture is queued again, and outbox file missing, which fails the capture at once and keeps its manifest. A cancelled step is a yield, a class of its own whose one case is `cancelled`: it is not an attempt, not a decline and not an error. Speech unavailable on this device, audio unreadable, drawing unreadable, handwriting language unsupported and cleanup model unavailable are final: the job ends and is not tried again on this device (§4). A job that died twice fails with a code of its own. A recording that is empty or silent is not an error either: it is ready with empty text, and so is a drawing that holds no words.

## 6. One writer, many producers

```
 producers                          one writer                      readers
 ─────────                          ──────────                      ───────
 typing in the app        ─┐
 recorder in the app      ─┤
 intents (app process)    ─┼──► CaptureEngine ──► NoteStore ──► stream, note view, search
 watch files              ─┤         │           (SQLite)  ◄─► CLI and MCP (macOS, a second process)
 recovered recordings     ─┘         ▼               ▲
                               ProcessingQueue       └──── SyncEngine (CloudKit)
                         transcribe ► clean ► title
```

Rules:

1. In each process, one `NoteStore` actor writes the database. On iOS only the app process opens the database. Extensions never do. On the Mac the `knot` command and the MCP server are a second process. They read, and they write only through `NoteStore`: a new capture goes through the same record-a-capture operation the engine uses (§5). Text added by the tool does not end a capture that is open in the app. It is placed by the window like any capture, and an open capture counts as an open window. The tool refuses to edit or delete a segment whose capture is still open.
2. Anything outside the app process that produces a capture writes an inbox item: a manifest file and a payload, written atomically into `Inbox/`, which sits in the app group container in a build that has one (§7). The app ingests inbox items at launch, on returning to the foreground and when notified, and takes the items it finds together in the order their captures started (product spec §3, rule 7). Ingest goes through the one `NoteStore` operation for an inbox item, which reconciles the item with the capture's row in whatever state the row is (§5), so a repeat changes nothing. Only a delivery from outside the app process is late by rule 7, and in v1 that is the Watch's. An item that the app itself wrote, because the store did not answer in time (rule 6), is never late: it goes where its manifest says. A manifest is a `CaptureManifest` (§3) and carries a format version. An item that cannot be read, or that a newer version wrote, becomes a failed segment that says so, through the store's one operation for it, `recordKeptItem`: a failed row with the item's reason, and one segment in a new note, which does not count for the append window and carries no arrival mark. The item keeps its files in `Inbox/`. The store records their names and never looks in `Inbox/` itself, and a screen reads the names to open or share each file (`keptFiles`). When a later version can read the item, ingest stores it through the failed row, in the note that holds its failed segment, and clears the names in the same transaction. Since WP-15's first pull request the ingestor calls that operation for an item it cannot read. An item whose body does not fit its kind, such as a file whose digest is not 64 hexadecimal digits, becomes a failed segment too: the store writes it so through `ingest`, and ingest fails with `inbox_item_unreadable`, so the file is kept. When the failed segment of an item that could not be read is deleted and then purged, its files in `Inbox/` are removed, and no later version of Knot stores that item. The owner decided it on 2026-11-21. The purge names those files, and the store forgets them in its transaction. A row failed with one of the kept item's reasons, by `recordKeptItem` or by ingest's own refusal of a body that does not fit its kind, whose segment was purged, is gone: `ingest` and `recordKeptItem` answer `purged` for it and write nothing, and the ingestor removes the item's files. A row that failed for any other reason is not gone, and its capture, arriving again whole, is stored: that is kept on purpose, since in doubt Knot keeps a capture. Nothing in `Inbox/` is deleted before it is stored, with that one exception. A temporary file that a cut write left in `Inbox/` is no item. Launch recovery removes every one, once a launch and in the app only, with `DurableFile.removePartials(in:)` (`LaunchRecovery.removeInboxPartials`). A writer in another process whose partial goes places its file again under a new name, once: `DurableFile.place` runs again when its write fails with `ENOENT`. A second removal inside one place fails that write to its caller and leaves nothing half-written. The orchestrator settled it on 2026-11-22.
3. The recorder writes a manifest before the first audio sample. Recovery at launch turns orphaned manifests into segments.
4. The sync engine runs only in the app process. It learns about writes from other processes through the change log.
5. Views never touch storage. They talk to view models, and view models talk to ports.
6. The capture ledger. Every capture has a `capture` row. On the store path the row is its first durable write, and that write is what "started" means. A recording writes its manifest first, and a capture that falls back to `Inbox/` starts with its file there. A typed capture starts at its first keystroke. A recording whose microphone cannot open never starts, and the surface says why.
   - After recovery no row is `open`. Each row is stored as a segment, discarded as empty, or failed with its content kept and visible. A failed capture becomes stored when a retry succeeds. The retry goes through precedence: a person's text since the failure stays, and the retry's content is kept as a conflict copy (§5).
   - Empty means no text for a typed capture, no strokes for an ink capture, and under one second for a tap-started recording. The second is measured between the two presses, and a stop that the clock puts before its start is kept.
   - A typed or ink capture whose save fails writes its content to a file in `Inbox/` and is marked failed. If the row itself cannot be written, the content still goes to `Inbox/`, and ingest creates the row later.
   - If the store cannot be opened at all, capture still works: every capture goes to `Inbox/`, and the stream shows what is wrong. Nothing is deleted. Ingest stores those captures once the store opens again.
   - Capture rows belong to the device that made the capture and do not sync. Writes from `knot` and the MCP server create rows too. The invariant covers segments that originated on this device.
   - On the watch the ledger is the outbox: every manifest is either still on the watch and visible, or acknowledged by an iPhone that holds its file in `Inbox/` or a capture row with the same ID.
   - The 150 ms and one-second tolerances in the product spec bound what a kill can lose inside a capture. They do not excuse a missing row.
   - The engine never waits for the store. A capture that begins while the store is not open yet, is migrating, or has not answered within 100 ms is written to `Inbox/` in the usual manifest format and ingested when the store answers. A recording writes its manifest first and its row when the row can be written. A capture that falls back to `Inbox/` stays on that path until it ends, and its manifest records the placement that was asked for and the note the surface showed. The store call it stopped waiting for may still commit. Either way the capture row is made once, by whichever arrives first, every later save is a checkpoint ordered by revision, and ingest places the capture where its manifest says: by the placement asked for, and for the window in the note its surface showed, whenever that note can still take it (§5).
   - A capture is owned by the process launch that began it. Recovery finishes only captures whose launch is not the current one, so it never ends a capture the user is making now.
7. What "on disk" means. There are three cases, and each claim says which one it rests on.
   - **A killed process.** Everything written is kept, within the 150 ms and one-second tolerances. The kill tests and the soak prove this.
   - **A sudden power cut or a kernel panic.** Only what was synced to the drive is kept. `DurableFile` syncs a file and its folder before the database row that points to it is committed. A folder's own name is synced as well, in its parent: `DurableFile` checks and syncs each folder of a path the first time it meets it, from the store's root down, and remembers it. If a save fails because a remembered folder is gone, it forgets that folder and those below it, checks and syncs them again, and tries once more: only that second try's success is acknowledged. A folder that another program replaced is not noticed (§19). `DurableFile` refuses a path that is not below its root, and compares paths by the real folder they name, never by the form in which they are written (`PathForm`): `.` and `..` are worked out from the text, and the deepest part of the path that exists is resolved through every symbolic link, so a root written with or without `/private` is the same folder before and after its folders exist. It checks each folder below the root at its first use, refuses a symbolic link or a file in a folder's place, and gives the file layer the path it checked. Two races stay open, because no check of paths can close them: a link made between the check and the write, and a link put in place of a folder after its first save. Letter case is apart: on a volume that folds case, a path written in another case than its root is refused while the root does not exist, and placed once it does. Every caller takes its paths from one `StoreLocations`, so none meets it. On first use it also syncs the folders above the store's root, upward to the first one the process may not open, because a folder that an app made with `FileManager` was never synced. The store's folders are Knot's alone: nothing else creates them, and nothing removes or replaces one while the store is in use (§19). The database runs with `fullfsync` on, because on Apple's systems `synchronous = FULL` alone can leave a commit in the drive's cache. A recording in progress is synced every second. The "saved" cue, an acknowledgement to the watch and the engine's durable revision are given only after that sync. WP-10 and WP-12 report what the syncs cost. If a draft save cannot afford one each time, drafts are synced at least once a second.
   - **What a kill leaves.** A kill inside `DurableFile.place` leaves a hidden partial file beside the destination. Every folder that `DurableFile` writes in has one owner that clears what a kill left there: launch recovery for `Inbox/`, the recorder's recovery for `Recording/`, which keeps the partial of a recording starting in its own process, the watch outbox for `Outbox/`, and the store for its copies. The peaks file is made in place with no temporary, so a kill can only cut it short (§8). No code on `main` clears a partial in `Assets/` yet: a package that places files there names its owner.
   - **A battery that runs out.** The system shuts down in order, which is the first case.
   - A test fails when the writer connection lacks either setting. A file-layer test drops every write that was not synced and checks that recovery still holds. A power cut itself is checked by the owner, once at M2 and once at M3, with a forced restart during a recording.

In v1 the only producer outside the app process is the watch link. Extensions that capture come later.

## 7. Storage

- **Database:** `KnotStore/knot.sqlite`, a GRDB `DatabasePool` in WAL mode with `synchronous = FULL`, foreign keys on and a 5-second busy timeout. On iOS and iPadOS it lives in the app's own container: iOS kills a process that is suspended while holding a lock on a database in a shared container, and no extension needs the database. On macOS it lives in the app group container, so that the `knot` command can open it. The writer connection sets `fullfsync` (§6, rule 7). Reads use the pool's reader connections and never wait for the writer.
- **Files:** under the same `KnotStore/` root, `Assets/<last two ID characters>/<assetID>.<ext>` for recordings and drawings, because the first characters of a time-ordered ID stay the same for years, `Recording/` for audio in progress and its manifests, `Inbox/` for items waiting to be ingested. On iOS, `Inbox/` and the recording state sit in the app group container, where the watch link and the widget extension reach them, and `Recording/` stays in the app's own container beside the database. On the Watch, the recording state and what the complication reads sit in the Watch's app group, where its widget extension reaches them, and the outbox and the recordings stay in the Watch app's own container. On the Mac, and in a build with no app group, `Inbox/` is below the store's root too. Each stored recording or drawing has a claim beside it for as long as it is stored, a symbolic link `.<ID>.claim` that names its file, so an ID holds one kind's file: any code that walks `Assets/` must expect those links.
- **File protection on iOS:** `completeUntilFirstUserAuthentication` for everything Knot writes. Recording and ingest must work while the phone is locked, and the default class would block them.
- **Build flavours:** every build that is not a milestone build uses development identifiers: the bundle ID with a `.dev` suffix, its own app group and its own iCloud container. That covers agent builds, PR builds, spikes and tests, and tests also pass the store path in. Development builds from two worktrees never share a store. On iOS each worktree has its own simulators. On the Mac a sandboxed app cannot write into a worktree, so its store sits in the development container, in a folder named for the worktree and chosen by a setting that only debug builds honour. Package tests are not sandboxed and pass a path under the worktree. A build made with the local signing configuration has no app group, and its configuration says so. `StoreLocations` then roots what would sit in the group in the app's own container, in the same `KnotStore/` layout, and reports that the group is absent, so that what needs it is off: the `knot-dev` tool cannot open that store, and the extensions see no recording state. A build that says it has a group and finds no container fails with a typed error. On the build Mac a team-signed build of a development identifier needs one consent dialog for each new signer of each container, which only the owner answers, and while the dialog waits every start of that identifier waits too (§20). On a real iPhone or iPad one development build is installed at a time: a second install replaces the first and inherits its store, which is disposable. Only a milestone build opens the default store or the real iCloud container. A thread started for an agent exports `KNOT_AGENT=1`. With it set, `StoreLocations` refuses the milestone store and the milestone `knot` refuses to run, so an agent cannot open the owner's notes by accident.
- **When data must survive:** notes on the owner's iPhone and iPad are disposable until the M2 milestone build, and notes on his Mac until the M4 milestone build, which needs SP-3's answer on where the Mac store lives. After those builds, every change to the schema or to the store's location ships a tested migration. Schema version 1 is fixed from the commit that the M1 milestone build is made from, `c2a1315b`, the first build installed on the owner's devices: the build after it must open the store that it left there, because on a device a milestone build is installed over the one before, and the app's container, which also holds the retired app's folder, is not cleared between them. Every schema change after that commit is a numbered migration, whichever package makes it, and the first is version 2, which keeps a stored recording's level peaks on its segment (`StoreSchema.migrations`). At each milestone tag the seeded store of §7's snapshots is made by that milestone's build, so M1's is of version 1. A lint fails on GRDB's `eraseDatabaseOnSchemaChange`.
- **Legacy data:** milestone builds reuse the retired app's bundle ID, `com.p3ob7o.knot`, by the owner's decision of 2026-11-19. On a device that had the retired app, v1 therefore shares its container. The retired app kept everything in `Application Support/Knot/` (its `captures.sqlite`, `assets/`, `staging/` and `migration-backups/`) and its settings in the standard defaults domain. v1 never opens, lists, moves or deletes any of that. `StoreLocations` roots everything v1 writes in a folder named `KnotStore/`, in the app's container and in the app group, which is a name the retired app never used. v1 keeps its per-device settings in a named defaults suite and never reads `UserDefaults.standard`. The gate's lint fails on that symbol, on `@AppStorage` without a named store, and on an autosave name that lacks the `v1.` prefix, because the system writes those into the standard domain whatever the app does. It refuses to open a database it did not create, which it tells by the store ID in `store_meta`. A test builds a container laid out as the retired app left it, opens the store there, and checks that every old file is byte for byte as it was and that every key the retired app wrote in the standard domain still has its value. The retired app keeps drafts apart from pending captures, for inactive vaults too, and once it is replaced nothing shows them. So before the first milestone install on a device the owner clears its Recovery window and keeps a copy of the retired app, which can still open its untouched store if something was missed. Every build that is not a milestone build keeps the development identifiers, the spikes and the TestFlight upload of the SP-3 spike app included, so nothing before the M1 milestone build touches the retired app or its container. The first milestone build installed on a device replaces the retired app there.
- **Tables:** `capture`, `note`, `segment`, `segment_history`, `asset`, `job`, `setting`; `change_log`, fed by triggers and consumed only by sync, holding one row per changed record and none for a draft or a recording in progress; `sync_record`, holding CloudKit system fields and the last-synced text per record; `sync_state`, holding the engine's serialised state; and an FTS5 index over titles and segment text, maintained by triggers. A `tombstone` row, an ID with its dates and no content, outlives the purge of each deleted note and segment. `store_meta` holds the store ID, its generation and the device ID. `segment_history` is local and never syncs: it holds text that the command line or MCP replaced and, for a moved segment, the row described in §5, each for 30 days. `counter` is local too: daily counts with no content, which the diagnostics export reads (§19).
- **The change log and the engine:** `change_log` stays the source of pending changes in every case. By CKSyncEngine's headers, which SP-4's code half read and did not run (docs/notes/SP-4.md), the engine keeps the pending changes it tracks in its saved state and clears them on a change of account, so a change of account empties its list, and a kill loses an addition made since the last saved state. So at each launch the adapter tells the engine again about every `change_log` row, by adding it or by setting `hasPendingUntrackedChanges`, whichever SP-4's second stage chooses, and a row leaves only when a sent event reports the record saved with the values the store still holds. An edit made during a send is therefore sent again.
- **Deletes:** soft, through `deletedAt`. A purge job removes rows and files after 30 days and leaves a tombstone, so a device that returns after a long absence cannot bring a purged note back, and `knot changes` can still report the deletion.
- **Migrations:** forward-only and numbered. Only the app migrates. The `knot` tool never does: on a store older than itself it exits with code 7. Before each migration the app makes a copy with `VACUUM INTO` or SQLite's backup interface, because copying the file of a database in WAL mode is not safe. It checks that the copy opens and holds the same counts, and it does not migrate without one. It keeps the newest copy until the following migration. A migration never rewrites or deletes a recording or a drawing. A build that finds a database newer than it understands does not open it, change it or delete it. It reads the version of the newest commit from the database's write-ahead log itself, before any connection touches the store, and copies nothing. It says so, and capture continues into `Inbox/`. A second opener that meets a migration waits for the busy timeout, five seconds, and then gets `store_busy`. Rolling a build back therefore means restoring that copy, and the troubleshooting guide gives the steps. Restoring never deletes anything. The app and the tool are stopped first. A restore builds the new store in a folder beside the store's, from the copy and the current store's recordings and drawings, syncs and checks it, and then puts it in the store's place in one step, by a swap. What the replaced folder held besides the store itself moves into the new store: the folders a capture may wait in, such as `Recording/`, `Outbox/` and an `Inbox/` below the root, and anything another writer put below the root while the restore ran. The rest, its database, its `Copies/` and its files, is set aside whole and kept, so a restored store starts with no kept copies, and the guide says how to export what was captured since. A journal beside the store's folder records the restore's phases, building, built and published, with the new store's ID. The next open, or the next restore, settles a restore that was cut short from that journal and from the store IDs of the two folders, never from which names exist. A restored store gets a new store ID and a generation above every one the store is known to have had, so a cursor or a revision that an agent kept from before the restore is refused as foreign and never taken as current. A restore that finds no record of the generation, in the database or in the store's folder, is not refused: it takes a store that cannot be read as an old one, and its new store ID keeps it apart. With sync on, Knot asks before a restored store uploads.
- **Backups:** the store and its files are never excluded from device backups or Time Machine. A store folder copied to another place opens with every note and file, and WP-10 tests that. With sync on, a fresh install restores from iCloud.
- **Snapshots:** once a day the app writes a copy of the database in the same way and keeps seven. They hold text only, since recordings and drawings stay for 30 days after a delete anyway. Test builds show two actions in About: export the store as it is, which works when the store will not open, and restore a kept copy. A restored copy brings back text. A recording or drawing that was purged after the copy was made shows as missing, never as a broken player, and the restore says how many there are. Captures waiting in `Inbox/` are ingested after a restore as usual: on iOS with an app group `Inbox/` sits in the group, outside the store folder, and in every other build it is below the store's root and moves into the restored store with `Recording/` and `Outbox/`. At each milestone tag a seeded synthetic store made by that build is committed, with work in flight in it: an open capture, a queued job and a pending delete. Every later build must open each one, migrate it and then pass the whole `NoteStore` contract suite on it.
- **Second process on macOS:** the `knot` CLI opens the same file with the same KnotStore code. It posts a Darwin notification after writing. The app then refreshes its observers and feeds the change log to sync. GRDB's observation does not see another process, so the app tells its observers itself when the notification arrives. The notification is a hint. The app also compares the store's change counter with the one it last showed whenever it comes forward, and once a minute while it runs, so a write by a tool that died before it could post is still seen. Anything that writes many rows (a first restore from iCloud, a large inbox, the purge) commits in small batches and yields between them, so a capture never waits behind it. While sync applies fetched changes, the triggers that feed `change_log` are off on its connection, so a change that came from iCloud is not queued to go back.

## 8. Recording

- The file written during recording must be readable after the app is killed. It is Core Audio Format holding 16-bit linear PCM, mono, written through `AVAudioFile`. Its data chunk has no fixed size until the file is closed, so a reader takes the audio to the last complete frame. WP-12's proof step killed 90 recordings on the Mac and in the iOS and watchOS simulators, and lost nothing that had been appended. Fragmented MPEG-4 is not used: its writer does not exist on watchOS, and a file killed in its first three seconds cannot be read (§20). The kill test runs on the live recorder, on injected audio. It runs on the Mac in the package tests. In the iOS Simulator the Mac drives it, because a test there cannot start or kill a process. The gate runs the Mac's in every tier. The Simulator's is the gate's step `recorder-sim`, with the recording state shared by two processes beside it: the gate takes it at every depth where the diff reaches KnotAudio's sources, its crash host, its tests or the package manifest (`RECORDER_SIM` in `scripts/lib/knot_tool.py`), and the nightly run takes it with a fresh seed.
- The working file keeps the input's sample rate from the start, for its whole length. A route change that changes the rate goes through a converter into it, or ends the recording. A recording's length is read from the file, never counted from what was appended.
- The file being recorded is synced to the drive every second (§6, rule 7), on a queue of its own and not on the audio tap's, because a sync can take over 100 ms.
- A full sync of a file never runs on a thread of Swift's cooperative pool, in any module that syncs one: it can hold the thread for long, and a Watch's pool has two. The recorder's start makes its durable writes, the free-space probe, the folder, the manifest, the working file and the folder's sync, in that order on a serial queue of its own, as recovery, conversion and removal do on theirs, and injected audio delivers its buffers from a queue of its own, as the hardware's tap does (pull request 96). The start's queue is serial, so a write that hangs holds every later start, and Knot makes one recording at a time.
- After stop, the audio is converted to AAC mono in `.m4a`, about 0.5 MB per minute, and verified: the recorder's `convert` checks that the converted file's length matches the working file's. The converted file waits beside the working file, at `Recording/<captureID>.m4a`, until the engine moves it into the `AssetStore` and ends the capture with the asset. Only once the capture's row points to the stored asset does the recorder remove the working file and its manifest (`removeWorkingFile`). Below 22.05 kHz the encoder takes at most 48 kbit/s, about 0.36 MB per minute.
- A recording is live when its manifest and its working file exist and the input runs, not when the first buffer has arrived. The time a start takes to be live is measured from the call to `start` to its return. A start runs to live or to a typed error, and a stop always finishes: neither is tied to the task that awaits it. A recording can also end by itself, when the system takes the audio session, the input goes away, a write fails or the 30-minute limit is reached. The session then reports the ending with its reason, and a stop after it is safe.
- The live path feeds the same audio to the transcriber for on-screen text, copied into `Sendable` chunks of samples. The chunk is a KnotCore type, so that the contracts and their fakes need no audio framework, and the copy is small: 100 ms of mono samples at a time. The stream to the transcriber drops its oldest chunks when the transcriber falls behind, so slow text never costs audio.
- If conversion fails, the working file stays as the segment's recording and the queue retries the conversion.
- The orphan that recovery reads is the working file. A manifest that cannot be read does not hide its recording. A recording holds no audio in three cases only: its working file is missing, the file is shorter than its header, or the file was read and holds no frame. A working file that is on the drive and cannot be read now, such as one protected while the device is locked, is kept, untouched, and returned at a later launch once it can be read (`Recorder.recoverOrphans`). Its row is not left open meanwhile, because an open voice row closes the store path to every capture by rule 15: recovery ends a voice row whose working file is on the drive and was not returned as failed with `conversion_failed`, its files kept (§13).
- WP-12's proof step reports the working file's size per minute on each platform. On the watch, a 30-minute recording and its converted copy must fit together.
- A stored recording keeps a small array of level peaks beside it, written while recording, so that a waveform never needs the audio decoded.
- While a recording is made, the recorder may append its peaks to a file beside the working file, `Recording/<captureID>.peaks` (`StoreLocations.recordingPeaks`), in the one format for them, `RecordingPeaks` in KnotCore. The file is a header of 12 bytes, `KNPK`, the format 1, three zero bytes and how many of the recording's own frames one value covers as a 32-bit little-endian integer, then one byte for each value. A value is the largest absolute sample of its stretch, linear, 0 for silence and 255 for full scale, and a stretch is a fixed count of frames, never a buffer: 50 ms of them by `framesPerValue(sampleRate:)`. A reader takes every whole value of a file cut anywhere after its header, answers no peaks for a header it does not know, and holds the values to the audio's length, since they may run a sync ahead of it or behind. A recording never fails, ends or waits because its peaks could not be written. A discard removes them, and `removeWorkingFile` removes them before the working file and the manifest, so that a peaks file never outlives its recording. Recovery judges no recording by them. They are made from audio, so they are in no log line, no error and no diagnostics file. When the capture ends the engine keeps them on the voice segment's row, through `NoteStore.setPeaks` (contract pull request 86, schema version 2). How a Watch recording's peaks reach the iPhone stays open (docs/plan/open-points.md, "Where the level peaks go when a capture ends").
- The saved recording state can outlive a crash, so it carries a heartbeat that the recorder writes every second. A state whose heartbeat is older than three seconds is stale: no recording is running. A heartbeat more than three seconds ahead of now is stale too, because a clock moved back. A press that meets a stale state recovers the orphaned recording and starts a new one, with the started cue, because a person pressing then is starting a recording. Controls show "recording" only while the heartbeat is fresh, the Live Activity carries a stale date, and launch ends an activity that has no recorder. A press while a recording is starting or stopping is ignored. In the app process the recorder itself is the truth: a press stops a recording that this process is running, whatever the heartbeat says. The heartbeat serves the controls and widgets of other processes, and recovery at launch. The rule for a press runs only in a process that has a recorder. Any other process hands the press to the app's process and never waits for an owner that may be dead. There, an idle recorder that finds a saved state recovers the orphan and starts, whether the heartbeat is fresh or stale.
- Playback and recording in one process: the recording wins (`AudioActivity`). A recording that starts stops a player that plays, which reports that it paused where it stood, and a play while this process records is refused, changes nothing and logs one line. A shell offers no playback while it records.
- The live cue's gap, the first frames after a start, goes nowhere, so that the cue's sound stays out of the file. It stays zero until the M2 sitting has said what of the cue reaches the file (docs/checklists/M2.md). The recording state and the live cue say live before a gap above zero would end, so the order of live against the gap is settled before anyone sets the gap above zero.
- The recorder takes its audio from an injected source. Under test it refuses the hardware input, so no automated test and no proof run by an agent opens a microphone on the build Mac.
- If writing fails while a recording runs, for example because the disk filled, the recording stops with the stop cue and its reason, and everything written so far is kept.
- The authoritative transcript comes from transcribing the saved file after stop. Every recording then takes one code path, whether it started in the app, from an intent, on the watch, or was recovered after a crash.

## 9. Speech and cleanup

**Speech**

- `SpeechAnalyzer` with `SpeechTranscriber`. The locale is the English variant set in Settings: by default English as the device's region writes it, when `SpeechTranscriber.supportedLocales` holds that variant, and US English otherwise. `supportedLocale(equivalentTo:)` is not used, because it answers differently from run to run (§20).
- Model assets install through `AssetInventory`. Until they are installed, voice segments stay `recorded` and show as pending. Readiness is read from `installedLocales`, not from `AssetInventory.status`, which follows the process's own reservation. The app reserves its locale with `assetInstallationRequest` at launch, which reserves even when nothing downloads. The system gives no notice when a model arrives, so the transcriber checks again when an install it started ends and when the app comes forward.
- Speech is not available on watchOS.
- Transcription runs over a file in runs. A run starts at an offset, reads at most a budget of audio and ends at the last finished phrase, and the transcriber returns where the next run starts. A range fixed in advance could split a word. The queue hands each run to the store, which saves its pieces and its resume time in one transaction on the segment's own transcribe job, so an interrupted job continues from its last run and a long recording finishes across several short runs. A run is applied only when it starts at the job's stored resume point, so a run applied twice adds its words once. A first phrase longer than the budget is taken whole, so every run that is not the last moves on, and the store refuses a run whose resume point is not after its start with `illegal_transition`, writing nothing, since such a run would add its words at every retry.
- How a file is cut into runs. The budget bounds what a run reads. Silence is not a phrase and never makes a run read more than its budget: a long silence is read in runs of at most the budget, each of them ends with no pieces and moves on, and the store applies such a run like any other. Only a phrase open from the window's start to its edge, a first phrase longer than the budget, makes the window longer: the run reads the window again, twice as long. A run never starts inside a word. It reads from a little before its offset, a quarter of its window and at most a second, in audio the run before heard, and keeps only the words whose middle is not before its offset, so a word heard again is dropped by its own time. The engine's phrase times can fall inside the next word (§20), so no join rests on them: a join is at the end of the last word a run gave, or in the pause after it.
- A run that finishes no phrase has no pieces. It resumes after its offset and no later than the end of its window, or at the end of the file. With nothing heard, the next run starts half a second before the window's end, since a word that begins at the edge is too short there to be heard (§20). With a lone phrase that began later in the window and is open at its edge, the next run starts just before its first word.
- The processing queue passes a budget, 60 s by default, and `knot-eval` passes the same one. Only the tests ask for a run with no budget. A run holds its window's frames in memory before it converts them: about 11.5 MB for a window of 60 s at 48 kHz, twice that each time a first phrase longer than the window makes it longer, and about 345 MB for a run of thirty minutes with no budget.
- The transcriber reads a run's frames before it asks for the model, so a file that cannot be read fails with `audio_unreadable` without the model.
- The engine ignores the cancellation of the task that awaits it. The implementation stops it with `cancelAndFinishNow()`, and the port throws a cancellation within a second. A file with no frames is never given to the analyzer, which would not return: it is ready with empty text.
- A recording in which no words are recognised is ready with empty text, and shows as a recording.
- `SpeechTranscriber` is not available in the iOS Simulator on the build Mac (§20). Tests there use the scripted transcriber, and speech on iOS is proven on hardware.

**Cleanup**

- A `LanguageModelSession` on `SystemLanguageModel(useCase: .general, guardrails: .permissiveContentTransformations)`, and a new session for each request, because a session takes one request at a time. The body is generated as plain text in one call and never streamed: the guard needs the whole answer. The title is a second request, and its failure only drops the title. Guided generation of both at once is not used: in WP-14's probe it tripped the guardrails on harmless text (§20).
- Budgeting uses the model's own `contextSize` and `tokenCount(for:)`. A transcript that does not fit is split on sentence boundaries.
- The fidelity guard is a pure function. It compares cleaned and raw text as word sequences. WP-14 states the allowed differences as a table: letter case, punctuation, and paragraph and list breaks. A word may be removed in three cases only: it is in a closed list of filler sounds (um, uh, er, erm, ah, eh, hm, hmm, mm, mhm); it repeats the word or words that follow it; or it belongs to a restart of at most four words whose first two words come again straight after. A negation, a number, a name or a date word is never removed unless the same word comes back at the same place in what follows the restart. "Like", "you know" and "I mean" are not on the list, because they often carry meaning: whether they ever count as fillers is the owner's choice at the cleanup sitting. Nothing is inserted except punctuation and list markers, and numbers stay as the transcriber wrote them. The guard rejects a result with any other difference, and one that drops more than a set share of the words that are not filler sounds. WP-14 sets that share from its evaluation set, and its proof step uses 40% for now. A mutation suite is a merge criterion: for each evaluation transcript it drops a negation, changes a number, swaps a name, reorders two clauses and adds a word, and the guard must reject every one.
- When the model cannot be used on this device (ineligible device, Apple Intelligence off), the raw transcript is final. When the model is only not ready yet, or the system limits requests, the clean job is deferred and runs later (§4).
- A refusal, an empty or malformed result and a result the guard rejects all end the same way: the raw transcript is the text, and the log records which of them happened. The errors of Foundation Models can hold generated text, so the log records their case and never their description.
- A generated title is one line of plain text, at most 60 characters, made only of words that occur in the note. A title that fails this is dropped, and the stream shows the first line. The same check runs again when a segment leaves the note (§4).
- Cleanup runs with greedy sampling, so the same transcript gives the same result on the same model, and each cleaned segment records the OS build whose model made it.
- The guard proves that words are kept. It does not prove that added punctuation keeps the meaning. The evaluation set has cases in which only the punctuation differs, and they are reported with the meaning-critical ones.

## 10. Ink

- `PKCanvasView` wrapped for SwiftUI. Drawing data is saved at the end of every stroke.
- `PKStrokeRecognizer` produces the recognised text. It is stored on the segment, so every device can search it without recognising again.
- The segment records the text's provenance beside it: the engine's `recognitionVersion`, the language it used and the OS build. In v1 no device recognises a stored drawing again, and a higher `recognitionVersion` triggers nothing. The provenance is kept so that a later version can decide which drawings to recognise again. Recognised text that the user has edited is never replaced.
- Recognition uses the English variant set in Settings, as speech does (§9). A language that the recogniser does not support is a final error, and the drawing shows "Kept, no text" (§4).
- Recognition runs only while the app is in the foreground. That is a choice of design: Knot defers recognition outside the foreground on every device. WP-18's probe saw the recognition service refuse a process that is not an app, and an app in the iOS 27.2 simulator about a second after it left the foreground, even one that held background time. The queue never runs a recognise job from background time or a background task, and a job deferred there runs when the app comes forward. A finished drawing is recognised as its capture ends, while the app is in front, so the usual case is unaffected.
- A port of KnotCore gives a stored drawing's image, for the ink segment view and the app shells. It comes with WP-02's third PR, with a fake that returns a fixture image, and KnotInk implements it in WP-18. Until WP-18 merges, `.live` answers that it is unavailable: the ink segment view shows its placeholder with the recognised text, and nobody has an image to pass to KnotExport, which then writes the drawing's stored data file under its ID and names it in its list (§3). Ink is gated off until M5, so no milestone build holds a drawing before then.
- A Pencil-capability check decides whether the canvas is offered: iPad, and iPhone Duo. WP-18 finds the right API for that check on iPhone.

## 11. Sync

This section is the proposal that spike SP-4 tests.

The code half of SP-4, in its first stage, read CKSyncEngine in the pinned SDK and ran the rules of this section on a harness with no server (docs/notes/SP-4.md). Nothing in it reached iCloud. Each rule below that rests on that reading alone says so, or cites the row of §20 that does, and SP-4's second stage and its report check it against the development container.

- **Container:** `iCloud.com.p3ob7o.knot`, private database.
- **Zone `Stream`:** `Note`, `Segment` and `Setting` records, managed by CKSyncEngine. The text fields `title`, `text` and `rawTranscript` go in `encryptedValues`. That choice cannot be changed for a field once the schema ships.
- **Zone `Attachments`:** one record per asset, holding a `CKAsset`. The engine's fetch options have a zone scope and no `desiredKeys`, so a record it fetches comes whole, assets included (§20). This zone is therefore kept out of every fetch the engine makes by the scope that the delegate returns from `nextFetchChangesOptions`: `.allExcluding([Attachments])`, or the scope it was given with that zone removed. By the SDK's headers the engine asks for those options before each server request, automatic fetches included. SP-4's second stage checks two things this rests on: whether a push for the excluded zone makes the engine fetch nothing again and again, and whether a deleted Attachments zone is still reported. Assets upload from the device that made them and download on demand, outside the engine, with `desiredKeys`, which also fetch an asset's metadata without its file. By CKAsset's header, a downloaded file lands in a staging area that the system clears, so the fetcher moves it into the store at once.
- **Local changes** reach the engine through `change_log`, so a write from any process syncs. `change_log` stays the only list of what waits to go up, whatever the engine keeps (§7).
- **Sending:** the adapter builds each batch itself, from what the store hands out for the current send (§3): only records inside the send's scope, at most 250 of them, and at most a byte budget of field data, 1.5 MB to start with, with one record always allowed alone. By the SDK's headers a change outside the send's scope fails the whole send, and a batch over the server's limits fails with `limitExceeded`, which the engine treats like any other failed send without saying that it splits the batch (§20). So the adapter counts bytes as well as records, and splits a batch refused with `limitExceeded` itself. A record over the record limit (§20) is never put in a batch: the store reports it and keeps it apart (§3).
- **Conflicts:** new segments never conflict. When a text field changed on both sides since the last sync, the server value stays in place and the local value is inserted as a new segment with `conflictOf` set. The copy holds text only and no recording or drawing, so deleting either one never removes a file the other needs. Its ID is derived from the segment, the losing device and the losing revision, so handling the same conflict twice makes one copy.
- **Default:** the switch is on when the device is signed in to iCloud and the `sync` gate is open.
- **Who processes a recording:** the device that ingested it owns its jobs, and `processingOwner` on the segment says which. That is the capturing device, or the iPhone for a watch recording. Other devices show the segment's state and do not process it. Retry on another device moves ownership there. Each move raises `ownerGeneration`. A device writes the text it made only if it still holds the current generation, and otherwise drops its result, so two devices that both finished cannot both publish. Two devices that took the work at the same moment hold the same generation. Then the one with the higher device ID is the owner. Every device applies that rule when the records merge, not only the two that raced, and the other drops its result. An owner that no longer exists shows as "elsewhere", with the action to move the work here.
- **Appends to a deleted note:** a segment that starts after its note's `deletedAt` moves to a new note when the devices sync. The new note's ID is derived from the deleted note's ID, so every device computes the same one and several such segments stay together. A segment whose note record has already been purged is treated the same way. The comparison uses two devices' clocks, so it can misjudge captures made within seconds of the delete. A late segment never lands in a deleted note: if the derived note has been deleted too, the segment moves on to the note derived from that one. A segment whose note has simply not arrived yet waits for the fetch to finish. By the SDK's headers CloudKit does not promise the order of fetched changes, so a segment can arrive before its note, in one event or across two. Such a segment is settled only when `didFetchChanges` comes, and only if every zone's `didFetchRecordZoneChanges` came without an error, because a zone whose fetch failed may still owe the note. Only then does it count as orphaned.
- **A moved segment:** a move (§4) syncs as a change to the segment's `noteID` and `noteGeneration`, together with the new note's record. The higher `noteGeneration` wins. Two sides with the same generation and different notes changed it at the same moment. Then a person's move or return wins over the deleted-note rule above, which the note's ID tells: a derived ID is a version 5 UUID and a fresh one is version 7 (§4). Between two notes of the same kind, the one whose ID sorts higher keeps the segment and the other is left empty. That uses the ID as a fixed tie-break, not as a time. A note that a move, an undo or a merge leaves empty is hidden, as rule 11 of the product spec says, and it is never marked deleted for that reason, so a segment that arrives in it later is not hidden with it. `knot changes` reports it as deleted, and the purge removes it once it has been empty and unchanged for 30 days. Deleting a note marks the note and not its segments, so a segment that another device had moved out before the two synced is no longer in it and stays. That holds until the purge: once the deleted note has been purged with the segments it then held, a move that arrives later does not bring the segment back, as for any change to a purged record. A segment that an undo returned to a note which another device has deleted is deleted with that note, as if the move had never been made, and is recoverable with it. A conflict copy is created in the note of the segment it copies, and follows it.
- **What a merge makes:** applying a fetched batch can make records of its own: a conflict copy, a derived note, or a note reference or an owner that it settled. Those are queued for upload in the same transaction, although the triggers are off on that connection (§7). Only a record applied exactly as it was fetched leaves nothing pending.
- **What syncs when:** a segment syncs once its capture has ended. Drafts and recordings in progress never sync.
- **Machine text:** a write by the processing queue never creates a conflict copy and never overwrites text whose origin is `edited`. Precedence is edited, then cleaned, then raw transcript.
- **Titles and deletes:** a title keeps the later edit, by four rules. A title of origin `user` wins over one of origin `generated` or `none`, whatever the times, because a machine never touches a title of origin `user` (§4). Between two titles of the same origin, the later `titleEditedAt` wins, and at equal times the title that sorts higher by its UTF-8 bytes wins, so that every device decides the same. `titleEditedAt` is the writing device's time of any change to the title or to its origin: a person's edit, the clean job's proposal, and the drop or the return of a generated title when a segment leaves or comes back. A note that never had a title has no `titleEditedAt`, and any time wins over none. An edit that arrives for a deleted note is applied to the deleted copy, which stays deleted.
- **Settings:** the append window, the cleanup switch and the English variant sync. The hotkey, launch at login and the sync switch are per device.
- **Deletes** sync as `deletedAt`. The purge after 30 days deletes the records.
- **Account changes:** signing out pauses sync and keeps local data. Signing in to a different account asks the user before uploading anything. Apple's headers advise otherwise: on a sign-out and on a switch of account they say to delete the local data of the previous account. Knot keeps it on purpose, because its local store is the primary copy, where a capture lands first, and not a cache of iCloud. By the same headers, read by SP-4's code half and not yet observed (docs/notes/SP-4.md), a change of account resets the engine's state and clears every pending change it held, and several changes made while the app was not running arrive as one event. `change_log` keeps what waits to go up (§7).
- **Notes removed from iCloud:** if the zone is deleted or purged from iCloud, Knot keeps the local notes, pauses sync and asks before uploading again. It never deletes local notes because the cloud copy is gone. By the SDK's headers, CKSyncEngine reports a deleted zone with one of three reasons: `deleted`, by the app; `purged`, when the user removed the app's data in the Settings app; and `encryptedDataReset`, when the user reset their encrypted data. For the last two the headers say to delete the locally cached data and not send it to iCloud again. Knot keeps the notes on purpose, for the reason given under account changes. Until the user answers, sync stays paused. After `purged` or `encryptedDataReset` the user asked iCloud to forget, so the prompt's default action keeps sync paused. SP-4's code half translates each reason as the headers describe it, and SP-4 tests each one as CloudKit reports it.
- **Newer records:** a record kind or field this build does not know is kept and saved back untouched (§4).
- **Gate:** the `SyncEngine` exists only when the switch is on and the `sync` feature gate is open.
- **Production schema:** TestFlight builds use CloudKit's production environment, where record types and fields cannot be removed. The schema is deployed there only after M5, when two-device sync and attachment sync have passed on hardware. Moving a device from the development environment to production resets the engine's saved state and uploads the local notes again; SP-4 tests that switch.
- **Structure:** the rules of this section live in a merge core that has no CloudKit in it and works on Knot's own record values. A thin adapter turns CKSyncEngine's events into those values and back. No type that the engine hands its delegate can be built outside it: every event payload, the fetch and send contexts, the engine's `State` and `CKDatabase`'s four change types have no accessible initialiser, and the engine needs a `CKDatabase`, which comes only from a container (§20). So the adapter has two layers. The delegate does nothing but one `switch` over the event, which unpacks each payload into records, record IDs, zone IDs, reasons and errors. The layer below it builds the batches, chooses the fetch scope and translates the events, and it takes only types a test can make and returns the core's values. The replica simulation and every named sync test run on the core, the layer below the `switch` has tests of its own, and the `switch` and the factory that makes the engine are proven by SP-4's harness, in its second stage against the development container, and on hardware at M4.
- **A long absence:** a device that returns after more than 30 days must not bring back what was purged, and must not lose a capture it never uploaded. A record this device had synced and that iCloud no longer has is treated as deleted here. A record it never uploaded is uploaded. Tombstones (§7) back the same rule locally. The age of a synced delete is measured between two dates the server gave, the delete's own and the newest this device has seen, never against the device's clock, so a device whose clock runs ahead cannot purge early. SP-4 fixes the mechanism, and the simulation has a replica that stays away for 31 days.
- **Recordings and drawings:** an asset is local only, uploading or published, and the segment's record says which, so another device can say "not uploaded yet" and never shows a broken player. Uploads sit in a durable queue and resume. "Remove recording" during an upload cancels it and removes the remote copy when one exists. Transfers follow the system's Low Data Mode.
- **Account isolation:** the engine's saved state is kept per iCloud account and per CloudKit environment. So is `sync_record`: a record counts as synced only for the account, the environment and the zone identity it was synced under. The zone carries an identity of its own, written when the zone is made, so a zone that was removed and made again is a different zone. That keeps two rules of this section apart: a record missing from the zone it was synced to is deleted here, and a zone that is gone or new deletes nothing. The account is the `recordName` of the user record ID that the engine's account event carries, as SP-4's code half read the SDK. That identifier stays in the store, and is never logged, shown, synced, exported or written to the diagnostics file (§19). The store is in device backups (§7), and by the headers the engine's saved state holds the last user record ID too, so it does not stay on one device. The environment comes from the entitlement the build was signed with, because no API that SP-4's code half read reports it. A fetch that would delete more than a set share of the local notes pauses sync and asks. The share is counted over the whole fetch, from the deletions the store holds until the fetch ends (§3). The first value is a tenth of them, an estimate. A change of account raises an account generation, and work started under the old one is dropped when it returns, so nothing queued for one account can reach another. Both answers to the upload question are defined: yes uploads the local notes to the new account, and no keeps sync paused.
- **The simulation's invariants:** it runs with two and with three replicas, and its interleavings include moves and their undos beside edits, appends and deletes. After any interleaving it checks six things. The replicas end equal. Nothing a replica acknowledged is missing. Nothing made after a delete sits in a deleted note. A conflict copy appears only when both sides edited the text. Applying a batch twice changes nothing. Every segment is in exactly one note, and a note with no live segment is never shown. Its named cases include a zone that was removed and made again, every replica uploading again after a change of environment, a replica whose clock runs 40 days ahead, two devices that take the same recording at the same generation, and every order of a move, its undo and a delete across three replicas.

## 12. Watch link

- **Watch outbox:** `<captureID>.m4a` and `<captureID>.json`. The manifest holds the capture ID, start, end, duration, device and checksum.
- **Send:** `WCSession.transferFile`, with the manifest as metadata. The watch keeps the file until the phone acknowledges that capture ID. The session's `didFinish` without an error is not a delivery: in the simulator it came for files that never reached the iPhone app. Only the acknowledgement moves a capture out of the outbox.
- **Receive:** the phone's delegate must move the received file before it returns, because the system deletes the file afterwards. It moves the file into `Inbox/` with `DurableFile`, checks it against its manifest, and acknowledges with `transferUserInfo` once it is durably there. Ingest follows and does not hold the acknowledgement, so a phone whose store will not open cannot fill the watch.
- **Coordinator:** the watch's sequence of record, convert and send lives in KnotLink beside the outbox, and the watch app only hosts it. It is tested on the Mac with kill points, and it finishes a conversion that a kill interrupted at the next launch.
- **Retry:** the watch re-sends each capture that is neither acknowledged nor still outstanding, on every trigger: when the session activates, when reachability changes, when either app comes forward, after each new capture, and on its background refresh. A capture that is still outstanding is never queued again. At launch the watch first waits for the session's activation callback and adopts `outstandingFileTransfers` by the capture ID in their metadata, before it queues anything again, so a relaunch makes no duplicate. Cancelling a transfer gives no delegate call, so the transport reports the cancel itself. A capture queued for longer than a set time with no `didFinish` and no acknowledgement, while the session is activated and reachable, is cancelled and queued again. That stall rule rests on the time since queueing until SP-2's sitting shows that a transfer's progress moves. Duplicates are harmless, because ingest is idempotent.
- **Checksums:** the phone checks each file against its manifest and acknowledges only a file that matches. On a mismatch the watch sends the file again. On the third mismatch the phone ingests what it received as a failed capture and keeps it, and it still does not acknowledge. The watch keeps its own copy, shows it as not delivered, and tries again when the session next activates. An intact delivery later replaces the damaged copy and makes the capture stored.
- **Back channel:** the phone sends the watch no note text and nothing about a transcript, because the watch is a capture device only (product spec §6). The watch learns that a recording arrived from the acknowledgement above. `updateApplicationContext` carries only what the watch needs to say whether a recording continues a note or starts a new one (product spec §3, rule 4): the end of the capture that a new recording would join, if there is one, and the window. The phone works that out by the rules of product spec §3, so a note closed by "New note" and a deleted note give none. What the watch shows is a forecast. The phone decides at ingest, by the recording's own timestamps. The Watch reads `receivedApplicationContext` at activation and does not wait for a callback at launch.
- **Testing:** in the 27.2 simulators files from the Watch to the iPhone, and user info in either direction, do not reach the other app, while application context, from iPhone to Watch, and `sendMessage`, from Watch to iPhone, do. The logic is tested against a fake transport, and the real transport has no simulator test. Delivery is tested on hardware.

## 13. Processes and extensions

| Platform | Process | Opens the database | Role |
|---|---|---|---|
| iOS | App | Yes, the only one | Runs the intents that record or write notes, the processing queue and sync. |
| iOS | Widget extension | No | Controls, widgets and Live Activity views. Reads recording state from app-group defaults. |
| watchOS | App | There is no database | Recorder, outbox files, link. |
| watchOS | Widget extension | No | Complications, Smart Stack widget, control. |
| macOS | App | Yes | Everything, plus the hotkey and panel. |
| macOS | `knot` command | Yes, with the same code | Short-lived. Posts a notification after writing. Never migrates: it exits with code 7 on a store older than itself. |
| macOS | `knot mcp` | Yes, with the same code | Lives as long as its client's session. On every call it reads the access switch and the schema version again, inside the transaction, and refuses when access is off or the store is newer than the build. |

Launch, in the app process: the capture surface is on screen before any launch step runs, and typing does not wait for them (§6, rule 6). The steps are: open the store, recover recordings, ingest the inbox, finish the open captures of earlier launches, resume jobs, start sync if it is on. Ingest comes before the open captures are finished, because the two orders give different results (§5). Recovering recordings reads their orphaned files (`Recorder.recoverOrphans`). Their rows end with the other open captures, after ingest. A voice row whose working file is on the drive and could not be read ends failed with `conversion_failed`, never open, and its files stay for a later launch (§8). A step that fails is logged with its code, and the steps that do not depend on it still run. The steps that need the store are skipped when it did not open. Jobs and sync start only after recovery and ingest have ended, so neither works on a half-recovered store. Each step has a breaker: if the last two launches died inside it, it is skipped and the diagnostics say so.

The breaker's rule has a known cost. A store that dies at every open crashes two launches in three: two launches die in the step, the third skips it, and the next tries it again. And the breaker cannot tell a crash from any other end of the process, so every end of the process inside a step counts as a death. Whether the breaker backs off further, and whether a new build clears its marks, is an open point (docs/plan/open-points.md, "The launch breaker's back-off").

The composition wraps some ports in types of KnotApp that forward each operation by hand: `TimedCaptureEngine`, which times a typed save, and `LaunchGatedQueue`, which holds the processing queue until the launch releases it, both in `LaunchGatedQueue.swift`; `RefusingCaptureEngine`, the engine of a build with no store place, in `LiveComposition.swift`; and `GatedNoteStore`, `GatedAssetStore`, `GatedSettingsStore` and `GatedAssetFetcher`, which answer for a store that is not open yet, in `StoreGate.swift`. An operation that a contract pull request adds with a default is answered from that default in the app, silently, until someone adds its forward. So a contract pull request that adds an operation lists the wrappers of its port that forward by hand, and the pull request of the operation's first caller adds each forward with a test at the composition's level that fails without it, as `EngineForwardingTests` does for `press`, `live` and the peaks.

## 14. Intents and system surfaces

| Intent | Protocols | Runs in | Used by |
|---|---|---|---|
| ToggleRecording | `AudioRecordingIntent` and `LiveActivityIntent`. iPhone and iPad only. It starts a recording when idle and stops the one that is running. | App process | Action Button, controls, Siri, Shortcuts |
| StopRecording | `LiveActivityIntent`. iPhone and iPad only. | App process | Live Activity, Dynamic Island |
| StartRecording on the Mac | Opens the panel already recording, with a stop control | App process | Siri, Shortcuts |
| StartRecording on the Watch | Opens the watch app already recording. Whether it can start without the app in front is SP-2's question. It calls the watch recorder, not `CaptureEngine`. | Watch app | Complication, control, Siri |
| OpenCapture, OpenSketch, OpenSearch | Opens the app on the capture surface, the canvas, or the stream with search focused | App process | Widgets, controls, Shortcuts |
| CreateNote, AppendText | The system notes schema (`createNote`, `appendText`) | App process, in the background | Siri, Shortcuts |
| FindNotes | Entity query | App process | Shortcuts |

Rules taken from Apple's documentation, to be confirmed by SP-1:

- ToggleRecording and StopRecording must be compiled into both the app and the widget extension.
- The Live Activity must start with the recording and last as long as it does, or the system stops the recording.
- If Live Activities are off or the microphone permission is missing, the intent must open the app.

Intents reach the environment through the App Intents dependency manager, which the app registers at launch. The widget extension links KnotIntents for the types only, and no intent runs there. An intent reads the environment through one accessor that fails with a typed error when nothing is registered, so an intent that the system runs in the wrong process fails safely. That accessor is `@Dependency(default:)` with the unavailable environment as its default, because `AppDependencyManager` has no lookup that can fail: in a process that registered nothing, the intent gets the unavailable environment and throws the typed error. Every intent that writes declares `allowedExecutionTargets = [.main]` (OS 27), so the system cannot run it in the extension. The Live Activity's attributes type lives in KnotIntents and belongs to WP-19. WP-01 proves the packaging with one trivial intent that appears in both the app and the widget extension.

CreateNote answers the system notes schema, which asks of `createNote` a required name, an optional content, attachments, a pin and a folder. The orchestrator ruled on 2026-11-22, where the documents were silent, and the owner can overturn it (`CreateNoteRule`). The capture goes through the engine as a typed capture into a new note, and once it is stored the title is set through `NoteStore.setTitle`, as the app's own title edit sets it: an intent holds no storage code, but it may call a port. A name with content is the title when `Limits.checkTitle` takes it. A name alone is the note's text, with no title. A name that the title rule refuses is the text's first line, above the content. A name and a content that are both empty once trimmed are refused, with nothing written, by a refusal of the call's form that carries no code of the catalog. Attachments are refused with `capture_invalid`, and nothing is written. A pin or a folder asked for is not applied: the note is saved, and the dialog says so. The folder and account entities that the schema requires exist, and their queries find none. `updateNote` is not built. A death or a refusal between the capture's save and the title leaves the note with no title (§20). An intent is tested by calling it: each runs through App Intents' own perform flow in the package's tests.

Shortcuts get StartRecording and StopRecording on every platform, and each is safe to repeat. ToggleRecording is for buttons: the Action Button and the controls.

On iPhone and iPad the intents that start a recording declare `supportedModes = [.background, .foreground(.dynamic)]`. They start in the background and call `continueInForeground` only when Live Activities are off or the microphone is refused, which is how the intent opens the app. StopRecording never needs the app in front and declares `[.background]`.

Knot's URL scheme only navigates: it opens the capture surface or a note. It never writes text and never starts a recording.

Intents on iPhone, iPad and Mac call `CaptureEngine`, and watch intents call the watch recorder. None contains storage code. `LiveActivityIntent` is used only on iPhone and iPad. The pinned SDK marks it unavailable on macOS (§20), so a type that adopts it, or that uses ActivityKit, is compiled for iOS only, inside `#if os(iOS)`. `canImport(ActivityKit)` does not tell the two apart, because it is true on the Mac too. The note entity is not indexed, so nothing about a note appears in Spotlight. Intents that only write may run on a locked device. Intents that read or pick a note require authentication, and declare `authenticationPolicy = .requiresAuthentication`, because the default is `.alwaysAllowed` (§20).

## 15. Mac specifics

- **Hotkey keys:** a key with at least one modifier, or a function key. A modifier alone is not possible with this API. SP-5 proves press and release in a sandboxed build, and the panel over a full-screen app. If press and release do not arrive, the fallback is a listen-only event tap, which needs the Input Monitoring permission.
- **Hotkey:** Carbon `RegisterEventHotKey`. It delivers both press and release, and developers report that it works in the sandbox with no extra permission. A small state machine with a 250 ms threshold separates a tap from a hold. It times presses with a monotonic clock, and a release that arrives before the mark has been handled is a tap, so no press does nothing. A tap is known at key release, and the panel must accept typing within 100 ms of it. A hold is known at the 250 ms mark, and the microphone opens then, never on a tap, so the system's microphone indicator lights only for a recording. The audio engine is prepared at key-down, so that the microphone is live within 150 ms of the mark. SP-5 measures whether first words get clipped. If they do, the alternative is to listen from key-down into a buffer that a tap discards, on built-in and wired inputs only. Hold-to-record is exempt from the one-second discard.
- **Hotkey failures:** if the key is already registered by another app, Settings says so and asks for another key. If a release never arrives, the recording goes on with the panel showing and a stop control. Esc or another press of the hotkey stops it, and Knot checks the key's state every second while recording.
- **Panel:** an `NSPanel` that does not activate the app and joins every Space, including full-screen apps. It opens on the display that has the keyboard focus. A tap makes it the key window. A hold shows it without making it key, and it hides shortly after the text has arrived unless the pointer or the keyboard enters it. It has a microphone control that starts and stops a recording, for when a key cannot be held.
- **Menu bar:** a click opens the menu, as the system's convention has it. The icon shows when Knot is recording.
- **Activation:** Knot is an accessory app (menu bar only) that becomes a regular app while its main window is open.
- **CLI and MCP:** pending spike SP-3. The preferred design is a sandboxed executable inside the app bundle, carrying the app-group entitlement and opening the store directly. The fallback is a CLI that talks to the running app over XPC. SP-3 tests a sandboxed build signed for development. The owner planned the early upload at the review's gate: at G1 he creates an App Store Connect record for the development identifier and an API key, and one internal TestFlight upload of the spike app in wave 1 checks distribution signing. The upload runs only once he has handed over the key, and the key is revoked after each upload. The XPC fallback is built only if SP-3 fails in wave 1, never later. SP-3 is closed only when the route it chooses has passed the distribution-signed check: if the direct route fails there, the XPC route gets an internal upload of its own, and the report says what the tool does when Knot is not running. Development builds of the Mac app and the tool are to use the Team-ID form of the app group, `$(TeamIdentifierPrefix)com.p3ob7o.knot.dev`. A bare tool signed for development carries no profile and is refused the `group.` form (§20), so the gate's development-signed step, in which the tool writes and the app shows it, can pass only with the Team-ID form. The form of the milestone builds waits for the distribution-signed check and the owner (docs/notes/SP-3.md). `Apps/Config/Identifiers.xcconfig` still names the `group.` form for development builds. It changes with SP-3's report, in a pull request of WP-01's. Until it does, a team-signed build of the main tree claims the `group.` form, and only SP-3's own builds use the Team-ID form. SP-3's code half confirmed the two packaging rules on the build Mac. A tool started from Terminal traps before `main` without its own `app-sandbox` entitlement ("Process is not in an inherited sandbox.") and without an Info.plist in its binary ("Info.plist from code signature information has no value for kCFBundleIdentifierKey."). A bare executable carries no provisioning profile, and with the Team-ID form it needs none. The tool reads its flavour and version from something that survives a symbolic link, such as a value compiled in, or a shell script that `exec`s its real path. Settings puts `knot` on the PATH as such a script, and whether it writes the script or shows the line to run is chosen in WP-34, with the owner (docs/notes/SP-3.md). Through a link `Bundle.main` finds no Info.plist (§20), so WP-01's `knot` takes the default flavour, `dev`, and would not refuse an agent the milestone tool. SP-5 checks that reading the key's state once a second works in the sandbox without Input Monitoring. A sandboxed tool cannot write to a folder given as an argument (§20), so `knot export` writes to standard output, as an archive or one stream, or into a folder in the group container that it names. The owner chooses which, on SP-3's report.
- **MCP:** standard input and output transport, tools only, written by hand, with conformance tests. It speaks the 2026-07-28 revision, which has no handshake, and also the handshake of the 2025-11-25 and 2025-06-18 revisions, because clients of both kinds are in use. WP-34 reads the specification before writing, as §21 requires for Apple's APIs. Nothing but protocol messages goes to standard output, and the server exits at end of input. While command-line access is off it keeps answering and fails each tool call with the reason, because a client restarts a server that exits. An MCP client that is itself a sandboxed app cannot start the tool: started by a sandboxed app, a tool with its own sandbox traps in sandbox setup (§20). The text of the Settings row and docs/cli.md say so, and give MCP clients the tool's absolute path.
- **One command table.** A single table of commands generates the command-line help, the usage errors, the MCP tool list, docs/cli.md and the golden tests, so they cannot drift apart.
- **The command-line gate:** in a milestone build below M4 the gate of the command line is closed, and the tool answers it as it answers the switch turned off: `access_off`, exit code 4. It reads the gate first and the setting second (`Agent.checkAccess`).
- **Two builds, two names.** A development build installs the tool as `knot-dev`, and `knot status` prints the flavour and the store it opened.

## 17. Testing

| Layer | What is tested | Where it runs |
|---|---|---|
| Rules and state machines | Table-driven tests with a fake clock | `swift test` on the Mac |
| Contract suites | One shared suite per port, run against both the fake and the real implementation | Mac, and the iOS Simulator for what runs only there (§5): those suites are hosted in the iOS app, in the `Knot-iOS-Tests` target, and the gate's `ios-hosted` step runs them |
| Store | Migrations, search, concurrency, a kill in mid-transaction, a second process | Mac |
| Recorder | File-driven input, the kill test, interruptions | Mac and iOS Simulator |
| Speech, cleanup | Fixtures, with accuracy reported | A Mac with the models installed |
| Ink | Fixtures, with accuracy reported | Tests hosted in the app in the iOS Simulator, never the package tests |
| Sync | Mapping, conflicts and the change log, with constructed records; a two-replica simulation | Mac |
| End to end | Fixture audio through to a finished note; kill and relaunch | Mac and Simulator |
| UI smoke | Type, record with injected audio, search, delete and undo | XCUITest on iOS Simulator and Mac |
| Hardware | Action Button, Lock Screen, hotkey, Pencil, watch delivery, real sync | Paolo, from `docs/checklists/` |

Rules:

- Fixtures are synthetic. Real notes and recordings never enter the repository or a test.
- Storage, capture, ingest and sync need failure-path tests through the production interface.
- A test that needs an on-device model reports "skipped: model unavailable". It never passes silently.
- A merge-gate run requires the on-device models on the Mac, where a skipped model test fails the run. In the iOS Simulator speech is always the scripted transcriber, because the real one is not available there, and cleanup may be the real model. `scripts/doctor.sh` probes both models before a gate run.
- The owner's own recordings never enter the test suite or the repository. The two `knot-eval` commands may read them from the folder that `KNOT_LOCAL_FIXTURES` names, which sits outside every worktree (§18). They print numbers only, and they write transcripts and the ten cleanup pairs back into that folder, never anywhere else.
- The capture ledger soak test is seeded and time-boxed. It uses the scripted transcriber, cleaner and recogniser, clips of at most two seconds and an injected clock. The harness is a parent process that starts a child over the real store, kills it at points the seed chooses from a named list, and relaunches it. The parent is the witness: the child reports each acknowledged capture with its revision and a hash of its content, the parent keeps that list, and after recovery it checks every entry against the store. A capture that vanished whole therefore fails the run. The run ends with one consistency check, shared with the store's tests and the diagnostics export: capture, segment and job rows agree, no capture ID is stored twice, and the foreign keys and the search index are clean. The parent reads what the stream returns, checks every piece of a long capture and the script's text exactly, and checks after each launch's recovery as well as at the end. A run that its time box cut short is not green. WP-06 builds the harness right after the store's first PR, and its second PR has the child run a recording on the live recorder with injected audio. WP-11, WP-12 and WP-15 each add their kill points in their own PRs. It runs at each milestone and in the merge gate of any PR that touches KnotCore, KnotStore, KnotCapture, KnotAudio, KnotApp, the harness or the pinned GRDB version.
- Mac UI tests need the one desktop session, so they queue on an exclusive slot.
- On the build Mac no UI test synthesizes an event: no click, no key, no menu, no `activate()`. The runner's events are real ones that go to whatever app is in front, and the owner works at that Mac. A Mac UI test launches through `KnotLauncher`, reads the accessibility tree, runs the audit and ends the app with `terminate()`. What it must enter comes through a launch argument that only a debug build honours, as the Mac's `.live` smoke test enters its line with `-KnotEnterLine`. What needs real typing or clicking on the Mac is a row of the owner's checklist, or runs on the hosted runner, for which the orchestrator's next scripts pull request adds a job. Four exclusions of the audit hold on the Mac alone. Three go by structure, since the elements have no name to give: the window's content as SwiftUI hosts it and a column that `NavigationSplitView` hosts, for the description audit, whose children are audited; and the window's title, which the system draws in the toolbar and dims while the window is not key, as it is in a test that does not bring the app to the front, for the contrast audit only. The fourth covers one issue that names no element at all, a parent and child mismatch. WP-41 revisits them.
- A test leaves no file outside its own folders. A file of a defaults suite that a test wrote counts too.
- A test that needs two calls in an order makes that order with a hook, never by the order in which it starts two tasks.
- No test blocks a thread of Swift's cooperative pool. A wait in a test is async, or it runs on a thread of its own: a blocked thread of the pool can hang a run on a runner with few cores, where the build Mac never shows it (§20).
- No suite has a bound that a loaded machine can miss. Every wait of the suites ends through `SuiteWait`, in KnotTestSupport, after ten minutes, with an issue that names what it waited for. A test that holds something back, such as a store hold or a scripted wait, bounds its own calls into what it tests the same way, so that a deadlock fails and does not hang. A bound of seconds is a bound that a loaded Mac reaches: two waits of ten seconds of the recorder's tests ran out together at a loaded gate (pull request 92). A wait rests on an order, a hook's or a queue's, and a hook records nothing itself: each test records its hooks' unmet waits as its own issues, so that none is counted against no test.
- A package test reads `Fixtures/generated/` only through `FixtureFiles`, before any model check. Every run that runs package tests speaks the audio first. A test that reads generated audio asserts nothing about its words unless it also needs a model, which only the build Mac has. A fixture is looked up before a model is asked for: a missing or changed fixture fails the test, and a test skips only on a missing model.
- These failure tests are required by name: two processes recording captures at once; a late draft save that must not replace newer text; an edit that arrives while a clean job is paused; a delete while a job runs; an interrupted transcription that continues from its last range; an unreadable inbox item; a checksum mismatch from the watch; a zone removed from iCloud; a hotkey release that never arrives; search text full of query syntax; a clock moved backwards; a database newer than the build; a store that will not open; a press while the saved recording state is stale; a record with an unknown kind. The engineering review added these: a capture begun before the store is open, during a migration and while another process holds the write lock; a checkpoint from `Inbox/` older than the stored text; the same capture ID with different content; a job found running at launch twice; a disk that fills during a draft save, a recording, ingest and a migration; a long typing session with sync off that leaves no more `change_log` rows than records; a fetched change that leaves nothing pending; a segment record that arrives before its note; a kill between applying a batch and saving the engine's state; a store restored from an older copy; a segment at the size limit; a change of account with uploads pending; a replica that stays away for 31 days; two devices that both finish the same recording; and export names made from hostile titles. The owner's answers at the review's gate added these: a segment moved on two devices before they sync; a move that meets a delete of the note it left; an undo that returns a segment to a note deleted elsewhere; a kill inside a move; and a container that still holds the retired app's files. The second engineering pass added these: a store call that commits after its capture fell back to `Inbox/`; a move repeated after a capture joined the new note; a return after the segment's note changed again; a move that arrives after the purge; a merge result that must be uploaded; a tool that dies before its notification; a revision from before a restore; text that runs past the size limit, repeated; an inbox item of a newer version, ingested after an update; an emptied note that appears in `knot changes`; `StoreLocations` with a missing group container; and a kill during the pre-migration copy.
- The checks are shown to fail. WP-06 merges only when four injected faults each turn the soak red: an acknowledgement before the write, a skipped capture row, a dropped last checkpoint and a capture stored twice. The `NoteStore` contract suite runs against three deliberately broken fakes, one that ignores a repeated capture ID, one that lowers a revision and one that loses a move's history, and must fail each.
- A seeded differential test applies random sequences of operations to the in-memory `NoteStore` and to the real one and compares every result. WP-34's golden tests run on both.
- Kill tests need a process to kill. WP-01 declares a small crash-host executable for KnotStore, for KnotAudio, for KnotLink and for KnotInk, and the soak's child.
- The nightly run executes the package tests under Thread Sanitizer. A lint keeps `@unchecked Sendable`, `nonisolated(unsafe)` and `@preconcurrency` to a reviewed list. A recorder test feeds 30 minutes of injected audio and counts the same frames out.
- Every query in the `NoteStore` contract has an index, and a test shows the query plan. A stream page is one query.
- A PR that changes the cleanup instructions, the guard or the speech settings reruns the cleanup evaluation and `knot-eval`, and states the results before and after.
- Accuracy thresholds are checked in the package PRs that own them and at milestones. The merge gate only requires that model tests ran.
- Package tests use Swift Testing: tables as parameterised tests, and a tag on every test this section names. XCTest is used for UI tests and for measured performance only. A contract suite is a set of functions in KnotTestSupport that take a factory, and each implementation's test target calls them. WP-01 proves that arrangement with one dummy port before WP-02 relies on it.
- `docs/plan/named-tests.txt` lists every test this section names with the package that owns it. The gate fails when a listed test is missing once its package has merged.
- One UI smoke test on each platform runs the app on its real composition with a temporary store. On the iPhone and the Mac that is `.live`: type, kill, relaunch, read. On the Watch, which has no typing and composes itself: record on injected audio, and read "Saved". The other UI tests stay on `.preview`.
- A UI smoke test on a real composition reads back what was composed, because a test that reads labels alone would pass with a fake. On the Watch, which has no typing, it reads a debug-only element that names the recorder's and the link's types, the outbox count and whether the store's root is temporary.
- The end-to-end suite carries a canary. Its fixtures hold a made-up word, and the test fails if that word appears in any log line, error or diagnostics file. It reads the log entries that its own process wrote under Knot's subsystem at the info level and above, from the system's store of them (`ProcessLog`). A line at the debug level is not kept by the system and is not read. What guards one is the logging facade, which takes a static event and typed fields at every level, with the lint's rule on log calls.
- Search is checked against a plain scan. For a seeded store, whole-word and prefix queries return the same notes as a scan of the text, across typed, spoken and handwritten segments and titles, and never a deleted note.
- Every UI smoke test runs the system's accessibility audit, which exists on all four platforms. Exclusions sit in one file, each with a reason. WP-41 makes the audit clean on every designed cell of the state matrix. The preview test reads that matrix from the brief's own table, so there is no second list to keep in step.
- Time thresholds are not merge criteria. The gate asserts query plans and counts of operations. Times are measured by `scripts/verify.sh --perf`, which takes every build slot, at milestones and in WP-42, on an optimised build with a seeded store of 10,000 notes and 20,000 segments. Since pull request 116 that build is optimised with the fakes (`KNOT_FAKES`), compiled for testing (`-enable-testing`) and with `DEBUG` defined. Eleven test targets import their module with `@testable`, which a module compiled without testing cannot serve, and two test files use members declared under `#if DEBUG` alone, of the seven such blocks in the sources. So in the measured build internal declarations stay reachable from other modules, and the optimiser may not drop them or treat them as private, and those debug hooks are compiled in: a measured time can be a little slower than the shipped app's, never faster. WP-42 decides whether `DEBUG` leaves the measured build (docs/plan/WP-42.md).
- The scripts have a self-test that `--quick` runs: a slot is released when its holder is killed, a failure prints the agreed fields, and the plan check catches a brief with a missing heading.

## 18. Build, tools and parallel work

- `.xcode-version` names the Xcode for the merge gate and the archive. Every script sets `DEVELOPER_DIR` from it and checks `xcodebuild -version` against it, so nobody has to remember a prefix. The beta Xcode is used only when a command names it.
- `scripts/bootstrap.sh` checks the prerequisites first (Xcode, XcodeGen at its pinned version, the simulator runtimes) and then generates the Xcode project. A missing prerequisite stops it with the command that installs it.
- `scripts/doctor.sh` runs first in every verify run and fails at once on a machine setting no agent can change, such as Automation Mode for Mac UI tests. It also refuses to run below a floor of free disk space. It refuses a repository, a build folder or a fixtures folder that a cloud file provider syncs, which is where the stray "… 2" copies in the retired tree came from. It probes that the gate's signed step can sign without a prompt.
- `scripts/verify.sh` has five tiers, and one run takes one tier: `--quick` checks formatting, builds the package and runs its tests; `--full` adds every app build and the UI smoke tests; `--soak` runs the capture ledger soak test, with `--seed` to repeat a run; `--perf` measures the timed targets and takes every build slot; `--gate` is what the orchestrator runs before a merge. `--only <step>` and `--module <name>` run one part, and `--skip mac-ui` is for implementers. The gate chooses its own depth from the diff, by the table below, prints the depth and the reason, and refuses `--only`, `--module` and `--skip`, so a partial run can never be called a gate.
- Two things in `scripts/verify.sh` that a system dialog can hold have a time limit. The packaging step starts the `knot-dev` it built with a limit of 30 seconds (`KNOT_TOOL_START_LIMIT`). Each xcodebuild run of UI tests, in the launch step and the Mac UI step, has xcodebuild's test limits on, 3 minutes a case and 5 at most, and an outer limit of 20 minutes (`KNOT_UI_TEST_LIMIT`). At the tool's limit or the outer limit the step fails and says that a system dialog, such as a consent prompt, may be waiting for the owner on the Mac, which no agent answers. Three starts have no such limit yet: the hosted iOS test run, the simulator launches, and the Mac app's own start in the launch step, which ends after ten seconds by its own loop without that message. WP-01 adds them in a pull request of its own.
- Every run ends with one summary line: counts, skips, duration, the Xcode version and the macOS build. It also keeps a status line of at most 140 characters, which `--status-line` prints for the tree it checked, and the orchestrator posts that one as a commit status. A failed step names itself, its log file and the command that reruns only that step. A failed soak also prints its seed, its kill point and where its store was kept.
- Every script reports failure through one function in `scripts/lib/fail.sh`: a stable code, what failed, the fix, whether a retry is safe, and what was changed.
- Each worktree builds into its own `.build/` and DerivedData, uses simulators named after the worktree, and gives its development builds a store of their own (§7). `scripts/worktree-remove.sh` removes all three, with the worktree's folder in the Mac development container. Agent builds turn the index store off, and each worktree keeps a small fixed set of simulators.
- `scripts/build-slot.sh` limits concurrent heavy builds on the machine. The default is 3. A slot is a lock the system releases when its holder dies. It uses `/usr/bin/lockf`, which ships with macOS; `flock` does not. One of the three slots is kept for the gate. A waiting script prints a line each minute and gives up after a set time, naming the holders. Mac UI tests queue on one exclusive slot, and the script also limits how many simulators are booted at once.
- Builds for tests use a local configuration that keeps the sandbox and leaves out the entitlements that need the owner's signing profile, with sync switched off. Device builds, milestone builds and the spikes use registered identifiers and the owner's signing: the development set for device builds and spikes, and `com.p3ob7o.knot` with its group and container for milestone builds only (§7). On the build Mac a locally signed and a team-signed build of one development identifier share a container only after a consent dialog for each new signer, which the owner answers, and while the dialog waits every start of that identifier waits, the gate's locally signed tool included (§7, §20).
- The owner's recordings live in one folder outside every worktree, named by `KNOT_LOCAL_FIXTURES`. `knot-eval --set synthetic` runs on committed fixtures and `--set local` on that folder. Either one exits with a code when its input or its model is missing. It never waits. For each recording `<name>.m4a` in that folder, `knot-eval speech` writes the raw transcript, and nothing else, to `<name>.transcript.txt` beside it, and `knot-eval cleanup` reads those files and writes `cleanup-pairs.md` there. The exit statuses are 2 for wrong arguments, 3 for a command that is not built yet, 4 for missing input and 5 for a missing model.
- `scripts/install.sh` exits non-zero when it missed a device, and a rerun skips the devices that already hold the build. `devicectl` does not install onto a Mac, so for a Mac the script writes the build to a folder the owner names, and he opens it there. From the M4 milestone build on, no milestone build is installed or run on the build Mac.
- A milestone build is made with a level, M1 to M7. A feature whose milestone has not passed is switched off in it by a gate, and a test lists the gates for each level: sync and the command line open at M4, and ink at M5. A fix for an earlier milestone is built at that milestone's level, so it carries no feature that has not had its sitting.
- `scripts/release.sh` takes the App Store Connect key as a file path only. In a dry run it prints the names of its variables and never their values. After a failed upload it says to check App Store Connect before a retry. It belongs to WP-43.
- `scripts/sdk-path.sh <platform> <framework>` prints where the Swift interfaces of the pinned Xcode are (§21).
- Formatting uses `swift format` from the toolchain with the checked-in configuration. After WP-01 merges, `scripts/` belongs to the orchestrator.
- Two steps start the Mac app on the owner's desktop, both of the one development bundle ID: the launch step's Mac part and the Mac UI step. The Mac UI step holds the exclusive Mac UI slot. The launch step holds a simulator slot and not that one, so its Mac app can come to the front beside another worktree's Mac UI test.
- The scripts take their tree from `KNOT_TREE` when the environment holds one, and `scripts/build-slot.sh` exports its own checkout's tree to the command it runs. So a script of another worktree is started with that worktree's own `build-slot.sh`, from inside it: started through another checkout's, it builds and tests that other checkout, silently.
- A `swift test --filter` that matches nothing ends with status 0 and runs no test, so a run is checked by the count of the tests it ran. The soak's step fails a run in which no test ran.
- A launch of the Mac app by a script or a test ignores saved window state: the launch step and the Mac UI tests pass `-ApplePersistenceIgnoreState YES` as the first arguments. The pair is not seen when a flag that takes no value, such as `-KnotPreview`, comes before it. Every development build shares one bundle ID, and so one saved window state, so a window closed once on the build Mac's desktop left every later launch with no window, in every worktree and at the gate. A launch that shows no window is read against saved state and the desktop before the code. No agent resets an app's container or its saved state by hand.

**The gate's depth.** A fixed table maps the changed paths to a depth, and the gate applies it without anyone choosing:

| The diff touches | The gate runs |
|---|---|
| Documents only | The plan check and the link check. No build. |
| One leaf module (Speech, Cleanup, Ink, Export, Link, Intents, Agent, or a widget folder) | The checks below, the package tests with the models required, a build of every app, and the UI smoke tests that module can reach |
| KnotCore, KnotStore, KnotCapture, KnotAudio, KnotSync, KnotUI, KnotApp, an app shell, `Package.swift`, `project.yml`, `scripts/`, entitlements or the pinned GRDB version | Everything: the same on every platform, the two-process test, the `.live` smoke tests, and the soak where §17 asks for it |

Every depth starts with the same checks: `doctor`, formatting, path ownership (the diff stays inside the paths the package owns), the contract check on KnotCore, the import check, the named-test list, the dependency pins, and a lint for a team ID, a network call, logged text, the standard defaults domain (§7), `eraseDatabaseOnSchemaChange`, an unlisted concurrency escape (§17), a required-reason API with no declared reason (§19), and a file whose name ends in " 2". The lint reads names and patterns, not meaning: a pass is not proof that no note text is logged, so the review reads for that, and reads every line that a `knot-lint: allow` comment excuses. The team-ID check reads the owner's signing configuration, which is on the build Mac and in no repository, and it runs at every depth, the documents depth too. Where the configuration is absent the step is skipped, never passed, and the gate fails on a skipped step. The gate takes the configuration for this check alone, through `KNOT_TEAM_CONFIG`. It refuses `KNOT_LOCAL_CONFIG` and removes a link to a local configuration that an earlier run left in the tree, so that it builds what every thread builds. The check reads tracked files only: a commit message and a pull request's description are outside it. Mac UI tests run only where the diff reaches the Mac app, KnotUI, `scripts/` or `.xcode-version`, and nightly, because they take over the desktop. The soak runs where the diff reaches the sources of KnotCore, KnotStore, KnotCapture, KnotAudio or KnotApp, the soak's child in `Packages/KnotKit/Sources/KnotSoakChild/`, the harness in `Packages/KnotKit/Tests/KnotSoak/` or `Packages/KnotKit/Package.resolved`, or where the diff of `Packages/KnotKit/Package.swift` names GRDB (`SOAK` in `scripts/lib/knot_tool.py`). A change to those modules' tests alone does not take it. A pull request that changes only the scripts does not take it either, and the orchestrator then runs the step by hand. The recorder's step in the iOS Simulator, `recorder-sim`, runs where the diff reaches KnotAudio's sources, its crash host, its tests or the package manifest (`RECORDER_SIM` in `scripts/lib/knot_tool.py`), and nightly (§8). WP-01 measures each depth. The aims are 12 minutes for a leaf and 25 for everything, both estimates. A step whose suite is not built yet is listed in `scripts/gate-steps.txt` with the package that delivers it, and it becomes required when that package merges. A nightly run on `main` does everything, with a fresh soak seed and on the iOS 27.0 runtime as well, which is the oldest system Knot supports.

**The merge queue.** GitHub's own queue is not offered to a repository owned by a personal account, so the orchestrator runs one.

- One pull request at a time. The order is contract PRs, then fixes for a red `main`, then the chain to the next milestone, then the rest by dependency.
- A PR enters when its review verdict is recorded, the `--quick` summary is on its head and the ownership check passes. From then on its branch is frozen.
- The orchestrator brings the branch up to date in its own gate worktree. When `main` has moved, it merges `main` into the branch, and once the gate has passed on that merge it pushes it as an ordinary push. It never rebases a branch that was pushed and never forces a push. A conflict goes back to the implementer. It runs the gate on that exact head, posts the status `knot/gate` with the summary line, and squash-merges at that exact head through GitHub's REST call for merging a pull request, with `sha` set to the tested head and the header `Time-Zone: Etc/UTC` (docs/orchestrator.md, the merge queue's step 5). It does not use `gh pr merge`, which sends no such header. The candidate is three hashes: the base, the head and the tree. If `main` or the head moved, the result is void. After the merge it checks that the tree on `main` is the tree it tested.
- Since 2026-11-20 the ruleset on `main` requires a pull request, squash as the only merge method, an up-to-date branch and two checks, `knot/gate` and `quick`, the hosted workflow's run of `scripts/verify.sh --quick`, and nobody bypasses it. The orchestrator set it at the owner's request. GitHub refuses a merge without both checks. Interactions with the repository are limited to collaborators until 2027-05-20.
- A failed step is rerun once, and only for an infrastructure code from `fail.sh`. A test that passes on a rerun is logged with an owner. The soak is never rerun to green, and storage, capture and sync tests are never set aside.
- A red night stops the queue. The cause is found by bisecting the squash merges, and it is reverted unless the fix is plain.
- A contract PR is additive where it can be: a new requirement comes with a default that throws the typed unavailable error, so open branches still compile. A breaking one carries the mechanical edits to every conformer and call site, as a stated exception to path ownership. A contract PR that only adds merges in the normal queue. One that breaks merges at one of two fixed times a day.
- Each pull request has a branch of its own. A branch whose pull request was squashed gets no further commits: the thread starts the package's next pull request on a new branch from `main`.
- Stacking happens only inside one package, and a stacked branch stays local until its base has merged. The thread records its fork point, rebases with `--onto` after the base is squashed, and only then pushes the branch for the first time.
- After the queue has updated a branch, its thread fast-forwards to the remote branch before it changes anything else.
- A pull request that did not come from one of the project's own threads is never run through the gate before its diff has been read, because the gate runs its code on the owner's Mac. The scripts that drive the gate come from `main`, not from the branch.
- macOS and Xcode on the build Mac are updated between milestones, never while one is being closed.

**The orchestrator's state.** It can be rebuilt from the repository, GitHub and one file.

- The briefs in `docs/plan/` carry what does not change: what each package owns, what it starts after and how many PRs it has, in a header a script can read.
- GitHub carries what changes: a branch name gives the package, labels give the queue state and a blocked code, and commit statuses carry the `--quick` and gate summaries. `scripts/status.sh` prints the table from those. `docs/status.md` is that output, written to `main` only at milestones.
- A journal in the build folder outside every worktree records each operation before it starts and when it ends, with the base, the head and the tree: a thread launched, a PR queued, a branch update pushed, a gate run, a merge, a worktree removed, a milestone build, an install. After a reset the orchestrator reads `docs/orchestrator.md`, runs `scripts/status.sh`, compares the journal with GitHub and the worktrees, and finishes or undoes an operation that was cut short before it does anything new. A release step that was cut short is never resumed. It goes back to the owner.
- At M1 a fresh thread takes over from the runbook alone, as a drill.

**What stays out of the repository.** The signing team's ID is not a secret, since it is in every signed app, but it ties the project to one account. It lives in a git-ignored `Local.xcconfig` in the build folder outside every worktree, named by `KNOT_LOCAL_CONFIG`, which `scripts/bootstrap.sh` links into a fresh worktree. Entitlements use the team prefix variable, code reads group identifiers from the Info.plist, and the lint fails when the local file's value appears in a tracked file. The repository is public, so it never gets a self-hosted runner. Its workflows hold no secrets, never use `pull_request_target`, have read-only permissions and pin their actions by revision. GRDB's revision is pinned as well as its version, and `scripts/verify.sh` checks it for SwiftPM and for Xcode, because the generated project's lock file is not committed.

## 19. Privacy and security

- **Entitlements:** app sandbox on the Mac, app group, iCloud with CloudKit, push (CloudKit uses it for change notifications), microphone, background audio.
- **Network:** CloudKit and Apple's model downloads only. Knot contacts no other host.
- **Logging:** `Logger` with categories. Logs hold IDs, counts, durations and error codes. They never hold text, transcripts, content-derived file names or audio, nor the identifier of the iCloud account (§11), which stays in the store and is never shown, synced, exported or written to the diagnostics file either.
- **Privacy manifest:** declares no collected data, and a required reason for each API that needs one, in every target. The SP-3 upload carries the manifests, so App Store Connect checks them in wave 1. The pull request that brings such an API into a module adds its reason to the manifest of every target that links the module, even where the manifest is another package's (PLAN.md §8.5). The gate's lint fails when one is missing in a target that its list names, and the review checks the reason's code.
- **Another program on the device:** the store defends against a crash, a kill and a power cut. It does not defend against a program that runs as the user and rewrites the store's folders while Knot runs: such a program can make Knot lose or misplace data, as it could by deleting the folder.
- **Errors:** every case of the error taxonomy carries a stable code, what to do next, whether a retry is safe and how often, and what was written. The command line, `--json`, MCP results and log lines all render from that one value. docs/errors.md has an entry for each code, and a test fails when a case has none. An unexpected failure carries a request ID and the command that shows its trace. No error ever contains note text.
- **Command-line access:** the `knot` tool refuses commands until the owner turns on command-line access in Settings on that Mac. It is off by default. While it is off the MCP server keeps answering and fails each tool call with the reason (§15). Deletes made through them are soft, and no command purges. Tool results mark note text as data, not as instructions. The switch is consent, not a wall: any program running as the user can reach the file itself, and the privacy text says so.
- **The player:** in a process whose hardware input `HardwareInputPolicy` refuses, a test's, a simulator's or an agent's, the player renders offline, by `AVAudioEngine`'s manual rendering, and nothing plays aloud: the one policy decides for the microphone and the speaker.
- **Diagnostics:** test builds can export a diagnostics file from About: capture rows without their content hash, job rows, the daily counters, signpost timings, the build and the OS. The counters (§7) hold captures by kind, captures and jobs that failed, uses of "New note", moves and returns. A move counts when it is made, a return counts apart, and a repeat that changes nothing counts as neither. The keep-gate sitting reads them (PLAN.md). It holds no note text, no titles and no content-derived names. Every log line about a capture carries the capture ID, which is the same on the watch, the phone and the Mac. A player's log line carries the asset's ID instead, since a player knows the file it plays and not the capture.
- **Search input:** search text is turned into a quoted query. Query syntax never reaches the full-text index raw.
- **Privacy text:** the README and the App Store privacy text say exactly what iCloud encrypts end to end and what it does not, checked against Apple's documentation when WP-43 writes them.
- **Agents and the owner's notes:** the build agents run as the owner's user. They use `knot-dev` from their worktree and never `knot`, their threads export `KNOT_AGENT=1` (§7), and the MCP server for the real store is registered for one personal folder, not for the user. By the owner's decision of 2026-11-19 the build Mac holds no real notes while the build runs, and from the M4 milestone build his real notes on a Mac live on his other Mac.
- **Text from outside:** agents act only on the project's own `wp/`, `spike/` and `contract/` branches. They never read issue or pull-request comments from GitHub, and review findings travel between threads. During the build the repository limits interactions to collaborators.
- **Limits at every door:** an MCP frame, piped text, a manifest and a synced record are each bounded in size (§4), and a file's path comes from its ID.
- **The microphone:** no automated test and no agent opens a hardware input on the build Mac (§8).
- **What a test's or an agent's process may not do:** open a hardware input, or ask the system to install a speech model, which may download. Such a process is known by its signs: it runs in a simulator, whose microphone is the Mac's; it holds a test bundle, or a test runner started it; or `KNOT_AGENT=1` is set. KnotAudio's recorder refuses the hardware input on any of them (`HardwareInputPolicy`), before it touches the hardware. KnotSpeech's live speech system refuses an install in a test's process or an agent's (`SpeechInstallPolicy`), before it asks the system anything. One type of KnotCore reads the signs, `ProcessSigns`, since contract pull request 101: `HardwareInputPolicy`, `SpeechInstallPolicy` and `StoreLocations` take them from it, and each says which it heeds and what it refuses.
- **UI tests:** an app that `XCUIApplication()` starts on the Mac carries none of those signs, and the three launch tests set no environment. Every UI test launches the app with `KNOT_AGENT=1`, through one launcher in `Apps/UITestSupport/`, and a test shows that the app so launched refuses the hardware input. The launcher comes with WP-22's first pull request, which makes the composition live. It keeps its own constant for the mark, `KnotLauncher.agentMark`, since a UI test's target does not link KnotCore. No UI test records.
