# WP-13 proof: SpeechAnalyzer and the `Transcriber` port

The proof step of WP-13, 2026-11-19, on the build Mac: a Mac16,9 with an M4 Max, macOS 27.3 (26C5047e), Xcode 27.2 (27B52). Its code is on the branch `wp/13-proof`, at `9cb270d`, where PR 1 starts. This note has two readers: WP-02, which writes the `Transcriber` port from it, and the orchestrator, which keeps docs/architecture.md.

Every example here is synthetic. The run on the owner's recordings is still to come: they are not on the Mac yet (see [The owner's recordings](#the-owners-recordings)).

## In short

The draft port of docs/architecture.md §5, "Report availability. Transcribe a file. Stream live text for buffers.", fits the API in outline. Four things in it have to change:

1. **Availability has five states, not two.** The port reports why it cannot run, because each reason ends differently. Availability has to be read from `installedLocales`, because `AssetInventory.status` says "not installed" for a model that is installed and works.
2. **A file is transcribed in runs that end where a phrase ends, not in fixed ranges.** Each run returns the text it finished and the time where the next run starts.
3. **Live text takes Sendable chunks of samples, not buffers.** `AVAudioPCMBuffer` is not `Sendable`, so a stream of buffers cannot cross from the recorder into the transcriber under Swift 6.
4. **Cancelling the task does not stop the engine.** The implementation must call `cancelAndFinishNow()`, and then the engine returns normally while its results end with `CancellationError`. The port promises the caller a plain `CancellationError` within a second.

The accuracy is good enough to build on: 5.8% word error rate on the clean clip, under the 8% that PR 1 must meet. Speed on the Mac is about 100 times real time: ten minutes of audio in 6 to 8 seconds.

## What the API does

The API is `SpeechAnalyzer`, an actor, with `SpeechTranscriber` as its module. The analyzer reads audio. The transcriber hands out results on its own `results` sequence, which a second task reads. Each final result is a phrase of a few words with its time range.

**Streaming**

- **Files.** `analyzeSequence(from: AVAudioFile)` reads from the file's `framePosition`, so a run can start at an offset. The results' times then count from that offset, not from the start of the file, and the caller adds the offset back.
- **Live.** With the `progressiveTranscription` preset, volatile results replace each other and final ones append. On the clean clip, fed in 100 ms chunks at four times real time, the first text came after 1.5 s of audio. There were 63 volatile updates and 2 final ones, and the final text scored 5.8%, the same as the file.
- **Formats.** The transcriber accepts 16 kHz or 8 kHz mono 16-bit audio. `AnalyzerInputConverter` (OS 27) converts any buffer to that, so the recorder's own format can go straight in.

**Cancellation**

- Cancelling the Swift task that awaits `analyzeSequence(from:)` does nothing. In the probe the cancelled call went on and transcribed the whole ten-minute file.
- `cancelAndFinishNow()` stops it. `analyzeSequence` then **returns normally**, with the time it reached, and the `results` sequence **throws `CancellationError`**.
- The proof wraps the run in `withTaskCancellationHandler` and calls `cancelAndFinishNow()` from it. A run cancelled after 1.56 s threw within 0.01 s. A live stream whose consumer went away ended within 0.03 s.

**Failures.** What each condition does in the API, and the case the proof maps it to:

| Condition | What the API does | Proof's case |
|---|---|---|
| The file is missing | `AVAudioFile` throws `com.apple.coreaudio.avfaudio` 2003334207 (`'wht?'`) | audio unreadable |
| The file is not audio | The same, 1954115647 (`'typ?'`) | audio unreadable |
| An `.m4a` cut short, as by a crash before it was finalised | The same as a missing file. A WAV cut short reads what is there. | audio unreadable |
| The file has no frames | `analyzeSequence` returns nil. Then **`finalizeAndFinishThroughEndOfInput()` never returns**, and after `cancelAndFinishNow()` the results never end. | Not an error. The proof never starts the analyzer on an empty file and returns empty text. |
| Silence | No results | Not an error: empty text |
| A supported locale whose model is not installed (fr_FR) | SFSpeechError 3, `unexpectedAudioFormat`, "Audio format is not supported", **not** `noModel` | model not installed, found by checking before the run |
| An unknown locale (xx_XX) | The same SFSpeechError 3. `AssetInventory.status` is `.unsupported`. | unsupported locale |
| The iOS Simulator | `isAvailable` is false, and the install request throws SFSpeechError 4, `noModel` | unavailable |
| Declared, not seen: `insufficientResources` (16), `tooManyAssetLocalesAllocated` (11) | | resources, a deferral |
| Declared, not seen: `noModel` (4), `assetLocaleNotAllocated` (10) | | model not installed |
| Declared, not seen: `audioReadFailed` (2), `audioDisordered` (17) | | audio unreadable |
| Anything else | | transcription failed, with SFSpeechError's code |

The engine's errors hold no audio and no text, so the code is safe to log.

**Availability, installing and the locale**

- **`AssetInventory.status` is not availability.** In a fresh process it said `.supported`, which means "not installed", although `installedLocales` listed en_US and transcription worked. After `assetInstallationRequest(supporting:)` it said `.installed`, and `reservedLocales` held en_US. The next process saw `.supported` and nothing reserved. The status follows the caller's reservation, not the model on disk. A process may reserve at most 5 locales (`maximumReservedLocales`).
- **Installing took 0.05 s, because nothing downloaded.** The system already had every English model on this Mac before this work began. `assetInstallationRequest` returned nil, which means nothing to download, and it reserved the locale. A first download was not measured: the Mac had nothing to download, and the Simulator cannot install.
- **`supportedLocale(equivalentTo:)` is not stable.** For en_IT, which has no English variant of its own, it answered en_ZA on one run and en_NZ on the next. The proof picks the exact language and region from `supportedLocales`, and US English otherwise. That is what product spec §11 asks: the device region by default, falling back to US English. The device's `en_US@rg=atzzzz` gives en_US.
- **No asset version.** The API names no model or asset version. A transcript's provenance is the engine, the locale and the OS build, as `transcription` on `Segment` already says (§4).
- **No notice when the model arrives.** The SDK has no sequence or notification for a change of `AssetInventory.Status`. To run deferred jobs "when the model's availability changes" (§4), the transcriber checks again when an install it started finishes and when the app comes forward.

- **Speed.** The whole set took 7.0 to 11.3 s across five runs, 0.010 to 0.016 of real time. The ten-minute clip took 5.8 to 8.1 s. These are measurements, not targets.
- **Scoring.** The normalisation is named `knot-wer-1`, and the proof's `SpeechScoring.swift` states it. Both sides are lower-cased. Money in digits is written out, times and thousands separators are split, and punctuation is dropped. Number words become digits ("seven" is 7, "twelfth" is 12th), "dr" becomes "doctor", and a closed list of British spellings becomes American. The last rule matters for the owner's run. The read-aloud references are written in British English ("harbour", "cancelled", "tyres"), and an en-US transcriber writes American spelling, which would otherwise count as errors.

**Resumable runs.** The ten-minute clip, transcribed whole and in runs that each read at most a set length of audio:

| Runs of | Runs | WER | Total time | Slowest run |
|---|---|---|---|---|
| whole file | 1 | 0.121 | 5.8 s | 5.8 s |
| 60 s | 11 | 0.130 | 7.2 s | 0.76 s |
| 20 s | 43 | 0.122 | 11.5 s | 0.38 s |

Each run drops its last phrase, which the cut may have split, and the next run starts where that phrase started. No two runs overlapped and none failed to move on. Running in short pieces costs about 0.13 s a run and almost no accuracy. So a long recording can finish across several short spells of background time.

The first probe was a bare executable. This one is a SwiftUI app with a bundle ID and an Info.plist, in `Spikes/WP-13-speech-probe` on `wp/13-proof`, launched with `simctl` on this worktree's iPhone simulator: iPhone18,1, iOS 27.2 (24B8117).

- `DictationTranscriber` is different. It lists nine English locales, and its status is `.supported`, so its model could perhaps be downloaded there. That was not tried, because the one install allowed was the speech model's. `SFSpeechRecognizer` reports no on-device recognition.

## For WP-02: the port

**1. Readiness, five states.**

| State | Means | The queue |
|---|---|---|
| ready | The model is on the device | runs the job |
| notInstalled | Supported, model missing | asks for the install, and defers the job |
| installing | The model is downloading | defers the job |
| unsupportedLocale | The chosen English variant is not supported | settings fall back to US English |
| unavailable | No SpeechTranscriber on this device: the Simulator, or hardware without it | the recording stays a recording with no text, and Retry on another device moves the work |

`install()` reserves the locale and downloads when needed. Only the app calls it, and `knot-eval` never does. It reports progress, which `AssetInstallationRequest.progress` gives.

**2. Files, in runs.** One call transcribes from an offset, with an optional budget of audio. It returns the finished pieces, each with its time range in the file, and the time the next run starts, or nil when the file is done. The queue saves the pieces and that time after each run, so an interrupted job goes on from its last run. That replaces "transcription runs over a file in ranges" (§9): a range fixed in advance can split a word, and a run that ends where a phrase ends does not.

**3. Live, over Sendable chunks.** Live text takes a sequence of `Sendable` audio chunks. A chunk is mono samples with their sample rate, a KnotCore type. The recorder copies each buffer into a chunk, which costs 64 KB a second at 16 kHz. Each update carries the final text so far and the volatile tail after it. Live text is for the screen only, and the authoritative transcript comes from the file (§8).

**4. Cancellation.** Cancelling the calling task cancels the run, and the call throws `CancellationError` within a second, with nothing saved from that run. It is a yield, not an attempt. The implementation must call `cancelAndFinishNow()` itself, because the API ignores task cancellation.

**5. Failures.** Each is a case of the taxonomy, in three classes:

- **Deferrals**, never counted: model not installed, model installing, system resources limited.
- **Attempts**, counted: audio unreadable, transcription failed with the engine's code.
- **Final**: speech unavailable on this device. The recording is kept without text.
- **Not failures**: an empty or silent recording is ready with empty text. A cancellation is a yield.

The proposed port, for WP-02 to settle:

```swift
public protocol Transcriber: Sendable {
    /// The English variant in use: the exact one when supported, otherwise en-US.
    var locale: Locale { get }
    func readiness() async -> TranscriberReadiness
    /// Reserves the locale and downloads its model when needed. The app only.
    func install(progress: @escaping @Sendable (Double) -> Void) async throws(KnotError)
    /// Transcribes from `offset`. With a budget, reads at most that much audio and ends
    /// at the last finished phrase. Cancelling the task throws CancellationError.
    func transcribe(file: URL, from offset: Duration, budget: Duration?) async throws(KnotError) -> TranscriptionRun
    /// Live text for the screen. The stream throws only KnotError, and ends when the chunks do.
    func live(_ chunks: some AsyncSequence<AudioChunk, Never> & Sendable) -> AsyncThrowingStream<LiveTranscript, any Error>
}

public enum TranscriberReadiness: Sendable, Equatable {
    case ready, notInstalled, installing, unsupportedLocale, unavailable
}

public struct TranscriptionRun: Sendable, Equatable {
    public let pieces: [TranscriptPiece]       // finished phrases, in order
    public let resumeAt: Duration?             // nil when the file is done
    public let provenance: TranscriptProvenance // engine, locale, OS build
}

public struct TranscriptPiece: Sendable, Equatable {
    public let text: String
    public let range: Range<Duration>          // in the file's own time
}

public struct AudioChunk: Sendable, Equatable {
    public let samples: [Float]                // mono
    public let sampleRate: Double
}

public struct LiveTranscript: Sendable, Equatable {
    public let final: String
    public let volatile: String
}
```

The fake that WP-02 ships, the scripted transcriber, has to script these cases: every readiness state; a change from notInstalled to ready; pieces over several runs with a resume time; each failure; an empty file; a cancellation during a run; and live updates that are volatile and then final. The contract suite runs them against the fake and against the real transcriber on the Mac. The proof's tests in `SpeechEngineProofTests.swift` are the start of the real side.

## Changes this asks of the architecture

1. **§5, the `Transcriber` row.** "Report availability. Transcribe a file. Stream live text for buffers." becomes: report readiness in five states, install with progress, transcribe a file in resumable runs, and stream live text for `Sendable` audio chunks. The port is above.
2. **§5, the error taxonomy.** Two new cases: "speech unavailable on this device", which is final, and "transcription failed", an attempt that carries the engine's code. "Speech model not installed" moves to the deferrals beside "model not ready", as §4 and the brief already treat it. An empty or silent recording is not an error.
3. **§9, speech.** "Transcription runs over a file in ranges and can start from an offset" becomes: in runs that each read at most a budget of audio and end at the last finished phrase, the transcriber returning where the next run starts. Add three rules:
   - Readiness comes from `installedLocales`, not from `AssetInventory.status`, which follows the app's reservation.
   - The locale is the exact language and region from `supportedLocales`, otherwise en-US, and never `supportedLocale(equivalentTo:)`.
   - The app reserves its locale through `assetInstallationRequest` at launch. That reserves even when nothing downloads, and a process may reserve at most 5 locales.
4. **§8, the live path.** "The live path feeds the same buffers to the transcriber" becomes "the same audio, copied into `Sendable` chunks".
5. **§20, platform facts.** Replace the Simulator row with the result inside an app, and add these rows. Each comes from a probe on this Mac on 2026-11-19:
   - `SpeechTranscriber` is unavailable inside an app in the iOS 27.2 simulator (24B8117), as in a bare executable. `DictationTranscriber` lists English locales there with status `.supported`, untested further.
   - Cancelling the awaiting task does not stop `SpeechAnalyzer.analyzeSequence`. `cancelAndFinishNow()` does: the call then returns normally and `results` throws `CancellationError`.
   - On a file of zero frames, `finalizeAndFinishThroughEndOfInput()` never returns, and `results` never ends.
   - A supported locale whose model is not installed fails with `unexpectedAudioFormat`, not `noModel`.
   - `AssetInventory.status` follows the process's reservation. `installedLocales` reports the model on disk.
   - `supportedLocale(equivalentTo:)` answers differently from run to run for a region with no English variant.
   - The API exposes no model or asset version.
   - On an M4 Max, a ten-minute file is transcribed in 6 to 8 s.

## Not verified yet
