# WP-12 proof: the recording format and the `Recorder` port

The proof step of WP-12, 2026-11-19, on the build Mac: a Mac16,9 with an M4 Max, macOS 27.3 (26C5047e), Xcode 27.2 (27B52). Its code is on the branch `wp/12-proof`, at `303c9a6`, where PR 1 starts. This note has two readers: WP-02, which writes the `Recorder` port from it, and the orchestrator, which keeps docs/architecture.md.

Every number comes from WP-04's generated audio, injected into the recorder. No microphone was opened. The simulators run on the Mac's processor and drive, so their times are the Mac's, not a phone's or a watch's.

## In short

- **The working file is Core Audio Format: 16-bit linear PCM, mono, written through `AVAudioFile`.** It came through 90 kills on the Mac, the iOS Simulator and the watchOS Simulator with nothing lost: every frame `append` had accepted was in the file, unchanged.
- **Fragmented MPEG-4 is out.** `AVAssetWriter` does not exist on watchOS. Where it exists, a file it is writing cannot be read until its first three seconds are written, and 17 of 40 kills left a file that neither `AVAudioFile` nor `AVAssetReader` could open.
- **The draft `Recorder` port does not fit the real API.** It has nowhere to put live audio or durable progress, no way to say that a recording ended by itself, and nothing on cancellation. "For WP-02: the port" gives the replacement.
- **Start latency on injected audio** is 18 ms to live on the Mac from a cold process and 13 ms warm, almost all of it three syncs to the drive. In the simulators it is 33 to 38 ms cold.
- **The working file is 1.92 MB a minute at 16 kHz and 5.76 MB at 48 kHz**, the same on every platform. A 30-minute recording on the watch and its stored copy take 68 MB together at 16 kHz and 186 MB at 48 kHz.

## How it was measured

`KnotAudioCrashHost`, the crash host WP-01 declared for KnotAudio, does the work. It runs on the Mac and, through `xcrun simctl spawn`, in this worktree's iPhone and watch simulators. An optimised build of it measured the tables below.

- **`record`** plays a clip into a working file at the pace of real time, in 100 ms buffers, the smallest a tap delivers, and syncs once a second with `F_FULLFSYNC`. After each append and each sync it writes the two frame counts into a small witness file with `pwrite`, which a kill does not undo.
- **`kill-test`**, on the Mac, starts a `record` child, waits until it is live, waits a delay its seed chooses, from 0.3 to 6 s, and kills it with SIGKILL. It then reads the file back through the same runner, so a file written in a simulator is read in that simulator, and compares it with the witness and with the injected samples. In the 16 kHz CAF runs every fifth trial kills the child within 20 ms of its start instead.
- **A trial passes** when the file is readable, holds all but at most one second of the frames the witness says `append` had accepted, and, for CAF, every frame it holds equals the injected audio. A kill before the first append may leave no file. That passes, because nothing was acknowledged.
- **The audio.** The 16 kHz runs use `clean.wav`. The 48 kHz runs use the same clip resampled once on the Mac, so the child and the reader see the same samples. The sizes use `long.m4a`, ten minutes of speech.
- **The named test** `recording-format-kill-test` runs four trials of the CAF kill test on the Mac in `scripts/verify.sh --quick`, with a fresh seed that a failure prints.

To repeat a run in the iOS Simulator: build the crash host with `xcodebuild -scheme KnotAudioCrashHost -destination 'generic/platform=iOS Simulator'` in `Packages/KnotKit`, then run the Mac's crash host as `KnotAudioCrashHost kill-test --format caf --source <clip> --dir <folder> --runner "xcrun simctl spawn <udid>" --child <simulator build>`.

## The format chosen, and why

**The kill test.** Lost audio is what `append` had accepted and the file did not hold.

| Platform | Format | Rate | Trials | Passed | Unreadable | Lost, worst | Lost, median |
|---|---|---|---|---|---|---|---|
| Mac | CAF | 16 kHz | 20 | 20 | 0 | 0 ms | 0 ms |
| Mac | CAF | 48 kHz | 10 | 10 | 0 | 0 ms | 0 ms |
| iOS Simulator | CAF | 16 kHz | 20 | 20 | 0 | 0 ms | 0 ms |
| iOS Simulator | CAF | 48 kHz | 10 | 10 | 0 | 0 ms | 0 ms |
| watchOS Simulator | CAF | 16 kHz | 20 | 20 | 0 | 0 ms | 0 ms |
| watchOS Simulator | CAF | 48 kHz | 10 | 10 | 0 | 0 ms | 0 ms |
| Mac | fMP4 | 16 kHz | 10 | 3 | 6 | 1060 ms | 160 ms |
| Mac | fMP4 | 48 kHz | 10 | 7 | 3 | 845 ms | 251 ms |
| iOS Simulator | fMP4 | 16 kHz | 10 | 6 | 3 | 1076 ms | 476 ms |
| iOS Simulator | fMP4 | 48 kHz | 10 | 5 | 5 | 951 ms | 848 ms |

The "lost" columns count readable files only. The kills fell between 0.4 and 6 s into each recording. Of the twelve early kills, eight came before the file existed and left none, and four left a file of 7,296 bytes: the header and the one buffer appended, unchanged.

**Why CAF survives.** `AVAudioFile` writes the CAF data chunk with its size set to -1, which the format defines as "to the end of the file", and leaves it so until the file is closed. A reader takes the audio to the last complete frame, with no repair. Each linear PCM write reaches the kernel before it returns, so a kill loses nothing that `append` accepted. Probed by hand: a file that holds only its 4 KB header reads as 0 frames, and so does one cut at 100 bytes or ending in half a frame. A file cut at 20 bytes, inside the format chunk that ends at byte 52, is unreadable (`kAudioFileInvalidFileError`), and so is an empty one (`kAudioFileUnspecifiedError`). Recovery treats all of them as a recording with no audio.

**Why fragmented MPEG-4 fails.** `AVAssetWriter` with a movie fragment every second writes about the first three seconds of audio (2.94 s at 16 kHz, 3.05 s at 48 kHz) as a bare `mdat` box and only then the `moov` box that describes it. Every file killed before that point, the latest at 3.0 s, was unreadable to both `AVAudioFile` and `AVAssetReader` (AVFoundation -11829). After it, each fragment's audio is written before its `moof` box, so a kill loses the open fragment, and one kill lost 1.08 s. A fragment every 0.25 s cut the later loss to about 150 ms but left the first three seconds unreadable. Many voice notes last only a few seconds, so that hole rules the format out even before watchOS is counted.

**The sample rate.** The working file keeps the input's rate at the start of the recording. Nothing is resampled in the usual case, which spares the watch's processor. A route change that changes the input's rate goes through an `AVAudioConverter` into the file's rate, or ends the recording. CAF and `AVAudioFile` take any rate.

## Start latency

On injected audio, from the call that starts a recording, as the median and the 95th percentile of 20 runs, in milliseconds. "Cold" is the first recording of a fresh process, "warm" the second to twenty-first of one process. The steps are cumulative:

- **Manifest:** a stand-in for the `CaptureManifest`, written as `DurableFile` will write it: write, sync, rename, sync the folder.
- **File:** the working file exists with its header, and its folder is synced.
- **Live:** the first buffer is in the file.
- **Synced:** the first buffer is on the drive.

What it shows:

- **The drive dominates.** Three syncs come before live: the manifest, its folder, and the working file's folder. Each costs about 4 ms on this Mac. The append itself takes about 0.05 ms. Creating the working file before the manifest lets the manifest's folder sync cover both names, since both live in `Recording/`, and saves one sync. The manifest still comes before the first sample.
- **Cold costs more in the simulators.** The first `AVAudioFile` of a process loads Core Audio's components: about 5 ms on the Mac and 20 to 25 ms in the simulators.
- **fMP4 was 1.5 to 10 ms slower** to live than CAF, cold and warm, on the Mac and the iOS Simulator.
- **These are the file's share only.** On a real input the engine must start, and the first tap buffer arrives only after its 100 ms of audio. So "live" should mean that the manifest and the file exist and the input runs, not that a buffer has arrived. A kill before the first buffer then loses less than 100 ms. The latency on a real microphone is measured at the owner's sittings.

## Does the draft `Recorder` port fit?

The draft, in docs/architecture.md §5: "Start and stop a recording. Publish levels. Recover orphaned recordings." It fits on none of the three counts.

### Streaming

The real API pushes. From OS 27, `AVAudioNode.installAudioTap(onBus:bufferSize:format:tapProvider:)` throws, and its provider is `@Sendable` and receives an `AVReadOnlyAudioPCMBuffer`, a `Sendable` buffer also new in OS 27, with its `AVAudioTime`. The tap delivers a buffer every 100 to 400 ms on a queue of the engine's, and cannot be paused or slowed.

- **More than levels.** The draft publishes levels and nothing else. The live path also needs the audio, for on-screen text (§8), and the capture engine needs to know how far the audio is durable, for the "saved" cue and its durable revision (§5, §6 rule 7). The port streams all three.
- **Nothing pushes back on the tap.** The writer stays synchronous inside it: `AVAudioFile` hands each linear PCM write to the kernel before it returns, and the kill tests show it. The transcriber gets its audio through a stream that drops the oldest when it falls behind, so a slow transcriber costs on-screen text, never audio.
- **The audio's type.** The tap's `AVReadOnlyAudioPCMBuffer` can cross to the transcriber without a copy, as SP-1's note also says, and `AVAudioFile.write(from:)` takes it from OS 27. `AVAudioPCMBuffer(copying:)` makes the `AVAudioPCMBuffer` that SpeechAnalyzer's `AnalyzerInput` takes. Carrying it in the port means KnotCore imports AVFAudio, which all four platforms have. If WP-02 keeps KnotCore free of it, WP-13's `AudioChunk` works too, at one copy a buffer: 192 KB a second at 48 kHz. This note recommends the read-only buffer. WP-02 settles it, since WP-13's note proposes the chunk.
- **The sync leaves the tap's queue.** `F_FULLFSYNC` acts on the file, not on a descriptor, so a sync on its own serial queue pushes whatever the writer has handed over, and the writer never waits for it. The durable count is what had been appended when the sync began.

### A recording that ends by itself

The draft has the caller stop the recording. The system stops it too:

- **Interruptions.** OS 27 deprecates `AVAudioSession.interruptionNotification`. Its replacements are `didBecomeInactiveNotification`, whose `DeactivationContext` says whether the system deactivated the session and, for an interruption, why, and `resumptionRecommendationNotification`. Warnings are errors, so the recorder must use the new ones. They arrive as main-actor messages and do not exist on macOS.
- **Route changes.** When the input hardware changes its rate or channel count, as AirPods connecting do, the engine stops itself and posts `AVAudioEngineConfigurationChange` on an internal queue. The recorder restarts the input into the file's rate, or ends the recording.
- **Failures and the cap.** A write can fail, for example on a full disk, and the 30-minute cap ends a recording too.

So a session reports an ending it did not request, with its reason, and `stop` must be safe after it.

### Cancellation

The real API has nothing to map Swift's cancellation onto. `AVAudioEngine.start()` is synchronous and takes no cancellation, a tap runs until it is removed, `AVAudioFile` can only be closed, and `AVAssetWriter.cancelWriting()` deletes the file it wrote. A recording is therefore not tied to the task that awaits it:

- **`start`** runs to live or to a typed error. A stop asked for while it starts takes effect once it is live, which a hold released early on the Mac needs. A press while starting is ignored by the engine, as the product spec says, not cancelled.
- **`stop`** always finishes. Cancelling the task that awaits it leaves the stop running, because a half-closed file is what recovery is for, not what a stop should leave.
- **A stream's consumer** that goes away ends delivery to it, never the recording.

### Errors

What the real API does, measured or read in the pinned SDK, and what the recorder does about it:

| Condition | What the API does | The recorder |
|---|---|---|
| The volume fills during a recording | `AVAudioFile.write` throws OSStatus -40 (`kAudioFilePositionError`), not `ENOSPC` | Stops on any failed write and keeps the file. It asks the volume for its free space to choose between "disk full" and "write failed". |
| The same, for the file's length | The file held 832 frames (52 ms) fewer than `append` had accepted | Takes a recording's length from reading the file, never from counting appends |
| The same, with `AVAssetWriter` | `appendImmediately` returns false with no error, and the file held 5.1 s less than was appended | Another reason to leave fMP4 |
| Any `AVAudioFile` failure | OSStatus codes under the domain `com.apple.coreaudio.avfaudio`, not `NSOSStatusErrorDomain`, with the failed call's name in `userInfo` | Keeps the code, drops the text |
| No input available | The SDK says the engine then throws "when possible, or an exception". An Objective-C exception ends the process. | Checks the input node's format for a zero rate or channel count before starting: "no input device" |
| Permission | `AVAudioApplication.recordPermission` and `requestRecordPermission`, on iOS, macOS and watchOS | Checks before it touches the engine: "microphone permission refused" |
| A call holds the audio | Activating a record session fails with `AVAudioSessionErrorCodeInsufficientPriority` | "Audio session busy" |
| A read past the end | Throws `kAudioFileEndOfFileError` from OS 27 | Recovery reads to the length the file announces, never beyond |
| A file cut short | 0 frames, or unreadable when cut inside the format chunk | Recovery keeps the capture as a recording with no audio |

## For WP-02: the port

The proposed port. Names are suggestions; the comments carry the semantics. `KnotError` stands for WP-02's error type, and `CaptureID` and `LaunchID` for KnotCore's IDs.

```swift
/// Records audio into a working file and says what is on disk.
public protocol Recorder: Sendable {
    /// Gets ready without opening the microphone, so that a start soon after is fast: the
    /// Mac's key-down (§15). Calling it often is harmless.
    func prepare() async

    /// Writes the manifest and the working file, starts the input, and returns: the moment
    /// of the "live" cue. Before it returns nothing implies a recording. Not cancellable:
    /// a start runs to live or to a typed error, and only the session ends the recording.
    func start(_ request: RecordingRequest) async throws(KnotError) -> any RecordingSession

    /// Finishes the recordings of earlier launches. Each orphaned working file is read to
    /// its last complete frame. A recording of the current launch is never touched.
    func recoverOrphans(currentLaunch: LaunchID) async throws(KnotError) -> [RecordedAudio]
}

public struct RecordingRequest: Sendable {
    public var captureID: CaptureID
    public var launchID: LaunchID
    public var limit: Duration          // 30 minutes in v1
}

public protocol RecordingSession: AnyObject, Sendable {
    var captureID: CaptureID { get }

    /// What happens to the recording, in order. Ends with exactly one `.ended`, whether the
    /// recording was stopped or stopped by itself. One consumer: the capture engine.
    var events: AsyncStream<RecordingEvent> { get }

    /// The audio the file receives, for on-screen text. When the consumer falls behind,
    /// the oldest buffers are dropped; the file never waits for it.
    var liveAudio: AsyncStream<AVReadOnlyAudioPCMBuffer> { get }

    /// Ends the recording: writes what is left, syncs, closes the file, and returns once it
    /// is on the drive, so that the "saved" cue can follow. Returns the same result when
    /// called again or after the recording ended by itself. Cancelling the awaiting task
    /// does not cancel the stop. Never throws: a failure is the result's `ending`.
    func stop() async -> RecordedAudio

    /// Ends the recording and removes its file and manifest: the accidental press of
    /// product spec §4.2.
    func discard() async
}

public enum RecordingEvent: Sendable {
    case level(peak: Float, average: Float)  // one per tap buffer, every 100 to 400 ms
    case durable(frames: Int64)              // after each sync: survives a power cut
    case ended(RecordedAudio)
}

public struct RecordedAudio: Sendable {
    public let captureID: CaptureID
    public let frames: Int64            // read from the file, not counted from appends
    public let sampleRate: Double
    public let ending: RecordingEnding
}

public enum RecordingEnding: Sendable, Equatable {
    case stopped                        // stop(), or the control that started it
    case limitReached                   // 30 minutes
    case interrupted                    // a call, Siri or an alarm took the audio session
    case inputLost                      // the input went away and could not be restarted
    case diskFull                       // a write failed and the volume has no room
    case writeFailed                    // any other failed write; the file is kept
    case recovered                      // finished by recoverOrphans after a crash
}
```

- **`start`'s errors** are the taxonomy's cases: microphone permission refused, no input device, audio session busy, too little space, write failed. Each leaves no file, or a manifest that recovery ends as a recording with no audio.
- **The injected source** is not in the port. The live recorder in KnotAudio takes its input as a dependency, the microphone in the app and an injected clip under test, where the microphone refuses to open. The contract suite builds the real recorder on injected audio through KnotAudio, not through the port.
- **The heartbeat** of §8 is the recorder's own write into `RecordingStateStore`, once a second. The `.durable` event lets the engine publish its durable revision from the same sync.
- **The fake** scripts: a start that fails with each case; a session that streams levels, durable counts and live audio; each ending, including endings it did not request; a stop during a start; a stop after an ending; a discard; and recovery of an orphan from an earlier launch next to a recording of the current one.

## Changes this asks of the architecture

docs/architecture.md is the orchestrator's file, so this note does not edit it.

1. **§8, the format.** "WP-12 picks the format (candidates: Core Audio Format, or fragmented MPEG-4)" becomes: the working file is Core Audio Format holding 16-bit linear PCM, mono, written through `AVAudioFile`, with a data chunk of unknown size until it is closed.
2. **§8, the sample rate.** The working file keeps the input's rate at the start, for its whole length. A route change that changes the rate goes through a converter into it, or ends the recording.
3. **§8, the stored copy.** "AAC mono in `.m4a`, about 0.5 MB per minute" holds from 22.05 kHz. Below that the encoder takes at most 48 kbit/s, about 0.36 MB a minute.
4. **§5, the `Recorder` row** becomes the port above: a start that returns a session once live, a session that streams levels, durable progress and live audio and ends with a reason, a stop that cannot fail or be cancelled, a discard, and recovery that skips the current launch. `prepare` covers the key-down of §15.
5. **§5, the error taxonomy.** A capture stopped because the disk filled cannot be recognised from the error `AVAudioFile` throws (-40). The recorder decides it from the volume's free space after a failed write.
6. **§8, the live path.** "The live path feeds the same buffers to the transcriber" stands, with the buffers as `AVReadOnlyAudioPCMBuffer`. If WP-02 keeps AVFAudio out of KnotCore, it becomes WP-13's change: "the same audio, copied into `Sendable` chunks".
7. **§6 rule 7 and §8, the sync each second,** runs on a queue of its own, off the tap's.
8. **§17, the kill test in the iOS Simulator.** `Process` does not exist on iOS, so a package test cannot kill a process there. The Mac drives it, as "How it was measured" shows. Whether the gate runs it, and how it builds the simulator's crash host, is the orchestrator's choice; this proof ran it by hand.
9. **§20, platform facts.** New rows, read in the 27.2 SDK unless marked:
   - `AVAssetWriter` and `AVAssetReader` are unavailable on watchOS, and AudioToolbox is not in the watchOS SDK. `AVAudioFile`, `AVAudioConverter` and `AVAudioEngine` are there.
   - From OS 27 the tap API is `installAudioTap(onBus:bufferSize:format:tapProvider:)`, which throws and hands a `@Sendable` provider an `AVReadOnlyAudioPCMBuffer`. The old `installTap` is deprecated. `AVAudioFile` is `Sendable` from OS 26.
   - From OS 27 `AVAudioSession.interruptionNotification` is deprecated in favour of `didBecomeInactiveNotification` and `resumptionRecommendationNotification`.
   - From OS 27 reading past the end of an `AVAudioFile` throws.
   - In OS 27 `AVAssetWriter.addInput`, `startWriting` and `expectsMediaDataInRealTime` are deprecated in favour of `inputReceiver(for:)`, `start()` and `appendImmediately`, which exist from OS 26.
   - Measured on macOS 27.3: `AVAudioFile` writes a CAF data chunk of size -1 and reads such a file to its end; it reports OSStatus codes under `com.apple.coreaudio.avfaudio`; a full volume makes its write throw -40; AAC mono takes 64 kbit/s only from 22.05 kHz.
   - Measured on macOS 27.3: `AVAssetWriter` with movie fragments writes about the first three seconds of audio before its `moov` box, so a file killed earlier is unreadable, whatever the fragment interval.

## The second pull request

WP-12's PR 2, on the branch `wp/12-recorder-2`, adds everything the brief lists after PR 1. Every number below comes from the build Mac, on injected synthetic audio. No microphone was opened, and nothing played aloud.

### Interruptions and route changes

- **An interruption** (a call, Siri or an alarm taking the session) ends the recording as `interrupted`, with everything written kept. From OS 27 an interruption is a deactivation by the system: `AVAudioSession.DidBecomeInactiveMessage` with `.systemInterruption`, observed with `NotificationCenter.addObserver(of:for:using:)`. The interruption notification and its keys are deprecated.
- **A reset of the media services** ends it as `input_lost`.
- **A route change alone changes nothing.** When it changes the hardware, as AirPods that connect do, the engine changes its configuration and stops itself. The input then puts its tap back in the new format and starts the engine again, on a queue of its own.
- **A new rate goes through an `AVAudioConverter`** into the working file's rate, so the file keeps one rate for its whole length. The converter holds back 8 to 262 frames as it works, measured for six pairs of rates from 16 to 96 kHz, the most 16 ms, at 48 kHz into 16 kHz. Before its tap goes, at a restart and at a stop, it is drained with `endOfStream`, so every frame the tap took reaches the file, to within one frame of the converter's own rounding.
- **A change that comes while the start runs**, as headphones that connect at the press, is noted and carried out once the start has ended. The watchers start before the tap goes in, so that no change goes unseen.
- **An engine that cannot start again** ends the recording as `input_lost`.
- **A stop asked for during the restart** waits for it, as it waits for a start.

All of this is shown on a stand-in engine and session. What a device does is checked at the owner's sitting.

### The full disk

The audio file's error does not say that the disk is full: a full volume fails a write with -40. So the recorder asks `FreeSpaceProbe` after a failed write or sync.

- **Below 1 MB free**, the ending is `disk_full`; otherwise it is `write_failed`.
- **A start with less room than a minute of audio** at the input's rate is refused with `too_little_space`, and nothing is written.
- **`SystemFreeSpaceProbe`** reads `volumeAvailableCapacityForImportantUsageKey`, or `volumeAvailableCapacityKey` on watchOS, where the first is unavailable. It reads the nearest folder that exists.

The named test `disk-fills-during-recording` shows it on a working file whose volume fills.

### The peaks

A recording's level peaks go beside it at `StoreLocations.recordingPeaks`, in the format of `RecordingPeaks`. There is one value for each 50 ms of the file's frames, and the last stretch's part is included.

- **They are made from what the working file accepted.** The audio of the live cue's gap is never in them.
- **The file is appended at each sync and at the end**, on the session's queue, without a sync of its own. A delivery never waits for it.
- **A peaks file that cannot be written is given up**, with one log line that holds its capture ID and no value.
- **They go first when the files are removed.**

Where they go when a capture ends is the engine's, ingest's and recovery's, as ruled: they read the file and hand its values to the store before they remove the working file.

### The cues

The recorder gives `recordingLive`, `couldNotStart` and `stoppedEarly`, as the port says, through `environment.cues`.

- **A shell's emitter must be in the environment before the audio module is wired.**
- **The emitter runs on a queue of the recorder's own**, never on the audio's thread, and nothing waits for it.
- **The live cue's gap** is the setting `liveCueGap`, zero by default and held to at most half a second. The audio that arrives while the live cue plays goes nowhere. It stays zero in the composition until the order of "live" against the gap is settled with what the owner finds of the cue in the file at M2: a gap above zero would drop audio while the state and the cue already say live.
- **An ending that begins inside the start** gives no live cue and no "recording": the live cue is given under the lock the ending takes as it begins, and the published phases only go forward.

What the SDK says of a cue while recording (AVAudioSession.h):

- On iOS 13 and later and watchOS 6 and later, a session that takes input holds back haptics and system sounds unless `setAllowHapticsAndSystemSoundsDuringRecording(true)` allows them. The default is not to.
- It is unavailable on macOS, where there is no audio session.
- Without it, the live cue's haptic is never felt, so the microphone's session allows them before it becomes active.
- Other system sounds can then play during a recording, and one played aloud can reach the file.

Whether each cue is felt and heard on each device, and what reaches the recording, is a row for the owner's sitting.

### The recording state and the heartbeat

`DefaultsRecordingStateStore` keeps the state as one JSON value under one key, `knot.recording-state`, in the `UserDefaults` the composition hands to `KnotAudioLive.wire`. With none it names no suite and never uses `.standard`.

- **`UserDefaults` is not `Sendable`**, so the store keeps the instance it is given behind a lock, and the caller keeps no use of it. Every instance of the suite, in this process or another, sees what one writes.
- **The recorder publishes as the phase changes:** starting, recording from the moment it is live, stopping, then idle however the recording ends.
- **It writes a heartbeat every second** from a queue of its own.
- **Recovery clears** a state that an earlier launch left, or that names no launch. It never clears one of the current launch.

The state across two processes:

- **On the Mac**, the crash host writes and the test reads, and the other way round.
- **In the iOS and watchOS simulators**, `KnotAudioCrashHost state-check --runner "xcrun simctl spawn <udid>" --child <the simulator's crash host>` writes the state in one child and reads it in another. It printed `state-check ok` in both.

The named test `press-while-saved-recording-state-is-stale` kills a crash host while it records and publishes. It then applies `RecordingPressRule` to the stale state and carries the decision out with the recorder's ports, in both orders.

### The player

`LiveAudioPlayer` plays, pauses and seeks through an `AVAudioEngine` and a player node.

- **From OS 27, a connection and a play throw:** `connectNode(_:to:format:)` and `playAudio()`.
- **The end is `dataPlayedBack` on a device.** Offline, where no device plays, it is `dataRendered`, which the SDK names as the one that applies there.
- **In a process whose hardware input `HardwareInputPolicy` refuses**, a test's, a simulator's or an agent's, the engine renders offline, so nothing plays aloud. A test moves the audio on, and the player passes the `AudioPlayer` contract. In a simulator a play reports playing at its position and stays there, never moving and never ending, until a pause or a seek: nothing renders it.
- **The recording wins**, as the orchestrator ruled. A recording that starts stops a player that plays, which reports that it paused where it stood. A play while this process records is refused and changes nothing, with one log line, `player_refused_while_recording`, that carries the asset the file's name gives. No error reaches the caller, so a shell offers no play while it records.
- **On iOS and watchOS, a play sets the session to playback**, which a recording can then take back.

## The third pull request

### The recorder's kill points

`Tests/KnotSoak/RecorderKillPoints.swift` gives the capture ledger soak the recorder's points, over the recordings that the soak's child makes on the live recorder with injected audio, one capture in five:

- `log:recording_live`: a start live, its manifest in place, its working file made and its name synced, its input started, before the start returns to the engine;
- `step:during_recording`: each time more of a recording is durable;
- `log:recording_stopped`: a stop's file closed, synced and read back and its manifest marked ended, before the stop returns;
- `log:recording_converted`: a copy in place, before the engine stores it;
- anywhere, after an acknowledgement.

At its three log events the child holds the recorder's own thread until it is killed. The child knows those three names since this pull request (`KillPointNames.logEvents`). The named test `soak-kill-points-recorder` runs the soak on them: 40 captures from a fixed seed in the package tests, and 200 from the tier's seed under `scripts/verify.sh --soak`, where each point must kill at least once.

Each point is armed at a pass that a launch reaches, and a launch runs 8 to 40 captures:

- A recording passes each log event once.
- It passes `during_recording` once when its audio runs past the first sync, and not at all when the first sync makes the whole of it durable. The soak's audio comes ten times faster than real time and is synced every 100 ms, so a pass needs more than ten buffers. That is one recording in two, or about one capture in nine.
- So `during_recording` is armed at its first pass, the log events at their first or second, and `anywhere` within the acknowledgements of the shortest launch.
- Armed at a pass up to ten, `during_recording` once went six launches without a kill, on seed 7301.

**What the soak proves.** It proves what survives a process's death, and a death keeps every byte written. So a stop that left out its last sync would pass it. The stop's last sync is held by three tests of KnotAudioTests: `aStopSyncsTheClosedFileBeforeItReturns`, `aFailedFinalSyncIsTheEnding` and `aStopWhoseLastSyncFailsStoppedEarly`.

### The start's writes and the injected audio, off the pool

- **The start's durable writes** run on a serial queue of the recorder's own, `knot.audio.start`, at user-initiated priority. They are the free-space probe, the folder's creation, the manifest's placement, the working file's making and the folder's sync, and the removal of what a failed start wrote. Before, they ran in the start's task on the cooperative pool, where a full sync held one of the pool's threads at every start: one of two on a watch. The queue is not the one for conversions and recovery, so no start waits behind a conversion. Their order is the same.
- **A stated limit: the start's queue is serial.** A write that hangs holds every start after it, where before each start had a thread of its own. This costs nothing here, because Knot makes one recording at a time, and a press while a recording is starting is ignored: no second start waits behind the first.
- **The injected input** delivers its buffers from a queue of its own, `knot.audio.injected`, as the hardware's tap delivers from the audio's thread. The recorder writes and measures each buffer in the delivery, so an injected recording now does that where a real one does, and not on the pool. A stop returns once no delivery is under way, and none follows it.

### The peaks file, made in place

The peaks file was made with `FileManager.createFile`, an atomic write through a temporary beside it, `<capture>.peaks.sb-<8 hex>-<6 characters>`. A kill between the temporary and its rename left the temporary in `Recording/` for good, as the soak saw once. The file is now opened in place, with `O_CREAT | O_TRUNC`, and the header and then the values are written to it. What a kill leaves, in each case:

- **Before the header is whole:** a file of fewer than 12 bytes, whose reader answers no peaks. Before, the same moment left no peaks file and a temporary beside it.
- **Between two values:** every value is one byte, so a file cut anywhere after its header holds whole values only. The reader takes them all. At most it holds fewer values than the durable frames cover: the values made since the last sync, which the next sync would have appended.
- **A file already at the name, written again:** the recorder never does this in its own flows. A recording makes its peaks file once, and a removal takes the peaks first. Only a file left by some other cause would be written again, and its values were then not this recording's. If one is, the first append empties it and writes the header, so a kill there leaves fewer values than the file held a moment before: none, or a header with fewer values. Before, the old file stayed whole until the rename replaced it.

The soak's switch for peaks temporaries (`SoakRules.peaksTemporariesAreRed`) is now true: a temporary left in `Recording/` turns the soak red.
