# WP-18 proof: PKStrokeRecognizer and the `InkRecogniser` port

The proof step of WP-18, 2026-11-19, on the build Mac: an M4 Max, macOS 27.3 (26C5047e), Xcode 27.2 (27B52), and this worktree's iPhone 17 Pro simulator on the iOS 27.2 runtime. Its code is on the branch `wp/18-proof`, at `c6c5d78`, where the rest of WP-18 starts if it is built. This note has two readers: WP-02, which writes the `InkRecogniser` port from it, and the orchestrator, which keeps docs/architecture.md.

Only the three synthetic drawings of `Fixtures/ink` were recognised.

## In short

The draft port of docs/architecture.md §5, "Turn drawing data into text", fits the API in outline: one drawing goes in, one text comes out, and nothing streams. Three things have to be added:

1. **`nil` means too many things.** No call of `PKStrokeRecognizer` throws. `recognizedText()` returns `nil` when the drawing holds no words, and also when the system refuses the request, when the language is not supported, and, on the Mac, when the calling task is already cancelled. The port must tell these apart, because "no words" makes a segment ready with empty text, and a refusal must never do that.
2. **Recognition runs only in an app in the foreground.** The recognition service refuses a process that is not an app, and on iOS an app in the background, even one holding background time. So a recognise job is deferred while the app is in the background, and the real contract suite cannot run in the package tests. It runs hosted in an app, in the iOS Simulator.
3. **The result carries the engine's version.** `PKStrokeRecognizer.recognitionVersion` (9 today) is meant to be stored beside the text, like the transcription's engine, locale and OS build.

Accuracy and speed are good enough to build on. `line` is recognised word for word. `list` loses two of its three words, because its lines nearly touch (see [Results](#results-on-the-fixtures)). `sketch` gives no words, as it should. A warm recognition of a drawing with words takes 35 to 60 ms on the Mac and in the Simulator.

## What the API does

`PKStrokeRecognizer` is an actor, new in iOS 27 and macOS 27, with the same declaration on both. Its whole surface is `init(preferredLanguages:)`, `updateDrawing(_:) async`, `recognizedText(strokeIDs:) async -> String?`, `indexableContent: String? { get async }`, `search(_:fullWordsOnly:caseMatchingOnly:)`, `languages`, and the static `supportedLanguages` and `recognitionVersion`.

**Streaming**

- There is no stream and no partial result. `updateDrawing` returns at once, and the first `recognizedText()` after it already holds the final answer. Six runs on the same drawing, each with a new recogniser, gave the same text.
- Updating the drawing after each stroke and asking again gives text that grows: "C", "CO", "cal", "call", … "call the vet at noon". On the `line` fixture each update took 27 ms (Mac) to 40 ms (Simulator) at the median and 64 ms at most. Knot recognises when the capture ends (product spec §4.3), so the port needs none of this, but it is there if live text is ever wanted.
- A query that is running when the drawing is replaced answers for the drawing it began with. The actor orders the calls, and nothing breaks.
- Three recognisers running at once finished all three in about 100 ms (Mac) and 125 ms (Simulator).

**Cancellation**

- Cancelling the task during a query does nothing. The call runs to the end, 27 to 62 ms after the cancel, and returns the full text.
- A call made from a task that is already cancelled behaves differently by platform. On the Mac it returns `nil` within 0.1 ms. In the iOS Simulator it recognises the drawing in full.
- So the implementation checks `Task.isCancelled` itself, and a `nil` from a cancelled task is a cancellation, never "no words".

**Failures**

Nothing throws except decoding. What each condition returns:

| Condition | What the API does |
|---|---|
| A drawing with words, in an app in the foreground | The text |
| A drawing with no words: the sketch, one dot | `nil` |
| An empty drawing, or one never given | `nil` |
| An empty set of stroke IDs, or an unknown ID | `nil` |
| A preferred language that is not supported (`tlh`) | `languages` is `[]`, and every query returns `nil` |
| A process that is not an app: `swift test`, or `xctest` under xcodebuild, on the Mac and in the Simulator | `nil`. The system log says `com.apple.corehandwriting` Code -1003, "The application does not have permission to run remote recognition or synthesis at this time". |
| An iOS app in the background, holding background time | The first call, made just as the app left the foreground, recognised. Calls one and two seconds later returned `nil`, with the same -1003 for the app's own bundle ID in the log. |
| Data that is not a drawing, or a drawing's data cut short | `PKDrawing(data:)` throws `NSCocoaErrorDomain` code 3 |

The -1003 reaches only the system log. The caller sees a plain `nil`.

**Other facts**

- `indexableContent` returns every candidate, one per line ("- milk\n-milk\nregal\n"). It runs at low priority, and its documentation says an interactive query can cancel it, though in the probe both answered. Knot stores `recognizedText()` and does not need it.
- `search(_:)` cannot be used under Swift 6 strict concurrency: its `[SearchResult]` is not `Sendable`, so it cannot leave the actor. Knot searches its own index, so this costs nothing.
- `supportedLanguages` lists 33 languages on the Mac and 20 in the Simulator, which lacks Arabic, Russian, Ukrainian, Hindi and Marathi in Devanagari, Thai, Vietnamese, Chinese, Cantonese, Japanese and Korean. `en-US` is in both.
- The drawing reads with y pointing down on both platforms, which is how the fixtures are written. Flipped, `line` reads "call fyonof af Noon".
- The recogniser expects writing at paper scale. `line` at 0.25 to 20 times its size reads correctly, and at 0.05 times it reads "call thevetotnoon".
- A drawing that went through `dataRepresentation()` and `PKDrawing(data:)` gives the same text.

## Results on the fixtures

The fixtures were loaded from `Fixtures/ink/<name>.json` after their SHA-256 was checked against `Fixtures/manifest.json`. Each stroke became a `PKStroke` with a black pen, its points taken as the file gives them. The same text came back in all four app hosts, apart from the space after a dash:

| Fixture | Expected | Recognised | Words right |
|---|---|---|---|
| `line` | call the vet at noon | "call the vet at noon" | 5 of 5 |
| `list` | - milk, - eggs, - bread | "- milk regal" (Simulator), "-milk regal" (Mac) | 1 of 3 |
| `sketch` | no words | `nil` | correct: no made-up text |

That is 6 of 8 words. **`list` is a spacing problem, not a reading problem.** The descenders of "eggs" end at y = 129 and the ascender of "bread" starts at y = 132. Recognised by stroke ID, each line reads correctly on its own: "- milk", "-eggs", "_bread". With the third line moved 15 points down, the result is "- milk\n-eggs _bread". With it moved 30 points down, "- milk\n-eggs\n_bread", all three words. The dash comes back as "-", "_", or with no space after it, so a list marker cannot be trusted to survive. WP-04 owns the fixture. Whether it keeps its tight lines as a hard case is the orchestrator's call, and WP-18's fixture test must state which result it expects.

Latency, in milliseconds, for `updateDrawing` and `recognizedText()` together, each run with a new recogniser, as a job would. "First" is the first run in the process:

| Host | `line` first / warm median / warm max | `list` | `sketch` |
|---|---|---|---|
| iOS Simulator, app | 145 / 47 / 48 | 57 / 62 / 63 | 12 / 12 / 12 |
| iOS Simulator, tests hosted in the app | 107 / 45 / 46 | 57 / 57 / 64 | 12 / 11 / 11 |
| Mac, app | 467 / 35 / 35 | 47 / 47 / 47 | 11 / 7 / 7 |
| Mac, tests hosted in the app | 63 / 38 / 38 | 55 / 52 / 56 | 10 / 6 / 7 |

The service starts cold once per boot. The first recognition after the Simulator booted took 3,060 ms, and the first on the Mac in this session took 832 ms. A recognise job's first run can be that slow. The 500 ms target of product spec §14 is for ink on disk, not for recognition, and `scripts/verify.sh --perf` measures it. The Simulator's times are the Mac's CPU, not an iPad's.

## Where recognition runs

| Host | Mac | iOS Simulator 27.2 |
|---|---|---|
| `swift test` (no bundle ID) | `PKDrawing(strokes:)` traps, 3 runs of 3 | not used |
| Package tests under xcodebuild (`xctest`) | every query `nil`, 79 refusals in the log | every query `nil`, 82 refusals |
| A bare executable (`KnotInkCrashHost`) | `PKDrawing(data:)` and `dataRepresentation()` work, `PKDrawing(strokes:)` traps, 3 runs of 3 | not used |
| An app | recognises, even launched in the background (`open -g`) and never active | recognises in the foreground; refused about a second after it goes to the background |
| Tests hosted in an app | recognises, with the app not active | recognises |
| A device | not tried | not tried |

The trap: `PKDrawing(strokes:)` reaches `PKReplicaManager`, which saves state to preferences keyed by the bundle ID. With no bundle ID, `CFEqual` gets `NULL` and the process stops with SIGTRAP. One run early in the session passed. Every later run trapped. Under xcodebuild, `xctest` has a bundle ID, so building drawings works there, and only recognition is refused.

**So the `InkRecogniser` contract suite needs the iOS Simulator.** More exactly, it needs an app host. Neither `swift test` nor the package tests under xcodebuild can recognise anything, on the Mac or in the Simulator. Tests hosted in an app work on both platforms. The iOS Simulator is the place to run them: `Knot-iOS-Tests` already exists, hosted in the app, "for what runs only in the iOS Simulator". iOS is also where ink is recognised in v1, since the Mac only views ink, and iOS is the platform that enforces the foreground rule. The fake's half of the suite runs in the package tests on the Mac, as every other suite does.

## For WP-02: the port

**1. One call, no stream.** The port takes drawing data and returns the text, once. Drawing data is the bytes of `PKDrawing.dataRepresentation()`, opaque to KnotCore, which cannot name a PencilKit type because KnotCore builds for watchOS.

**2. The result.** Text, empty when the drawing holds no words, with its provenance: the engine's `recognitionVersion`, the language it used, and the OS build. Apple's documentation for `recognitionVersion` says to store it beside the results and to recognise again on an OS with a higher version.

**3. Availability.** As for the other engines, the port reports whether it can run for a language: available, or unsupported language, from `supportedLanguages`. An unsupported language is final. The ink stays ink with no text, and the user can still read the drawing.

**4. Failures**, each a case of the taxonomy, in the classes WP-13's note uses:

- **Deferrals**, never counted: the app is not in the foreground, and the call was cancelled. The job runs again when the app comes forward (§4).
- **Attempts**, counted: recognition failed, when the app was in the foreground and still got nothing it can trust (below).
- **Final**: the drawing's data is unreadable, which no retry fixes. The segment shows it failed, and the file is kept.
- **Not failures**: a drawing with no words is ready with empty text.

**5. How the real implementation reads a `nil`.** WP-18 builds this, and the contract suite checks it:

1. Decode the data. A throw is "drawing unreadable".
2. If the language is not in `supportedLanguages`, or `languages` comes back empty, report the unsupported language.
3. On iOS, if the app is in the background, defer, before calling and again after a `nil`.
4. If the task is cancelled, defer, before calling and again after a `nil`. A text that comes back from a cancelled call is still good, and it is kept.
5. After a `nil` in the foreground, recognise a small known drawing, a word built into KnotInk, with a new recogniser. If it reads, the drawing truly holds no words: return empty text. If it does not, the request was refused: defer when the app has left the foreground, and otherwise count a failed attempt. This costs one extra call of about 40 ms, and only when the answer was `nil`.

The proposed port, for WP-02 to settle:

```swift
/// The bytes of a PencilKit drawing, as the canvas saved them. KnotCore never reads them.
public struct InkDrawingData: Sendable, Hashable {
    public let bytes: Data
}

public protocol InkRecogniser: Sendable {
    /// Whether this engine can read handwriting in `language` on this device.
    func availability(for language: Locale.Language) async -> InkRecogniserAvailability
    /// Recognises one finished drawing. Empty text means the drawing holds no words.
    /// Throws a deferral when the app is not in the foreground or the task is cancelled.
    func recognise(_ drawing: InkDrawingData, language: Locale.Language) async throws(KnotError) -> InkRecognition
}

public enum InkRecogniserAvailability: Sendable, Equatable {
    case available, unsupportedLanguage
}

public struct InkRecognition: Sendable, Equatable {
    public let text: String                       // "" when no words were found
    public let provenance: RecognitionProvenance
}

public struct RecognitionProvenance: Sendable, Equatable {
    public let engineVersion: Int                 // PKStrokeRecognizer.recognitionVersion
    public let language: String                   // BCP 47, the language the engine used
    public let osBuild: String
}
```

The scripted recogniser that WP-02 ships has to script: a text; empty text; each failure case; a deferral for the background and one for a cancellation; and an unsupported language. The contract suite runs those against the fake on the Mac, and against the real recogniser hosted in the app in the iOS Simulator. To reach the background case there, the real recogniser takes the app's foreground state through an injected function, which the suite can set to "background". A hosted test cannot send its own app to the background.

## For WP-18's first pull request

- Package tests in KnotInkTests must not call `PKDrawing(strokes:)`, because `swift test`, which `scripts/verify.sh --quick` runs, traps on it. Building drawings from the fixtures, and recognising them, belong in the hosted tests.
- `KnotInkCrashHost` is a bare executable, so it can decode and write drawing data but cannot build a drawing from strokes. The kill test gives it data made elsewhere: in the hosted tests, or by the test that starts it under xcodebuild.
- `PKStrokePath(bezierPath:creationDate:pointProvider:)`, new in OS 27, could build the fixtures' strokes from their Bézier paths directly. The proof used the sampled points.

## Changes this asks of the architecture

1. **§5, the `InkRecogniser` row.** "Turn drawing data into text" becomes: report availability for a language, and recognise one finished drawing into text and its provenance, with no stream. The port is above.
2. **§5, the error taxonomy.** One new final case, "drawing unreadable", beside "audio unreadable". One new deferral, "app not in the foreground", beside "no background time". "Recognition failed" stays, as an attempt. A drawing with no words is not an error.
3. **§5, where the suites run.** The `InkRecogniser` row of the table loses its "if": the real recogniser's suite runs hosted in the app in the iOS Simulator, and the fake's in the package tests on the Mac.
4. **§4, the domain model.** `Segment` gains `recognition: (engineVersion, language, osBuild)?` for ink, as voice has `transcription`. Whether a higher `recognitionVersion` triggers a new recognition is for the orchestrator. A recognised text that the user has edited must never be replaced, and §10 says that no device recognises a stored drawing again.
5. **§10, ink.** Add: recognition runs only while the app is in the foreground. The queue never runs a recognise job from background time or a background task, and a job deferred there runs when the app comes forward. A finished drawing is recognised as its capture ends, while the app is in front, so the usual case is unaffected.
6. **§17, testing.** The row "Speech, cleanup, ink: Fixtures, with accuracy reported, on a Mac with the models installed" changes for ink: ink fixtures are recognised in tests hosted in the app in the iOS Simulator, not in `swift test`.
7. **§20, platform facts.** Add these rows, each from a probe on this Mac on 2026-11-19:
   - `PKStrokeRecognizer` works inside an app in the iOS 27.2 simulator, unlike `SpeechTranscriber`.
   - It refuses a process that is not an app (Code -1003 in the log), and an iOS app about a second after it leaves the foreground, even with background time. It returns `nil` and does not throw.
   - A Mac app is served even when it is not active.
   - `PKDrawing(strokes:)` traps in a process with no bundle ID. `PKDrawing(data:)` does not.
   - Task cancellation does not stop a query. A call from a cancelled task returns `nil` on the Mac and recognises in full on iOS.
   - `PKStrokeRecognizer.search(_:)` returns a type that is not `Sendable`.
   - `supportedLanguages` has 33 entries on the Mac and 20 in the iOS 27.2 simulator.
   - `recognitionVersion` is 9 on macOS 27.3 and in the iOS 27.2 simulator.

## Declarations read

From the pinned Xcode 27.2 SDK, `PencilKit.swiftmodule/arm64e-apple-macos.swiftinterface` and its `.swiftdoc`. The `PKStrokeRecognizer` declaration in `arm64e-apple-ios.swiftinterface` is the same line for line.

- `PKStrokeRecognizer` (iOS 27, macOS 27): `init(preferredLanguages:)`, `drawing`, `updateDrawing(_:)`, `languages`, `indexableContent`, `recognizedText(strokeIDs:)`, `search(_:fullWordsOnly:caseMatchingOnly:)`, `SearchResult`, `supportedLanguages`, `recognitionVersion`, with the doc comments of `updateDrawing` (paper scale), `indexableContent` (low priority, can return `nil`), `recognitionVersion` (store it, recognise again on a higher one) and `init(preferredLanguages:)` (best effort).
- `PKDrawing`: `init(strokes:)`, `init(data:)`, `dataRepresentation()`, `strokes`, `transform(using:)`, `requiredContentVersion`.

- `PKStrokePath`: `init(controlPoints:creationDate:)`. `init(bezierPath:creationDate:pointProvider:)` (OS 27), not used.
- `PKStrokePoint`: `init(location:timeOffset:size:opacity:force:azimuth:altitude:)`.
- `PKInk`: `init(_:color:)`, `InkType.pen`.

## Not verified yet

- **A device.** Speed and accuracy on the iPad mini, with real Pencil strokes. The M5 checklist has the rows, among them M5.1-09 for the sketch.
- **The background on a device.** The Simulator granted unlimited background time, and recognition was refused anyway. A device may differ in the details, for example in how long the grace after leaving the foreground lasts.
- **The inactive state.** An app that has not yet become active was served in the Simulator. An app made inactive by Control Center or an incoming call was not tried.
- **The iPhone Duo.** Nobody on the project owns one (WP-18's failure rules).
- **Languages other than English**, and the cost of the built-in check word in step 5 on a device.
