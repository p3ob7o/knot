## Build

- The thinnest real `CaptureEngine` and `ProcessingQueue`.
- One end-to-end test. In it a typed capture and a recording go through the engine, the queue, the in-memory `NoteStore` and the scripted `Recorder`, `Transcriber` and `Cleaner`, and the assertions read the stream page that `NoteStore` publishes. The test makes its own recording, in the format the fixture clips use, and reads no file from `Fixtures/generated/`. The scripted transcriber returns the committed text `Fixtures/audio/canary.txt` for it, so the canary word goes through the engine, the queue and the store.
- On the store path WP-05 writes the capture row as the first durable write of a capture. A recording writes its manifest first, and a capture that falls back to `Inbox/` stays on the file path until it ends: its row is made once, by whichever arrives first. The capture ledger is rule 6 of `docs/architecture.md` §6.
- The engine passes only the placement the user asked for. The store's record-a-capture transaction decides where a capture goes.
- The engine records a capture through the one `NoteStore` operation that the `knot` command and the MCP server also use, so the append rule runs in one place.
- Saving a checkpoint of an open capture is its own store operation, ordered by revision, and it never lowers stored text.
- The `BackgroundRunner` that runs work straight through, for the foreground and the Mac. Each drain of the queue takes a runner and a progress sink (docs/architecture.md §5).
- `CaptureEngine` and `ProcessingQueue` are not faked. `CaptureEngine` publishes the revision of the content that is durably saved.
- Ingest and recovery are not on the `CaptureEngine` protocol. The composition calls KnotCapture's own types for them, in the order of docs/architecture.md §13: open the store, recover recordings, ingest the inbox, finish the open captures of earlier launches, resume jobs, start sync if it is on. Recovering recordings reads their orphaned files (`Recorder.recoverOrphans`), and it comes before ingest. Ingest reconciles `Inbox/` through `NoteStore`'s one ingest operation. Then the open rows of earlier launches end: a typed capture at the last durable save the store wrote on its row, and a recording at the end of the audio its file holds. Ingest comes before the open captures are finished, because the two orders give different results (docs/architecture.md §5).
- A capture that the store path does not take goes to `Inbox/`, whether the store was too slow or answered with an error, and its state carries the code (docs/architecture.md §5). When the write to `Inbox/` fails too, the capture has reached no disk. The port does not say how the engine reports it. WP-05 builds it to product spec §4.4: the surface stays open with the text in it and says that it could not save.
- The store writes a stored recording's transcribe job itself, so `ProcessingQueue.enqueue` only wakes the queue. The clean job is the queue's to write: when the transcription's last run is saved, and at launch for a transcribed recording that lacks one. Writing it twice must change nothing.
- `.preview` asks `ScriptedTranscriber` for its default script. A plain one answers `audio_unreadable` for a file that nobody scripted, so that a test which forgot to script a file fails.
- The preview environment in `Packages/KnotKit/Sources/KnotFakes/Preview/`. `.preview` runs the real engine and queue over the fakes on iOS and macOS.
- WP-01 writes the environment factory so that a debug build asks KnotFakes for the preview environment, which answers `.unavailable` until WP-05 fills it in. WP-05 therefore edits only its own folders.
- UI tests select `.preview` with a launch argument that only debug builds honour.
- Every contract correction WP-05 finds goes in a contract PR.

## Failure rules

- The engine never waits for the store. A capture that begins while the store is not open, is migrating or has not answered within 100 ms goes to `Inbox/` in the manifest format and is ingested later. A recording writes its manifest first.
- A capture belongs to the process launch that began it, and recovery finishes only the captures of earlier launches.
- A capture has one life across the store and `Inbox/`. One that falls back stays on the file path until it ends, and its manifest records the placement that was asked for and the note the surface showed. The store call it stopped waiting for may still commit. The row is made once, by whichever arrives first, every later save is a checkpoint by revision, and ingest places the capture where the manifest says.
- WP-05 also gets a second opinion from a different model. Every finding the orchestrator sets aside is written in the PR and in the journal.
- The code in `Packages/KnotKit/Sources/KnotFakes/Preview/` compiles only in a debug build, or in a build that sets `KNOT_FAKES` (docs/architecture.md §3). A release app must hold none of it.

## Named tests

- `capture-before-open-migration-or-write-lock-tracer`: A capture begun before the store is open, during a migration and while another process holds the write lock.
- `store-call-commits-after-inbox-fallback-tracer`: A store call that commits after its capture fell back to `Inbox/`.
- `tracer-end-to-end-typed-and-recording`: One end-to-end test, in which a typed capture and a recording go through the engine, the queue, the in-memory `NoteStore` and the scripted `Recorder`, `Transcriber` and `Cleaner`, and the assertions read the stream page that `NoteStore` publishes.
