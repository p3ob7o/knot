## Build

### All four PRs

- The manifest format and the placing of files are not the engine's own. `CaptureManifest` in KnotCore is the one versioned format for an inbox item, and `DurableFile` in KnotCore is the only code that places a file.
- Every log line about a capture carries its capture ID.
- A later PR keeps every rule that WP-11 PR 1 builds.

### PR 1

- The `CaptureEngine` actor. For typed captures: begin, update and end. The capture surface's model in KnotUI sends the saves, at most 150 ms behind the last keystroke, and the model and the app shell flush on end, background and termination.
- Voice captures, run through the `Recorder` port.
- `begin` of an ink capture goes on throwing `port_unavailable`, as the tracer left it. Drawings come with WP-11 PR 4.
- A typed capture has one pump, the capture surface's model in KnotUI, and KnotCapture has no session tracker. The model holds the intent, "New note" or an open note, and passes it as the request's placement. The append rule has one owner, the store's record-a-capture transaction, and the engine passes only the placement the user asked for. The owner confirmed the ruling on 2026-11-21.
- Late arrivals are placed by the store, not by WP-11.
- What the capture surface shows. docs/product-spec.md §4.1 fixes it: the note a capture would join, following the window, with the destination fixed at the first keystroke. WP-11 and WP-21 implement it. The note shown comes from a store query that calls the same rule as the store's decision.
- The engine passes the store the note the surface showed with the placement asked for, as a manifest records them. The store places the capture in that note whenever the note can still take it, so the store path and the `Inbox/` path agree (docs/architecture.md §5).
- One capture is open at a time on a device, as rule 15 of docs/product-spec.md §3 says. A capture started on another surface ends the open one, whatever its kind.
- Empty captures discarded. Text that is only spaces and line breaks is empty.
- The capture row. The capture ledger is rule 6 of docs/architecture.md §6. On the store path the engine writes the capture row as the first durable write of a capture. A recording writes its manifest first, and a capture that falls back to `Inbox/` stays on the file path until it ends. The engine that WP-11 extends keeps to that rule.
- The engine publishes the revision of the content that is durably saved, for typed and voice captures. Durability follows rule 7 of docs/architecture.md §6.
- Saves. Saving a checkpoint of an open capture is its own store operation, ordered by revision, and it never lowers stored text. After the capture row is made, every later save is a checkpoint by revision.
- A recording ends through the `Recorder` port: `convert` makes and verifies the `.m4a`, the engine moves it into the `AssetStore` and ends the capture with the asset, and `removeWorkingFile` removes the working file once the capture's row points to the asset (docs/architecture.md §8). No call to the store carries a job: the store writes a stored recording's transcribe job itself.
- The engine never waits for the store. A capture that begins while the store is not open, is migrating or has not answered within 100 ms goes to `Inbox/` in the manifest format and is ingested later. A recording writes its manifest first.
- A capture has one life across the store and `Inbox/`. One that falls back stays on the file path until it ends, and its manifest records the placement that was asked for and the note the surface showed. The store call it stopped waiting for may still commit. The row is made once, by whichever arrives first, and ingest places the capture where the manifest says.
- A capture belongs to the process launch that began it, and recovery finishes only the captures of earlier launches.
- Long text. Text past the size limit continues in further segments of the same capture, in the same note, and nothing is cut. The first segment shares the capture's ID, and each later one has an ID derived from the capture's ID and its position, so a repeat returns the same segments and the ledger counts the capture once. WP-02 and WP-11 carry it.
- No call of the engine waits for one capture's line while it holds another's, and a start reaches disk before it waits for anything.
- The first two findings of WP-11 come from the review of pull request 40, the tracer, which set them aside under PLAN.md §8.4 for this package, because WP-11 owns the engine from that merge. Finding 52: after a start fails with nothing on disk, its retry and a start on another surface each hold a line and wait for the other's. Finding 53: with no failure at all, two starts on two surfaces that wait behind an end wait for each other once the end returns. Pull request 40 left a test of each in `Packages/KnotKit/Tests/KnotCaptureTests/Engine/RecheckSequenceTests.swift`, marked as a known issue.
- Finding 54 comes from the review of pull request 50. When the open capture ends by its own call during the recorder's start, the recording's manifest still names it while the recording's `Inbox/` item names nothing, so after a death the recording joins a note it would not join alive. The link is decided once, as the start arrives, with no wait, and never changes, so that a recording's manifest and its item always name the same capture, and the recording lands in the same note alive and after a death. Its witness is in the engine's tests as a known issue once pull request 50 has merged.

## Failure rules

- When the store is unavailable, captures go to `Inbox/` and the stream says what is wrong.
- WP-11 PR 1: a typed capture whose save fails follows rule 6 of docs/architecture.md §6. WP-11 PR 4: so does an ink capture whose save fails.
- A late draft save must not replace newer text.
- Crash recovery covers all three kinds, and a recovered capture ends at its last durable write. WP-11 PR 1 covers typed drafts and recordings: a typed draft found at relaunch becomes a finished segment. WP-11 PR 4 covers drawings: a drawing found at relaunch goes on to recognition. WP-22's launch sequence has the step that finishes the open captures of earlier launches.
- At launch the composition ingests `Inbox/` before recovery ends the open rows of earlier launches, through `NoteStore`'s one ingest operation. The engine does neither itself (docs/architecture.md §5).
- Recovery never ends a capture of the current launch.
- A soak failure is never retried to green. It prints its seed, its kill point and where the store was kept.

## Named tests

- `soak-kill-points-capture-engine`: WP-11 PR 3 adds one file of kill points to the soak, and the soak is among its merge criteria.
- `late-draft-save-must-not-replace-newer-text`: A late draft save that must not replace newer text.
- `capture-before-open-migration-or-write-lock-engine`: A capture begun before the store is open, during a migration and while another process holds the write lock.
- `disk-fills-during-draft-save`: A disk that fills during a draft save.
- `store-call-commits-after-inbox-fallback-engine`: A store call that commits after its capture fell back to `Inbox/`.
- `text-past-size-limit-repeated-engine`: Text that runs past the size limit, repeated.
- `engine-random-interleavings`: A seeded test of random interleavings of starts, updates, ends and discards on three surfaces, over a store whose calls are held and released at random, in which every call returns within a limit and every acknowledged text is found; one outcome, a discarded recording kept with its audio when its end's store call commits late after a full disk, is a stated limit.
