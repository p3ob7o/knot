## Build

The command-line and MCP contract is fixed in docs/product-spec.md §10. This brief says what WP-34 builds and tests. For the behaviour of each command and each rule, read §10.

### All three PRs

- The commands in docs/product-spec.md §10, with `--json`. The MCP server. The install step from the Mac app.
- One command table generates the help, the usage errors, the MCP tool list, `docs/cli.md` and the golden tests, so they cannot drift apart.
- Writes go through `NoteStore`. A new capture goes through the same record-a-capture operation as the engine, so the append rule runs in one place. A segment written this way is marked as coming from the command line or from MCP.
- Errors use one mechanism, as docs/architecture.md §19 states. WP-34 renders the command line's text, `--json` and the MCP results from the one value of WP-02's error taxonomy.
- The access switch. Command-line access is off by default, until it is turned on in Settings on that Mac. While it is off the `knot` tool refuses commands, and the MCP server keeps answering and fails each tool call with the reason. WP-33 and WP-34 build that switch.
- Each note says whether it is settled, and each segment carries its state in the six names of docs/product-spec.md §5. KnotAgent takes the mapping to those six names and the settled rule from KnotCore.
- Deletes made through the tool are soft, and nothing purges.
- Tool results mark note text as data, not as instructions.
- WP-34 bounds piped text and an MCP frame, as docs/architecture.md §4 states.
- Only the app migrates. The tool exits with code 7 on an older store.
- The tool posts a notification after writing. The notice is a hint: the app also compares the store's change counter with the one it last showed.
- A development build installs the tool as `knot-dev`, and `knot status` prints the flavour and the store it opened.
- `docs/cli.md` holds a three-command quick start, every command with an example and its `--json` output generated from the golden files, the exit-code and error tables with anchors, and a registration line for each client.

### PR 1

### PR 2

- The other commands of docs/product-spec.md §10 apart from `knot mcp`: `append`, `changes`, `show`, `search`, `edit`, `title`, `move`, `delete`, `restore` and `export`.
- The command line follows the additions to docs/product-spec.md §10: an unsettled note carries the time at which it will settle, a deletion stays reportable after the purge, a foreign cursor is refused, and a segment whose capture is open cannot be edited or deleted.
- A revision that leaves the store carries the store's generation. A write that names a revision from before a restore is refused as a conflict, like a foreign cursor.
- The move names what the caller saw. `knot move <segment> --from <note>` moves the segment only if it is still in that note, and otherwise changes nothing and says where it is, so a repeat is safe even after a later capture has joined the new note. `knot move <segment> --back` returns it. A return is refused when the segment's note has changed since the move, or when the note it left is deleted or gone, and it works on the Mac where the move was made, because `segment_history` is local.
- `knot restore` keeps its two meanings and gains none: it undoes a delete, or brings back replaced text on a segment that is not deleted.
- `knot changes` reports both notes after a move, and reports a note left empty as deleted.
- Export never downloads. It first asks KnotExport what an export would leave out, and refuses and writes nothing when attachments are on another device, and `--skip-missing` exports the rest with a list. The tool cannot reach KnotInk, so it passes KnotExport no drawing images, and KnotExport writes each drawing's stored data file under its ID and names it in the list (docs/architecture.md §3). A sandboxed tool probably cannot write to a folder given as an argument, so SP-3 decides how `knot export` delivers its output.
- `knot export` names the reason each file was left out: not on this device, unreadable, or of a kind this build does not know. It reads what the export reports after it has written, as well as the preview before, and a file that went missing in between makes the result incomplete, exit 8. It passes KnotExport the machine's time zone for the day in a file name.
- The orchestrator's reading, which the owner can overturn: a file of a kind this build does not know counts as missing, so `knot export` refuses without `--skip-missing`, though docs/product-spec.md §10 names only files still on another device.
- The XPC route to the running app is built only if SP-3 fails in wave 1, never later. If it is, WP-34 builds it, and the tool does what SP-3's report says when Knot is not running, which docs/product-spec.md §10 then follows.
- From PR 2 on, the real store is wired into the `knot` executable, and the golden tests run on the in-memory `NoteStore` and on the real one.

### PR 3

- Embedding the tool in the Mac app, by the route SP-3 chose. WP-01's first PR already embeds and signs a trivial `knot` there as a packaging proof.
- `knot mcp` runs the MCP server on standard input and output. It is tools only, written by hand, with conformance tests.
- The MCP server speaks the 2026-07-28 revision, and the handshake of the 2025-11-25 and 2025-06-18 revisions, because clients of both kinds are in use. WP-34 reads the specification before writing it.
- Nothing but protocol messages goes to standard output, and the server exits at end of input.
- The server offers the same operations as the commands, as tools, except export. Tool names carry a noun. The capture tool requires a placement of "window" or "new note", and its result says which. Results are bounded and carry a next cursor. No tool exports.
- The command table generates each MCP tool from the same row as its command, the move included.
- `knot mcp` reads the access switch and the schema version again on every call, inside the transaction, and refuses when access is off or the store is newer than the build. While access is off it keeps answering and fails each call with the reason, because a client restarts a server that exits.
- The install step. The Settings row for command-line access shows the two lines to paste, each with the tool's absolute path: one puts `knot` on the PATH, and one registers the MCP server. The target is 2 minutes from the switch to a note read by an agent.

## Failure rules

- The access switch is consent, not a wall: any program running as the user can reach the file itself, and the privacy text says so.
- The command line opens at M4. In a milestone build made at a lower level, a gate switches it off.
- Agents use `knot-dev` and never `knot`, and their threads export `KNOT_AGENT=1`. With it set, the milestone `knot` refuses to run, so an agent cannot open the owner's notes by accident.
- The Mac development store sits in the development container, in a folder named for the worktree.
- The tool never migrates, and `knot mcp` refuses a store newer than the build.
- No error ever contains note text, and logs never hold note text, transcripts or audio.
- The current MCP revision, 2026-07-28, has no `initialize` handshake, and requires `server/discover` and a `resultType` on every result. That was read in the specification's changelog on 2026-11-19, and WP-34 reads it again before writing.
