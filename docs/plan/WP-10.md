## Build

### PR 1

- Everything in docs/architecture.md §7, apart from what WP-10 PR 2 holds: the pool and its settings, schema version 1 and the migrator, repositories implementing `NoteStore` and `AssetStore`, the FTS5 index and search, the trigger-fed change log, soft delete and purge, the pre-migration copy.
- The ports. WP-10 implements `NoteStore` with the capture rows and the one-transaction capture operation, `AssetStore`, `SettingsStore` and the local-only `AssetFetcher`. Each implementation passes the contract suite of its port. KnotStore exposes one live entry point, which returns the unavailable port until this package fills it in.
- The capture ledger. It is rule 6 of docs/architecture.md §6, backed by a `capture` table whose rows `NoteStore` carries. WP-02 defines the `Capture` type and WP-10 stores it. A capture row records the placement that was asked for.
- Recording a capture. `NoteStore` records a capture in one transaction, applying the append rule and writing the capture row and the segment. The append rule has one owner: this transaction decides, and the engine passes only the placement the user asked for. The note a capture surface shows comes from a store query that calls the same rule. The `knot` command and the MCP server write through the same `NoteStore` operation as the engine, so the append rule runs in one place.
- Late arrivals are placed by the store, by the rules of docs/product-spec.md §3, and not by WP-11 or WP-15.
- A capture has one life across the store and `Inbox/`. The row is made once, by whichever arrives first: the store call or the ingest of the fallback file. Every later save is a checkpoint by revision, and ingest places the capture where its manifest says.
- Checkpoints and repeats. Saving a checkpoint of an open capture is its own store operation, ordered by revision, and it never lowers stored text. Recording a capture is idempotent by capture ID: a repeated capture ID with the same content returns the first result, and with different content it fails as a conflict. Replacing text checks the precedence of edited, cleaned and raw inside the store. WP-02 and WP-10 carry all three with contract tests.
- The content hash of a capture is keyed with a secret of the store and stays out of the diagnostics export.
- What the command-line contract asks of the store, from schema version 1: a store ID and a change counter, with a `revision` on each note; a `revision` on each segment; and a local `segment_history` table that keeps replaced text for 30 days. A stale revision fails. Changes after a cursor include a late capture and a deletion, and a cursor ahead of the store is reported.
- The store's generation. A restored store gets a new generation. A revision that leaves the store carries the store's generation, and a write that names a revision from before a restore is refused as a conflict, like a foreign cursor.
- The move. The store carries the move of a segment to its own note as one operation and its inverse, as docs/architecture.md §4 and §5 state. WP-02 puts both in the `NoteStore` contract and in the in-memory fake, and WP-10 implements them.
  - The new note has a fresh ID, and its other fields come from the segment. Both notes take new counter values, and each note's latest-capture time is recomputed, in one transaction.
  - The move names what the caller saw. It moves the segment only if it is still in that note, and otherwise changes nothing and says where it is, so a repeat is safe even after a later capture has joined the new note.
  - `noteGeneration` on `Segment` rises each time the segment's note changes, by a move, a return or the deleted-note rule.
  - `segment_history` keeps the note a segment left for 30 days. It is local, so a return works on the device where the move was made. A return is refused when the segment's note has changed since the move, or when the note it left is deleted or gone. The app's undo is the same return.
  - Titles do not move with a segment. When a segment leaves a note, the note's generated title is checked again against the words still in the note and dropped if it no longer fits, and a typed title is never touched. The new note has no title. A return puts a dropped title back if the note still has none. The check is one function in KnotCore, which KnotCleanup and the store both call.
  - A conflict copy moves with the segment it copies.
- Deletes are soft. Deleting a note marks the note and not its segments. A note left empty is hidden and is never marked deleted for that reason. A purge leaves a tombstone, so a deletion stays reportable after the purge.
- Search. Search text never reaches the full-text index as raw query syntax.
- Performance rules. A stream page is one query, and every query in the `NoteStore` contract has an index. Reads use the reader connections. Bulk writers commit in small batches.
- Durability, as rule 7 of docs/architecture.md §6 states. WP-10 turns `fullfsync` on and reports what a commit costs. `DurableFile` syncs a file and its folder before the row that points to it is committed.
- Asset files are placed by atomic move and verified by SHA-256. `DurableFile` in KnotCore is the only code that places a file. A path on disk comes from an ID. Asset folders are named by the last two characters of the ID, since the first ones of a time-ordered ID stay the same for years.
- Locations. On iOS and iPadOS the database lives in the app's own container, and only `Inbox/` and the recording state use the app group, as docs/architecture.md §7 states. WP-10 implements both locations. `StoreLocations` in KnotCore is the only code that computes a store path, with no default in any library target, and it roots everything v1 writes in a folder named `KnotStore/`. Tests pass the store path in.
- iOS file protection as specified.
- Change streams for the UI.
- The change feed. Listing the notes changed after a counter value reports both notes after a move, and it reports a note left empty as deleted, without marking it deleted in the store (docs/architecture.md §11).
- The store's tests end with the same consistency check as the soak and the diagnostics export, as docs/architecture.md §17 states: capture, segment and job rows agree, no capture ID is stored twice, and the foreign keys and the search index are clean.
- `change_log` holds one row per record and none for drafts.
- Settings. v1 keeps its settings in a named defaults suite and never reads `UserDefaults.standard`. The lint of WP-01's gate fails on that symbol.
- Migrations. Only the app migrates. The copy before a migration is made with `VACUUM INTO` or the backup interface, checked, and required. The newest pre-migration copy is kept until the following migration.
- Schema version 1 is the schema of the M2 milestone build. Every change after that build is a numbered migration, whichever package makes it. WP-01's lint fails on GRDB's `eraseDatabaseOnSchemaChange`.
- Copies. A daily copy is kept seven times. A restored copy brings back text. A recording or drawing purged after the copy was made shows as missing, and the restore says how many there are. Captures waiting in `Inbox/` are ingested afterwards as usual.
- Rolling back never discards work. Restoring a pre-migration copy stops the app and the tool, and moves the current store folder aside whole and keeps it.
- Backups. The store and its files are never excluded from device backups or Time Machine.
- Legacy data, as docs/architecture.md §7 states it. Milestone builds reuse `com.p3ob7o.knot`, so on a device that had the retired app v1 shares its container. The retired app owns `Application Support/Knot/` there. v1 refuses a database it did not create.
- The keep-gate counts. WP-10 keeps a local table of daily counters that hold no content: captures by kind, captures and jobs that failed, uses of "New note", moves and returns. A move counts when it is made, a return counts apart, and a repeat that changes nothing counts as neither. WP-22's exporter reads the table, as docs/architecture.md §7 and §19 state.
- Seeded stores. At each milestone tag a seeded synthetic store made by that build is committed. It holds work in flight: an open capture, a queued job and a pending delete.
- Kill tests use the crash-host executable that WP-01's first PR declares for KnotStore.

### PR 2

- The second-process rules, which wait for SP-3. The `knot` tool never migrates: on an older store it exits with code 7.
- Two processes share the `capture` table on the Mac. As docs/architecture.md §5 states, the rules about open captures on a device are checked in the record-a-capture transaction, against that table.
- The notice between processes is a hint. The app also compares the store's change counter with the one it last showed whenever it comes forward, and once a minute while it runs.
- The sync columns, which wait for SP-4. `sync_record` holds the account, the environment and the zone identity that each record was synced under, as docs/architecture.md §11 states, and a record counts as synced only under that identity.
- The interface for sync. KnotStore gives KnotSync one transactional interface, so KnotSync issues no SQL. The triggers of `change_log` are off while sync applies. A record that a merge makes is queued for upload in the transaction that made it, although the triggers are off on that connection.
- Device identity. WP-10 keeps an install ID in the Keychain for this device only, and a store that arrives through a backup gets a new device ID and a reset sync state.
- Every change after the M2 milestone build is a numbered migration, the second PR of WP-10 included.

## Merge criteria

- `scripts/verify.sh --quick` passes before each PR opens.
- The real store passes the same `NoteStore` contract suite as the fake, and the suites of `AssetStore`, `SettingsStore` and `AssetFetcher`. They run on the Mac, in the package tests.
- The contract suite's cases for the command-line contract pass: a repeated capture ID with the same content changes nothing and returns the first result; a stale revision fails; changes after a cursor include a late capture and a deletion; and a cursor ahead of the store is reported.
- The contract suite's cases for the move pass: a move and its return leave both notes exactly as they were; a repeat answers "not in that note"; a move is refused for an open capture, for a deleted segment and for a conflict copy; a segment alone in its note is refused; a return is refused when the note it left is deleted; a dropped title is put back by a return; and a process killed inside a move leaves the segment in exactly one note.
- A process killed in mid-transaction leaves a consistent database.
- A test shows that the writer connection keeps both settings, `fullfsync` and `synchronous = FULL`.
- The PR reports what a commit costs on the Mac.
- A test shows each query plan. The gate asserts query plans and operation counts. Time thresholds are not merge criteria.
- Search is checked against a plain scan.
- A store folder copied elsewhere opens with every note and file.
- After a restore the newer store is still there.
- A restore of a copy older than a purge passes its test.
- A seeded differential test applies random sequences of operations to the in-memory `NoteStore` and to the real one and compares every result.
- Every later build opens each seeded store, migrates it and passes the whole `NoteStore` contract suite on it.
- The named tests below pass. Storage has failure-path tests.
- A reviewer runs gstack `/review` on each PR, and a different model gives a second opinion through `/codex`.
- The capture ledger soak runs in the merge gate of any PR that touches KnotStore. The step becomes required when WP-06 merges.
- WP-10 PR 2: a second process reads and writes concurrently on macOS.
- After G1 and SP-3, the gate has one development-signed step for a PR that touches KnotStore: the sandboxed app and `knot-dev` share a store, the tool writes and the app shows it.
- Package tests use Swift Testing and UI tests use XCTest, as docs/architecture.md §17 states.

## Failure rules

- A store that cannot be opened is never deleted.
- A database newer than the build is refused untouched.
- v1 refuses a database it did not create.
- The app does not migrate without a checked copy.
- Notes on the owner's iPhone and iPad are disposable until the M2 milestone build, and notes on his Mac until the M4 milestone build. After those builds, every change to the schema or to the store's location ships a tested migration.
- On iOS the system kills a process that is suspended while holding a lock on a database in a shared container. That is why extensions never open the database.
- If the iPad Pencil work is cut, ink stays a kind the store knows, so a later version can add it without a migration.
- A soak failure is never retried to green. It prints its seed, its kill point and where the store was kept.
