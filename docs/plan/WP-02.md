## Build

### PR 1

- PR 1 holds the domain types, rules and reducers.
- The domain types in `docs/architecture.md` §4. They include `Capture`, `closedAt` on `Note`, and `transcription` and `processingOwner` on `Segment`.
- `transcription` records the engine, the locale and the OS build that produced a voice segment's transcript. v1 has no re-transcription.
- `Segment` has a local `arrivedAt` that does not sync.
- Each note has a `revision`, and so has each segment.
- `noteGeneration` on `Segment` syncs, and rises each time the segment's note changes, by a move, a return or the deleted-note rule.
- Ownership of a recording carries a generation. A conflict copy holds text only and has a derived ID. An asset is local only, uploading or published.
- A capture row records the placement that was asked for. A capture belongs to the process launch that began it. The content hash of a capture is keyed with a secret of the store.
- Each cleaned segment records the OS build whose model made it.
- Jobs count attempts, deferrals and deaths apart, as `docs/architecture.md` §4 states.
- Sizes are bounded as `docs/architecture.md` §4 states. A path on disk comes from an ID. Asset folders are named by the last two characters of the ID, since the first ones of a time-ordered ID stay the same for years.
- Every synced enum has an unknown case from PR 1, so a new case does not break a branch.
- The append rule as a pure function, with table-driven tests for every rule in `docs/product-spec.md` §3, late arrivals included. The rule is written as an ordered list of small rules, first match wins, each with its own test table. The tests cover rules 9 to 15, and the table for rule 16 covers a capture made inside the window of a segment that was just moved.
- Three rules of `docs/product-spec.md` §3 and §4.1 are exact, and WP-02 tests each. A capture started on another surface ends the open one, whatever its kind. A gap that is negative by less than the window counts as inside it, and a larger one starts a new note. Text that is only spaces and line breaks is empty.
- A title is generated only when a note's first segment is a recording. A generated title uses only words from the note. The check that a generated title still fits its note is one function in KnotCore, which KnotCleanup and the store both call.
- Segment state machines as pure reducers, with tests for every transition and every illegal one.
- The ink state machine has no transition from ready back to drawing, because a finished drawing is not reopened in v1. The reducer tests reject that transition.
- The recording reducers follow `docs/architecture.md` §8. A stale recording state is judged by a heartbeat: a press that meets a stale state recovers the orphan and starts a new recording. In the app process the recorder decides, not the heartbeat: a press stops a recording that this process is running. The heartbeat serves other processes and recovery.
- The one-second discard is measured between the two presses. Hold-to-record is exempt from it.
- A press never does nothing after a crash, as `docs/product-spec.md` §4.2 states.
- WP-02 and WP-33 encode these rules of `docs/product-spec.md`: rules 9 to 15 of §3; what happens when a capture cannot start or cannot be saved, in §4.4; and the hotkey behaviour of §6. The microphone opens at the 250 ms mark of a hold and never on a tap, and listening from key-down is the alternative if SP-5 measures clipped first words. A release that never arrives leaves a visible stop control, and a key another app already uses is refused in Settings.
- WP-02 turns the assumptions of `docs/product-spec.md` §16 into tests. The owner confirmed 33 of the 34 as written, and they are decisions now. §16 marks each as cheap or costly to change after WP-02, and gives a worked example for each costly one. An assumption that WP-02 cannot test is tested by the package that builds what it speaks of: A6 by WP-32; A9, A21 and A26 by WP-16; A12 by WP-31; A13 and A30 by WP-33; A27 by WP-21, WP-30 and WP-33; A29 by WP-21; and A36 by WP-30. A8, A32 and A33 are tested by the `NoteStore` contract suite of PR 2.
- The settings model, feature gates (`sync`), an error taxonomy and the logging facade.
- A milestone build switches off by a gate each feature whose milestone has not passed: sync and the command line open at M4, and ink at M5. WP-01 builds that mechanism.
- Errors use one mechanism, as `docs/architecture.md` §19 states. Every case of the error taxonomy carries a stable code, the next action, whether a retry is safe and how often, and what was written. Error codes are values and not a closed list of cases. A test fails when a case lacks a code or an entry in `docs/errors.md`.
- The error taxonomy names by case each failure whose behaviour `docs/architecture.md` fixes, as `docs/architecture.md` §5 lists them. It also has the deferral class and three more cases: text too long, a capture stopped because the disk filled, and a cursor from another store generation.
- One home for each rule, all in KnotCore:
  - `CaptureManifest`, the one versioned format for a recording in progress, an inbox item and a watch outbox file. A manifest records the placement that was asked for and the note the surface showed.
  - `StoreLocations`, the only code that computes a store path, with no default in any library target. It roots everything v1 writes in a folder named `KnotStore/`, because the retired app owns `Application Support/Knot/` in the same container. On iOS and iPadOS the database lives in the app's own container, and only `Inbox/` and the recording state use the app group, as `docs/architecture.md` §7 states. The threads of agents export `KNOT_AGENT=1`, and `docs/architecture.md` §7 says what `StoreLocations` refuses when it is set.
  - `DurableFile`, the only code that places a file. It syncs the file and its folder before the row that points to it is committed, and a file-layer test drops unsynced writes. The layer that drops them lives in KnotTestSupport, so that the store's and the recorder's tests can use it too.
  - The mapping from internal states to the six that a person sees: saved on the Watch; saved, text on its way; saved, text being made elsewhere; ready; needs you; kept, no text.
  - The settled rule.
- KnotUI and KnotAgent both use the mapping and the settled rule, and the command line reports the six names.

### PR 2

- PR 2 holds the ports, fakes and suites the tracer needs, which are the stores, the recorder, the transcriber, the cleaner, the clock and the IDs.
- The ports in `docs/architecture.md` §5. No port throws an untyped error.
- `AppEnvironment` in KnotCore. WP-01 PR 1 declares it with its `.unavailable` value, and WP-02 extends it as its ports land.
- KnotFakes holds the fakes and the fixture builders and imports no test framework. Its code compiles only in a debug build, or in a build that sets `KNOT_FAKES`, so a release app links it empty. KnotTestSupport holds the shared contract suites and is used by test targets only. It also holds the lookup of fixtures: a test finds `Fixtures/manifest.json` by walking up from its source file, and a fixture that is missing or changed fails the test with `fixture_missing` or `fixture_changed`, and never skips it, as `Fixtures/README.md` states.
- Across PR 2 and PR 3 the fakes are: an in-memory `NoteStore`; scriptable `Recorder`, `Transcriber`, `Cleaner`, `InkRecogniser`, `WatchLink` and `SyncEngine`; fakes for `AssetStore`, `AudioPlayer`, `AssetFetcher`, `RecordingStateStore`, `RecordingActivity` and `SettingsStore`; a fake clock; builders for notes and segments; and one shared contract test suite per port. `CaptureEngine` and `ProcessingQueue` are not faked. PR 2 holds the ones the tracer needs.
- Package tests use Swift Testing, as `docs/architecture.md` §17 states. Each real implementation runs its contract suite where it can run, as the table in `docs/architecture.md` §5 says.
- Two operations are part of the contracts. `NoteStore` records a capture in one transaction, applying the append rule and writing the capture row and the segment. `CaptureEngine` publishes the revision of the content that is durably saved.
- The `knot` command and the MCP server write through the same `NoteStore` operation as the engine, so the append rule runs in one place.
- The append rule has one owner. The store's record-a-capture transaction decides, the engine passes only the placement the user asked for, and the note a capture surface shows comes from a store query that calls the same rule. WP-02 writes a test that the prediction and the decision agree.
- The capture ledger is rule 6 of `docs/architecture.md` §6, backed by a `capture` table whose rows `NoteStore` carries.
- The record-a-capture operation sets `arrivedAt` on the segment when it places a late arrival, and `NoteStore` has an operation that clears it on a note's segments, which changes neither the change counter nor a revision. WP-02 puts both in the `NoteStore` contract and in the in-memory fake.
- Four parts of the command-line contract reach the store, and WP-02 and WP-10 carry them from schema version 1: a store ID and a change counter, with a `revision` on each note; a `revision` on each segment; capture recording that is idempotent by capture ID; and a local `segment_history` table that keeps replaced text for 30 days.
- The contract suites cover each of the four: a repeated capture ID with the same content changes nothing and returns the first result; a stale revision fails; changes after a cursor include a late capture and a deletion; and a cursor ahead of the store is reported.
- A revision that leaves the store carries the store's generation. A write that names a revision from before a restore is refused as a conflict, like a foreign cursor.
- The command line follows the additions to `docs/product-spec.md` §10: an unsettled note carries the time at which it will settle, a deletion stays reportable after the purge, a foreign cursor is refused, and a segment whose capture is open cannot be edited or deleted. WP-34's golden tests run on the in-memory `NoteStore` as on the real one, so the fake carries these too.
- Checkpoints and repeats. Saving a checkpoint of an open capture is its own store operation, ordered by revision, and it never lowers stored text. A repeated capture ID with the same content returns the first result, and with different content it fails as a conflict. Replacing text checks the precedence of edited, cleaned and raw inside the store. WP-02 and WP-10 carry all three with contract tests.
- Text past the size limit continues in further segments of the same capture. The first shares the capture's ID, and each later one has an ID derived from the capture's ID and its position, so a repeat returns the same segments and the ledger counts the capture once. WP-02 and WP-11 carry it, with a test that repeats a long capture.
- A derived ID is a version 5 UUID, so a note made by the deleted-note rule and a note made by a person's move are told apart by the ID alone.
- The move. The store carries the move of a segment to its own note as one operation and its inverse, as `docs/architecture.md` §4 and §5 state. WP-02 puts both in the `NoteStore` contract and in the in-memory fake.
  - The move names what the caller saw. It moves the segment only if it is still in that note, and otherwise changes nothing and says where it is, so a repeat is safe even after a later capture has joined the new note.
  - The new note has a fresh ID, and its other fields come from the segment. Both notes take new counter values, and each note's latest-capture time is recomputed, in one transaction.
  - Titles do not move with a segment. When a segment leaves a note, the note's generated title is checked again against the words still in the note and dropped if it no longer fits, and a typed title is never touched. The new note has no title. A return puts a dropped title back if the note still has none.
  - The clean job proposes a title only for the note that holds its recording when the job finishes, and only if that recording is the note's first segment and the note has none.
  - A conflict copy moves with the segment it copies.
  - `segment_history` keeps the note a segment left for 30 days.
  - A return is refused when the segment's note has changed since the move, or when the note it left is deleted or gone. The app's undo is the same return.
  - The contract suite covers these cases, and the real store passes them: a move and its return leave both notes exactly as they were; a repeat answers "not in that note"; a move is refused for an open capture, for a deleted segment and for a conflict copy; a segment alone in its note is refused; a return is refused when the note it left is deleted; a dropped title that a return puts back; and a process killed inside a move leaves the segment in exactly one note.
- A note left empty is hidden and is never marked deleted for that reason. Deleting a note marks the note and not its segments.
- The `NoteStore` contract suite must fail three deliberately broken fakes.
- The whole `NoteStore` contract suite also runs on a seeded store. The seeded store committed at each milestone tag holds work in flight: an open capture, a queued job and a pending delete. Every later build opens it, migrates it and passes the whole suite on it.

## Failure rules

- After WP-02 merges, the public API of KnotCore changes only through a contract PR (PLAN.md §8.5). A contract PR that only adds merges in the normal queue. One that breaks keeps the two fixed times.
- Every contract correction that WP-05 finds merges as a contract PR.
- Crash recovery covers all three kinds. A typed draft found at relaunch becomes a finished segment, a drawing found at relaunch goes on to recognition, and a recovered capture ends at its last durable write.
- Late arrivals are placed by the store's record-a-capture transaction, which applies the append rule. WP-11 and WP-15 do not place them.
- The in-memory `NoteStore` is checked against the real one: WP-10 has a seeded differential test that applies random sequences of operations to both and compares every result.
- Each PR also gets a second opinion from a different model. Every finding the orchestrator sets aside is written in the PR and in the journal.
