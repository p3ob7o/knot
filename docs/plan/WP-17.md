## Build

### PR 1

- The watch outbox: `<captureID>.m4a` and `<captureID>.json`. The manifest holds the capture ID, start, end, duration, device and checksum. It is a `CaptureManifest`, the one versioned format in KnotCore for a recording in progress, an inbox item and a watch outbox file.
- The watch keeps the file until the phone acknowledges that capture ID. On the watch the capture ledger is the outbox: every manifest is either still on the watch and visible, or acknowledged by an iPhone.
- The coordinator. The watch's sequence of record, convert and send lives in KnotLink beside the outbox, and the watch app only hosts it. It is tested on the Mac with kill points, and it finishes a conversion that a kill interrupted at the next launch.
- Kill tests use the crash-host executable that WP-01 PR 1 declares for KnotLink.
- The `LinkTransport` protocol, with a fake. Everything in docs/architecture.md §12 sits behind it.
- `WatchLink`: send a capture, receive acknowledgements, publish recent-capture state. The Watch's recent recordings show a time, a length and a delivery state, and nothing about a transcript.
- WP-32 composes the watch app, and hosts the coordinator in it.

### PR 2

- Send. `WCSession.transferFile`, with the manifest as metadata.
- Receive. The phone's delegate must move the received file before it returns, because the system deletes the file afterwards. It moves the file into `Inbox/` with `DurableFile` and checks it against its manifest.
- Acknowledge. The phone acknowledges with `transferUserInfo` once the file is durably in `Inbox/` and matches its manifest, without waiting for ingest, so a phone whose store will not open cannot fill the watch.
- Checksums. The watch link acknowledges only a file that matches its checksum. On a mismatch the watch sends the file again. On the third mismatch the phone ingests what it received as a failed capture and keeps it, and it still does not acknowledge. The watch keeps its own copy, shows it as not delivered, and tries again when the session next activates. An intact delivery later replaces the damaged copy and makes the capture stored.
- Retry. The watch sends unacknowledged captures again when the session activates, when reachability changes, when either app comes forward, after each new capture, and on its background refresh. A transfer that shows no progress for a set time is cancelled and queued again. Duplicates are harmless, because ingest is idempotent.
- The back channel. The phone sends the watch no note text and nothing about a transcript, because the watch is a capture device only. The watch learns that a recording arrived from the acknowledgement. `updateApplicationContext` carries only what the watch needs to say whether a recording continues a note or starts a new one: the end of the capture that a new recording would join, if there is one, and the window. The phone works that out by the rules of docs/product-spec.md §3, so a note closed by "New note" and a deleted note give none. WP-17 gives the payload no field that can hold note text.
- A capture started from the Watch follows the window. What the watch shows is a forecast. The phone decides at ingest, by the recording's own timestamps.
- The phone side. KnotLink exposes one live entry point, which returns the unavailable port until WP-17 fills it in, so that WP-17 wires itself in without editing `Packages/KnotKit/Sources/KnotApp/`.

## Failure rules

- File transfer does not work in the Simulator. The logic is tested against the fake transport, and delivery on hardware.
- `WCSession.transferFile` can stall with no error until Bluetooth is toggled. That is reported, not confirmed, and SP-2 measures it.
- A file whose checksum does not match is not acknowledged, and on the third mismatch it is ingested as failed and kept.
- Durably in `Inbox/` means synced to the drive. An acknowledgement to the watch is given only after that sync, as rule 7 of docs/architecture.md §6 states.
- A file's place on disk comes from its ID, never from a name inside a manifest.
- The Watch shows no note content: no stream, no text of a recording and no preview of one. Nothing KnotLink carries to the watch holds note text or anything about a transcript.
- Every log line about a capture carries its capture ID, which is the same on the watch and the phone. Logs never hold note text, transcripts or audio.
- Read the SDK before using an OS 26 or OS 27 API. Any such API used is named in the PR with the declaration that was read (docs/architecture.md §21).
