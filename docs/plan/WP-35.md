## Goal

On an iPad, the Pencil starts a note as readily as the keyboard.

## Owns

- `Apps/iOS/iPad/`
- `Apps/iOS/Ink/`, the canvas screens shared by the iPad and a Pencil-capable iPhone

The plan names no separate folder for this package's UI tests, so they sit in the paths above.

## Build

- The side-by-side layout. The stream and the open note sit side by side. At launch the open column is the capture surface.
- When two columns do not fit, as in portrait on an iPad mini or in a narrow window, the iPad uses the iPhone layout. UI tests cover a narrow width.
- Knot has one window on the iPad in v1 (assumption A36).
- Pencil on the capture surface starting an ink segment. On that surface the Pencil always draws. WP-35 checks in the 27 SDK how the system's handwriting input is turned off there before relying on it.
- A drawing does not end on one stray key press or touch. UI tests cover a key press during a drawing.
- The canvas screens in `Apps/iOS/Ink/`, on WP-18's canvas wrapper, recognition and Pencil-capability check. The Sketch control of WP-31 PR 2 and the OpenSketch intent of WP-19 PR 4 open the canvas.
- Keyboard shortcuts and the menu bar, as docs/product-spec.md §6 lists them: ⌘N new note, ⌘F search, ⌘↩ end capture.
- The iPad inherits "Move to its own note" from the iPhone's note view. The move, and every other segment action, can be reached from the keyboard on the iPad.
- The Pencil-capable iPhone path.
- The cells of the state matrix in docs/design/brief.md §6 that this package implements are those of the iPad column marked "Yes":
  - Capture, empty
  - Capture, adding to an open note; the window running out
  - Recording, typing and Pencil not accepted
  - Ink in progress; ending a drawing
  - Stream, populated
  - Stream, largest text size
  - Note, mixed segments
  - Ink segment: shown, being recognised, failed, nothing recognised
  - Two columns do not fit; keyboard up
- The iPad cells marked "iPhone" inherit the iPhone's design, and a dash means the state does not apply on that surface. The iPad has had the iPhone's layout, which WP-30 builds, since M1.

## Failure rules

- Nobody on the project owns an iPhone Duo. The Pencil-capable iPhone path ships untested on hardware. It sits behind the capability check and is stated as untested.
- The cut order names the iPad Pencil first: WP-35, the rest of WP-18, the Sketch control and intent, and M5. Scope leaves only on the owner's word, at the keep-gate sitting or at a later milestone sitting. No agent cuts scope. A part that is cut is not started.
- If this package is cut, the iPad keeps the iPhone's layout, which it has had since M1, and has no canvas, no side-by-side layout, no hardware-keyboard shortcuts and no menu bar. Ink stays a kind the store knows, so a later version can add it without a migration.
- If M5 is cut, every condition that names M5 names M4: the deployment of the CloudKit production schema, which then also needs a recording made on one device to play on the other, and the start of WP-43.
