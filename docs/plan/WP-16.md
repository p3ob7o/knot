## Build

- Everything in docs/architecture.md §11, as amended by SP-4. WP-16 implements the rules that §11 fixes: the sync default, who processes a recording, when a segment syncs, the precedence of machine text, titles, deletes, appends to a deleted note, and which settings sync.
- SP-4's report also answers how a replica that stayed away for more than 30 days is handled, a segment that arrives before its note, a kill between applying a batch and saving the engine's state, a store restored from an older copy, a record at the size limit, a change of account with uploads pending, what a restored or replaced phone does to device identity, and whether a segment record's note reference can change after the record is saved.
- The structure. The rules of §11 live in a merge core that has no CloudKit in it and works on Knot's own record values. A thin adapter turns CKSyncEngine's events into those values and back. The engine's events cannot be built in a test, so the replica simulation and every named sync test run on the core.
- The adapter has two layers, as docs/architecture.md §11 states from docs/notes/SP-4.md. The delegate does nothing but one `switch` over the event, which unpacks each payload. The layer below it builds the batches, chooses the fetch scope and translates the events, takes only types a test can make, and has tests of its own.
- The store's interface. KnotStore gives KnotSync one transactional interface, the six operations of docs/architecture.md §3, which docs/notes/SP-4.md drew from the SDK: apply a fetched batch idempotently, holding its deletions of notes, save the engine's state on its own, read the pending records for the current send, record a sent batch, settle at the end of a fetch, and keep apart a record over the size limit. KnotSync issues no SQL.
- The pause before a large delete counts the deletions of the whole fetch, which the store holds until the fetch settles, and not those of one batch (docs/architecture.md §3 and §11).
- `change_log` stays the source of pending changes in every case. At each launch the adapter adds every row to the engine again (docs/architecture.md §7).
- Sending. The adapter builds each batch itself: only records inside the send's scope, at most 250 of them, and at most a byte budget of field data, 1.5 MB to start with, with one record always allowed alone. It splits a batch refused with `limitExceeded` itself, and never sends a record over the record limit. The limits were read in the SDK and not measured (docs/architecture.md §11 and §20, docs/notes/SP-4.md).
- Fetching. The delegate keeps the Attachments zone out of every fetch through the scope it returns from `nextFetchChangesOptions`, which by the SDK's headers, read and not yet run against a server, the engine asks for before each server request. A segment whose note has not arrived is settled only at `didFetchChanges`, and only when every zone's fetch completed without an error (docs/architecture.md §11, docs/notes/SP-4.md).
- Stopping. A stop cancels the engine's operations, raises the run's generation and releases the engine, and the store drops every input from an older generation, because by the SDK's headers an operation in flight may finish after the cancel returns (docs/architecture.md §5 and §20).
- While sync applies fetched changes, the triggers that feed `change_log` are off on its connection. A record that a merge makes is still queued for upload in the transaction that made it: a conflict copy, a derived note, or a note reference or an owner that the merge settled. Only a record applied exactly as fetched leaves nothing pending.
- A first restore from iCloud writes many rows, and bulk writers commit in small batches.
- The ports. WP-16 implements `SyncEngine` and the syncing `AssetFetcher`. KnotSync exposes one live entry point, which returns the unavailable port until WP-16 fills it in, so that WP-16 wires itself in without editing `Packages/KnotKit/Sources/KnotApp/`.
- What stays on the device. `arrivedAt` on `Segment` is local and does not sync. Nor do a segment's `revision`, the capture rows, `segment_history` or the daily counters.
- What syncs when. A segment syncs once its capture has ended. Drafts and recordings in progress never sync.
- Who processes a recording. `processingOwner` on the segment says which device runs its jobs, and ownership of a recording carries a generation. A device writes the text it made only if it still holds the current generation. Two devices that take a recording at the same generation are told apart by device ID: the higher one owns it, every device applies that rule when the records merge, and the other drops its result.
- Machine text. A write by the processing queue never creates a conflict copy and never overwrites text whose origin is `edited`. Precedence is edited, then cleaned, then raw transcript. Replacing text checks that precedence inside the store, so sync carries no check of its own.
- Conflicts. New segments never conflict. When a text field changed on both sides since the last sync, the server value stays in place and the local value is inserted as a new segment with `conflictOf` set. A conflict copy holds text only and has a derived ID. It is made in the note of the segment it copies.
- Appends to a deleted note. A segment that starts after its note's `deletedAt` moves to a new note when the devices sync. The new note's ID is derived from the deleted note's ID, so several segments added to a note that the other replica had deleted land together in one new note. A late segment never lands in a deleted note. A segment whose note has not arrived yet waits for the fetch to finish.
- Moves. A move syncs as a change to the segment's `noteID` and `noteGeneration`, together with the new note's record. The higher generation wins a merge. At the same generation a person's move or return wins over the deleted-note rule, and then the note whose ID sorts higher keeps the segment. A derived ID is a version 5 UUID and a fresh one is version 7, so the two are told apart by the ID alone.
- A note left empty by a move, an undo or a merge is hidden, and it is never marked deleted for that reason. Deleting a note marks the note and not its segments. A move does not outlive a purge: a segment moved out of a note that another device deleted stays only if the move reaches that device before the deleted note is purged, 30 days later. After that the purge stands, as for any change to a purged record.
- Titles and deletes. A title keeps the later edit, by the origin of each title and the note's synced `titleEditedAt`, as docs/architecture.md §11 orders them. An edit that arrives for a deleted note is applied to the deleted copy, which stays deleted. Deletes sync as `deletedAt`, and the purge after 30 days deletes the records. The age of a synced delete is measured between two dates the server gave, never against the device's clock.
- Settings. The append window, the cleanup switch and the English variant sync. The hotkey, launch at login and the sync switch are per device.
- Accounts, environments and zones. The engine's state is kept per account and environment. A record counts as synced only for the account, the environment and the zone identity it was synced under, and the zone carries an identity written when it is made. So a record missing from the zone it was synced to is deleted locally, and a zone that is gone or new deletes nothing. SP-4 fixes the mechanism.
- The account is the `recordName` of the user record ID from the engine's account event. It stays in the store, and is never logged, shown, synced, exported or written to the diagnostics file. The environment comes from the entitlement the build was signed with (docs/architecture.md §11 and §19, docs/notes/SP-4.md).
- Accounts and removed zones. Apple's headers say to delete local data on a sign-out, a switch of account, a zone purged in Settings and an encrypted-data reset. Knot keeps the notes on purpose, because its local store is the primary copy. Until the answer, sync stays paused, and after a zone is purged or its encrypted data is reset, the prompt's default action keeps it paused. On a change of account the engine clears the pending changes it held, by the same headers, and `change_log` keeps them (docs/architecture.md §11, docs/notes/SP-4.md).
- Moving a device from CloudKit's development environment to production resets the engine's saved state and uploads the local notes again.
- Recordings and drawings. An asset is local only, uploading or published. Assets and their metadata are fetched on demand outside the engine, with `desiredKeys`. By CKAsset's header, a downloaded file lands in a staging area that the system clears, so it is moved into the store at once (docs/architecture.md §11, docs/notes/SP-4.md).
- Status: idle, syncing, error, quota exceeded, no account. When iCloud storage is full, sync says so, and text waits with the recordings while everything stays on the device.
- Diagnostics: counts, last sync time, last error code.
- The replica simulation. It runs with two and with three replicas, and its interleavings include moves and their undos beside edits, appends and deletes. After any interleaving it checks six things: the replicas end equal; nothing a replica acknowledged is missing; nothing made after a delete sits in a deleted note; a conflict copy appears only when both sides edited the text; applying a batch twice changes nothing; and every segment is in exactly one note, and a note with no live segment is never shown.
- The simulation covers each rule of §11 that WP-16 implements. Its named cases include a zone removed and made again, every replica uploading again after a change of environment, a replica whose clock runs 40 days ahead, two devices that take the same recording at the same generation, every order of a move, its undo and a delete across three replicas, and several segments added to a note that the other replica had deleted.
- The CloudKit schema. From the deployment of the production schema on, the schema is a committed file, and the gate fails on a change to it that is not additive.

## Failure rules

- The production CloudKit schema cannot drop fields. Deploy it only when Paolo approves. Every operation on the milestone iCloud container, in either environment, needs the owner's word.
- Only a milestone build opens the real iCloud container. Every other build uses its own iCloud container: agent builds, PR builds, spikes and tests.
- Sync opens at M4. In a milestone build made at a lower level, a gate switches it off.
- Sync runs only in the app.
- When the zone is removed from iCloud, the local notes stay, sync pauses and Knot asks before uploading again. Knot never deletes local notes because the cloud copy is gone.
- A record kind or field this build does not know is kept and saved back untouched.
- A fetch that would delete more than a set share of the local notes pauses sync and asks. The first value is a tenth of them, an estimate.
- Signing out pauses sync and keeps local data. Signing in to a different account asks before uploading anything.
- A store that arrives through a backup gets a new device ID and a reset sync state, so a restored phone never acts as the old one. WP-10 keeps the install ID that tells.
- An owner that no longer exists shows as "elsewhere", with the action to move the work here. Automatic takeover of a recording whose owner is gone is deferred to `TODOS.md`.
- With sync on, Knot asks before a restored store uploads.
- Every change to the schema after the M2 milestone build is a numbered migration, whichever package makes it.
- From the M4 milestone build on, no milestone build is installed or run on the build Mac, because a milestone build with sync open would bring the owner's notes onto it.
- Adding a dependency, such as an existing sync layer over GRDB and CKSyncEngine, stays the owner's decision under D30.
- Never log note text, transcripts, audio or content-derived paths.
