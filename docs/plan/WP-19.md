## Build

### All four PRs

- The intents in docs/architecture.md §14, App Shortcuts with phrases, a note entity with a query, and the watch variants.
- Intents reach the environment through the App Intents dependency manager, which the app registers at launch. An intent reads the environment through one accessor that fails with a typed error when nothing is registered, so an intent that the system runs in the wrong process fails safely.
- The accessor is `@Dependency(default:)` with the unavailable environment as its default, because `AppDependencyManager` has no lookup that can fail. Every intent that writes declares `allowedExecutionTargets = [.main]`. On iPhone and iPad the intents that start a recording declare `supportedModes = [.background, .foreground(.dynamic)]`, and StopRecording declares `[.background]` (docs/architecture.md §14).
- The widget extension links KnotIntents for the types only, and no intent runs there.
- Intents on iPhone, iPad and Mac call `CaptureEngine`, and watch intents call the watch recorder. None contains storage code.
- An intent that starts or stops a recording on iPhone, iPad or Mac calls the engine's `press`, which the contract pull request on the engine's port brings, so that the press rule has one applier where there is an engine.
- Intents are tested against `.preview`.

### PR 1

- The text intents: CreateNote and AppendText, on the system notes schema (`createNote`, `appendText`), which run in the app process in the background; and FindNotes, the entity query on the note entity.
- The note entity is not indexed, so nothing about a note appears in Spotlight. Intents that only write may run on a locked device. No intent that reads or picks a note runs on a locked device: those require authentication.
- The accessor, `@Dependency(default:)` with the unavailable environment as its default, which fails with a typed error when nothing is registered.
- KnotIntents exposes one live entry point, which returns the unavailable port until WP-19 fills it in, so that WP-19 wires itself in without editing `Packages/KnotKit/Sources/KnotApp/`.

### PR 2

- ToggleRecording, on iPhone and iPad only: `AudioRecordingIntent` and `LiveActivityIntent`. It starts a recording when idle and stops the one that is running, so the control that starts a recording also stops it. ToggleRecording is for buttons: the Action Button and the controls.
- StopRecording on iPhone and iPad: a `LiveActivityIntent`, for the Live Activity and the Dynamic Island.
- StartRecording on the Mac opens the panel already recording, with a stop control.
- Shortcuts get StartRecording and StopRecording on iPhone, iPad and Mac, each safe to repeat.
- A recording started from the Action Button or a control follows the window. The Live Activity shows whether a recording continues a note or starts a new one, without any text from the note.
- The Live Activity's attributes type lives in KnotIntents and belongs to WP-19. WP-30 implements `RecordingActivity`, the app-side code of the Live Activity, and WP-31 owns its views.
- OpenCapture and OpenSearch open the app on the capture surface, or on the stream with search focused. Where an Open intent lands is a supporting port that WP-02 PR 3 adds. WP-31 builds the Search control and widget target that open the stream with search focused.
- Rules taken from Apple's documentation, which SP-1 confirms: ToggleRecording and StopRecording are compiled into both the app and the widget extension, and the Live Activity starts with the recording and lasts as long as it does, or the system stops the recording.
- SP-1 also tests in which process each intent runs, and whether a toggle control's intent carries the value the control showed. PR 2 follows its report.
- `LiveActivityIntent` is used only on iPhone and iPad. The pinned SDK marks it unavailable on macOS, so a type that adopts it, or that uses ActivityKit, is compiled for iOS only, inside `#if os(iOS)`. `canImport(ActivityKit)` does not tell the two apart, because it is true on the Mac too (docs/architecture.md §14 and §20).

### PR 3

- StartRecording on the Watch opens the watch app already recording, for the complication, the control and Siri. It calls the watch recorder, not `CaptureEngine`.
- Whether a watch intent can start a recording at all, and without the app in front, is SP-2's question. PR 3 follows its report.
- Shortcuts get StartRecording and StopRecording on the Watch, each safe to repeat.
- A recording started from the Watch follows the window.

## Prior art

- WP-01 PR 1 proves the packaging with one trivial instance of each: an App Intent declared in the package and present in both the app and the widget extension, and a Live Activity attributes type. Read them before writing.

## Failure rules

- If Live Activities are off or the microphone permission is missing, the intent must open the app.
- If a locked start fails, the control opens Knot after Face ID and recording starts at once.
- An intent that the system runs in the wrong process fails with the accessor's typed error.
- Read the SDK before using an OS 26 or OS 27 API. Any such API used is named in the PR with the declaration that was read (docs/architecture.md §21).

## Named tests

- `repeating-start-or-stop-recording-changes-nothing`: Shortcuts get StartRecording and StopRecording on every platform, each safe to repeat, with a test that repeating either changes nothing.
- `intent-accessor-fails-typed-when-nothing-registered`: An intent reads the environment through one accessor that fails with a typed error when nothing is registered, and WP-19 tests that.
