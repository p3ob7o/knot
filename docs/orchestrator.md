# The orchestrator's runbook

For the thread that runs the Knot build. Read it after a reset, before doing anything new. `PLAN.md` §8 and `docs/architecture.md` §18 set the rules. This file says how they are carried out today, and it changes as the tooling lands.

## Where the state is

- **The plan.** `PLAN.md`, the briefs in `docs/plan/`, and `docs/plan/open-points.md`, which lists what is still unsettled and who settles it.
- **GitHub.** The branches (`wp/…`, `spike/…`, `contract/…`), the pull requests and their descriptions.
- **The journal.** `journal.md` in the build folder, which sits outside every worktree. On the build Mac the build folder is `~/knot-build`. The journal has one line for each operation, written before it starts and again when it ends, with the base, the head and the tree where they apply. Its times are local. It holds no note text and no secrets.
- **The threads.** The package threads in T3 Code, and their worktrees, which `git worktree list` shows.

After a reset, read the last lines of the journal, list the open pull requests and the worktrees, and compare the three. Finish or undo an operation that was cut short before starting anything new. A release step that was cut short is never resumed: it goes back to Paolo.

A time or a count in the journal or in a message is read from the clock or from a command at the moment it is written, never from memory or from one sample. `~/knot-build/drafts/journal-add.py` stamps a row with the clock's reading itself; its `--at` takes a time read earlier from a log or a commit, and the row's note names where it came from. On 2026-11-21 four statements of one day had to be corrected, among them a review given as about 75 minutes that had taken about 30, and a thread copies such a sentence into its pull request.

After a clean-up of the disk, the free space is read at once and again ten minutes later, and what the clean-up freed is stated only from the second reading. On 2026-11-24 the simulators of four idle worktrees were deleted, 30.7 GB by `du`, and `df` showed it only nine minutes later; in between the orchestrator told Paolo that the deletion had freed nothing.

## Launching a package

1. Read its rows in the start table of `PLAN.md` §6. Everything a row names has merged. A spike it names has its report merged and Paolo's confirmation, and the changes its report asks of `docs/architecture.md` have merged too.
2. Read `docs/plan/open-points.md` for the points to settle before that package starts. Settle them in the documents first, in a pull request of the orchestrator's own.
3. Write the launch in the journal.
4. Launch one top-level thread with `t3_thread_launch`: a worktree from `origin/main` on the branch `wp/<number>-<slug>`, the model `claude-opus-5-5`, and effort `high`, or `xhigh` for WP-10, WP-12 and WP-16. The first message is the prompt of `PLAN.md` Appendix B, followed by what the orchestrator has settled for the package and by what the build Mac has today.
5. Keep to five implementer threads at a time.

The implementers that build from the design round's handoff (`docs/design/handoff/`) run otherwise. Paolo asked on 2026-11-26 for agents on GPT 6.2 Sol to implement the design, and they run on it: the Codex provider's `gpt-6.2-sol`, at reasoning effort `high`. Each runs as a delegated task in a worktree of its own, in place of the top-level thread of step 4. Its brief is `~/knot-build/drafts/sol-common.md` and a task file of its own. No hook guards its git, so the brief spells out the rules on branches, staging, commits and pushes. It runs no `--full`, and neither the launch step nor the Mac UI step.

What the build Mac has today, for every first message:

- A forced push can wait for Paolo's approval, and a thread that sends one stalls there. A thread never rewrites a branch it has pushed, takes a new folder from `mktemp -d` in place of a recursive delete, and never chains a command that removes something with one that must run.
- When a tool call comes back as declined together with a message on another subject, Paolo answered while the call waited for approval. The thread acts on the message, and sends the call again if it was already allowed.
- The owner's recordings, when he has made them, are in the folder that `KNOT_LOCAL_FIXTURES` names. Nothing derived from them enters a commit, a pull request, a log or a test.
- `KNOT_AGENT=1` is exported in every shell before a script runs.
- A hook refuses `git add -A`, `git add -u` and a commit inside a compound command. A thread stages files by name, runs `git commit -F <file>` as a command of its own, and gives `gh pr create` its description with `--body-file`.
- A thread records each commit in UTC, as `AGENTS.md` says: `TZ=UTC git commit -F <file>`. The hook lets that form through.
- No hardware microphone, ever. A simulator's microphone is the Mac's own, so no recording path runs in a simulator.
- Before a gate with the Mac UI step, the orchestrator reads how long ago this Mac had input. When Paolo is at it, he is asked for the window first, in clock times: the launch step's Mac part and the Mac UI step start the app on his screen, about 21 to 30 minutes into the gate, and a window that opens under his hands can take what he types. On 2026-11-23 a Mac UI test failed while he typed, the system giving the app's window as a dialog, and passed in the window he then gave.

A Mac UI test launches, reads the accessibility tree, runs the audit and ends the app, and what it must enter comes through a debug-only launch argument. What needs real typing or clicking is a row of Paolo's checklist, or runs on the hosted runner (docs/architecture.md §17). The main display is whatever Paolo has set: on 2026-11-21 it was a virtual display, mirrored.
- A test leaves no file outside its own folders, and a file of a defaults suite that a test wrote counts too (docs/architecture.md §17).
- No suite has a bound that a loaded machine can miss. Every wait of the suites ends through `SuiteWait` after ten minutes, with an issue that names what it waited for, and a test that holds something back bounds its own calls into what it tests the same way (docs/architecture.md §17). On main, three calls in `NoteStoreFakeTests.swift` that are made during a hold do not yet: WP-02's third pull request bounds them.
- A package test reads `Fixtures/generated/` only through `FixtureFiles`, before any model check, and every run that runs package tests speaks the audio first. A missing fixture fails a test, and a test skips only on a missing model (docs/architecture.md §17).
- The owner's team configuration is on the Mac since 2026-11-20, in a file outside the repository. A thread whose package must sign with the team gets the file's path in `KNOT_LOCAL_CONFIG`, and no other thread does: every other build signs locally. The team's ID is never printed, never logged and never written to a tracked file, a note or a pull request. A thread that has the file runs `scripts/verify.sh --only team-id` before each push, and it does not run the gate, which refuses the variable.

So the ID is in the build logs of every worktree that has built an app. The team-ID check does not see it there, because it reads tracked files only, and it sees no commit message and no description of a pull request. No thread puts a build log, or a part of one, into a note, a commit message or a pull request without taking those lines out. On 2026-11-20 every branch, tag, commit message and pull request description was searched, and none held the ID.
- A build signed with the team and a locally signed build of the same bundle ID do not share a container quietly on this Mac. Each new signer raises a consent dialog that only Paolo answers, and while it is open every start of that bundle ID waits, the gate's own too. So a team-signed build of the development identifiers runs on this Mac only with him at the Mac, and while no gate and no UI test runs. He allowed this Mac to be registered as a development device, and he answers each consent dialog himself. Whether Xcode on this Mac holds an account is read before a build that needs one, never stated: on 2026-11-23 it held none ("A milestone build", below).
- Other threads build at the same time. A thread runs one heavy build at a time.
- A note or a pull request describes the SDK and the simulators, never the owner's own settings: no locale or region of this Mac, no account name, no path under `/Users`. The repository is public.
- The description of a pull request follows `PLAN.md` Appendix C.

The first message ends by telling the thread to send its RESULT line to the orchestrator's thread with `t3_thread_send` when it ends.

## When a thread hands back

The last line of its final message is `RESULT ok` or `RESULT blocked` with a code (`PLAN.md` §8.3).

- `RESULT ok`: arrange the review.
- `needs_owner` and `needs_hardware`: tell Paolo exactly what is needed, and resume the thread when he has done it.
- `needs_contract_change` and `needs_shared_file`: the orchestrator arranges the change, as `PLAN.md` §8.5 says.
- `brief_wrong`: correct the brief first, in a pull request of the orchestrator's own.
- `baseline_red` and `tool_failure`: find the cause before launching anything else on that base.

A top-level thread does not wake the orchestrator by ending. The RESULT line that it sends with `t3_thread_send` does. That line is not Paolo's: the orchestrator reads the thread's last message before it acts on it. One scheduled check an hour looks for a thread that stalled on an approval prompt. A thread that shows as waiting on a background command of its own is at work, and it has not handed back until its RESULT line arrives. A delegated task wakes the orchestrator by itself, and so does a watched pull request when its checks end.

## Review

- A fresh reviewer reads the diff against the package's brief and `AGENTS.md`, from a list of points that the orchestrator writes for that pull request. It runs as a delegated task, so its end wakes the orchestrator. It changes nothing, runs what it runs in a scratch clone, and ends with `REVIEW pass` or with `REVIEW changes` and the counts.
- Knot is one person's app (`PLAN.md` §8.4). A review brief says so: a finding that needs several surfaces, or two devices, acting inside the same fraction of a second is ranked low and recorded as a known limit unless a capture is lost, and the reviewer says plainly when a sequence needs more than one person can do. One person's ordinary sequences across surfaces stay in scope. A fix of that kind that costs more than a small change goes to Paolo first.
- The orchestrator checks each finding before it passes it on, and rules where the documents are silent. A ruling goes into the documents in a pull request of the orchestrator's own.
- A reviewer's "no document says" is checked against the documents before a question for Paolo is built on it. On 2026-11-24 a question to drop a planned feature, what the Watch shows of whether a recording continues a note, rested on such a claim, and `docs/architecture.md`, under the Watch's back channel, did say it; the question was caught before it reached him.
- A proof step's code stays on `wp/<number>-proof` with no pull request, and its note merges from `wp/<number>-note`. The orchestrator reads a short note itself, and the squash message says that no second agent did.
- WP-02, WP-05, WP-06, WP-10, WP-11, WP-12, WP-15, WP-16 and WP-17 also get a second opinion from another model.
- The implementer fixes the findings. After two rounds the orchestrator decides what is left. It writes every finding it sets aside in the pull request and in the journal.
- Paolo gave a rule on 2026-11-21, when he dropped finding 85: "Stop focusing on such edge cases." The orchestrator reads it so, and this is its reading, not his words: after a review's second round, a finding that is no lost capture, is not on a milestone checklist's path and is no cheap test of core code is recorded as a known limit, and no further round is run for it. A pull request whose first review found no loss gets one review.
- A reviewer's test that goes into a suite is run many times and under load before it merges, and is read for two calls started as tasks whose order it relies on: such an order is made with a hook (docs/architecture.md §17). The gate's replay runs a taken test at least 30 times. On 2026-11-20 one such test passed on the build Mac every time and failed the hosted check on `main`.

## The merge queue

One pull request at a time.

Since 2026-11-20 the ruleset on `main` requires a pull request, squash as the only merge method, an up-to-date branch and two checks, `knot/gate` and `quick`, the hosted workflow's run of `scripts/verify.sh --quick`, and nobody bypasses it. GitHub refuses a merge without both checks, so the hosted check is required, not a habit: a head waits for it as it waits for the gate.

1. In the gate worktree, check out the pull request's head. If `main` has moved since the branch last took it in, merge `main` into it there, with `TZ=UTC` in front of the command, so that the merge is recorded in UTC. A conflict goes back to the implementer.
2. Run the gate on that commit from the main checkout, so that main's scripts check the candidate: `scripts/verify.sh --gate --tree <the gate worktree> --branch <branch> --package <ID>`. The head is detached there, and on a detached head the gate refuses `--package` alone: `--branch` names the branch, which also tells a note's pull request from a code one. A stated exception to path ownership is passed with `--allow <path>`, and an allowance that matches nothing fails. A pull request that changes `scripts/` is gated with its own scripts, from the gate worktree. Write the result in the journal with the base, the head and the tree.
3. If step 1 made a merge, push it to the branch as an ordinary push, and let the workflow run on the new head. Never rebase a branch that was pushed and never force a push: a forced push waits for Paolo's approval.
4. Post the status `knot/gate` on that head, with the output of `scripts/verify.sh --status-line --tree <the gate worktree>`: the same `--tree` as the gate run, because the line is kept in that tree's `.build/logs` and names no commit. A failed gate is posted too, as a failure, and what it found goes to the implementer.
5. Squash-merge at the tested head, with a subject and a body of the orchestrator's own, so that no session link enters the history. The merge is made through GitHub's REST call for merging a pull request, `PUT /repos/<owner>/<repository>/pulls/<number>/merge`, with `merge_method` set to `squash`, with `sha` set to the tested head, which refuses the merge if the head has moved, and with the header `Time-Zone: Etc/UTC`. The subject goes in `commit_title` and the body in `commit_message`. GitHub's REST documentation gives that header for the time zone of a commit that GitHub makes. Without it the commit on `main` takes the zone GitHub last knew for the account. The merge of pull request 36 was the first made this way, and it showed what the header does: the committer's date of the squash records +0000, and the author's date keeps the zone GitHub holds for the account, as on every merge before it. Neither is this Mac's offset. `gh pr merge` sends no such header and is never used for it: on 2026-11-24, at a resume after a reset, the orchestrator merged pull request 122 with it before it had read this file, and the committer's date of that squash carries +01:00, the zone GitHub holds for the account. A commit on `main` keeps its dates. The subject starts with the package's ID, as in `WP-02 PR 1: …`, because the gate's helper reads the subjects on `main` when it cannot ask GitHub which pull requests have merged.
6. Check that the tree on `main` is the tree that was tested. If `main` or the head moved in between, the result is void.
7. Delete the branch. A branch whose pull request was squashed gets no further commits. If the thread goes straight on with the package's next pull request, it starts a new branch from `origin/main` in the same worktree. Otherwise remove the worktree.

Two pull requests of which the second holds the first: after the first is squashed, a three-way merge of `main` into the second conflicts wherever the second changed lines that the first had changed, whatever was merged into it before, since the squash is one commit beside the first's own. The orchestrator then shows that `main`'s tree is the tree of a commit that the second already holds, and records the merge with the strategy `ours`, which leaves the second's tree unchanged. It was seen at pull request 104, on one file.

A pull request beside the planned ones gets a row of its own in its package's brief, lettered after the package's number, as 11a, 11b, 12a, 13a and 06a were. The letter runs on past `d`: since pull request 116 `scripts/check-plan.sh` takes a row lettered `a` to `z`, where it took `a` to `d` alone, in three places. The pull request is on a branch `wp/NN-…` and squashed under a subject `WP-NN: …`. Since pull request 116 `package_of_branch` in `scripts/lib/knot_tool.py` also reads a lettered branch such as `wp/06b-…`, but the subject fallback of `merged_prs` still reads `WP-NN` followed by a word boundary, so `WP-06b:` names no package to it, and `scripts/status.sh` counts the row as not merged when it cannot ask GitHub.

The gate is `scripts/verify.sh --gate`, and its depth comes from the diff (docs/architecture.md §18). `scripts/gate-steps.txt` lists every step and marks those that are still pending, each with what delivers it, and the orchestrator turns a line to required when that has arrived. The Mac UI step, `mac-ui`, is required since WP-01's third pull request, pull request 38. The soak, `soak`, is required since WP-06's first pull request and its step, pull requests 70 and 79, were on `main`. The `.live` smoke tests run inside the launch step and the Mac UI step since the first pull requests of WP-30, WP-32 and WP-33; the step of their own, `live-smoke`, is not built and stays pending. The two-process test waits for WP-34.

The team-ID check is required since 2026-11-20, when Paolo's signing configuration came to the Mac, and it runs at every depth. The orchestrator names the configuration for it with `KNOT_TEAM_CONFIG`, in front of the gate's command. That variable serves the check alone and links nothing into the tree. `KNOT_LOCAL_CONFIG` would link the configuration into the gate worktree and give the gate's app steps build settings that no thread has, so the gate refuses it, and it removes such a link if an earlier run left one. Without a configuration the step is skipped, and the gate fails on a skipped step: its line reads FAILED, and that is what is posted. A thread without the configuration runs `scripts/verify.sh --full`, which reports the step as skipped and ends ok.

A step log left from an earlier run no longer reads as this run's. Since pull request 95 the scrub of the kept logs keeps each log's time. Since pull request 116 a whole run, the gate among them, first moves every file an earlier run left in `.build/logs/` to `.build/logs-earlier/`, so that after a gate every log in `.build/logs/` is the gate's own. A run of one step, `--only` or `--module`, rewrites only the logs of the steps it starts, and the others keep their own times (docs/dev-setup.md). Before pull request 95 the scrub at the start of every run gave each kept log the run's time, so a step log left from an earlier run read as this run's: the gate worktree held pull request 76's soak log, dated one second into pull request 63's gate, which ran no soak.

When the launch step fails on every branch at once, the first check is the Mac app's saved window state and the desktop, before the code: every development build shares one bundle ID and so one saved window state, and a window closed once left every later launch with no window (docs/architecture.md §18). No agent resets the app's container or its saved state by hand.

Since pull request 38 the packaging step starts `knot-dev` under a time limit, and so does each run of UI tests, and at the limit the step fails and says that a system dialog may be waiting for Paolo (docs/architecture.md §18).

A pull request that changes the gate, or a contract that others build on, is tried on the next pull request in the queue before it merges, by running its scripts with `--tree` on that candidate. On 2026-11-19 this found two faults in the tooling that its own gate could not show. The trial of a scripts pull request has a base and a tree, both made locally:

- The base is the scripts pull request's head, merged with `main` whenever the other pull request's branch holds a newer `main` than the scripts pull request's does. With the bare head as the base, what `main` gained since counts as the other package's change, and the ownership step fails at once.
- The tree is the other pull request's head merged onto that base, never the scripts pull request's head merged onto the other's. The ownership step takes the changes from the common ancestor of the base and the tree, so the base must be an ancestor of the tree.
- The trial runs the base's scripts with `--tree` at the tree and `--base` at the base. Merged with `main` alone, a self-test check of a file that the scripts pull request changes fails, and without `--base` the ownership step counts the scripts pull request's files as the other package's.

Both rules on the base and the tree come from two false starts on 2026-11-24, at the trial of pull request 116 on pull request 115.

The trial also runs `scripts/self-test.sh` from the trial tree itself, as the hosted `quick` check does. The gate runs main's self-test, which reads the plan of the scripts' own checkout, main's, and the hosted check runs the branch's own self-test on the branch's own plan. So a self-test case that rests on the real plan can pass at the gate and fail on the hosted runner: pull request 116's case added a made-up row 22e to a copy of the real plan, pull request 115 gave WP-22 its real row 22e, and the copy held the label twice. A self-test case on the plan uses a fixture plan, or names that the real plan cannot come to hold, as that case now does with 22y and WP-22z.

## The nightly run

The nightly run has two halves. `scripts/nightly.sh` cites this section for the rule that a red night stops the merge queue.

- **The hosted half.** `.github/workflows/nightly.yml` runs on a hosted runner at 03:17 UTC every day, on `main`, and on demand. It speaks the fixtures' audio with `scripts/verify.sh --only fixtures`, then runs the package tests under Thread Sanitizer, `scripts/verify.sh --only tsan`, the named test `package-tests-under-thread-sanitizer-nightly`. When a step fails or the run is cancelled, it keeps `.build/logs/` as the artifact `nightly-logs` for seven days.
- **The local half.** `scripts/nightly.sh`, on a checkout of `main` on the build Mac, runs seven runs one after another, each a verify run of its own: `--full`; the package tests under Thread Sanitizer, `--only tsan`; the soak with a fresh seed, `--soak`; the launches on the iOS 27.0 runtime, the oldest Knot supports, with their own simulators; the recorder's kill test and its shared recording state in the iOS Simulator, with a fresh seed, `--only recorder-sim`; the report of a model that changed with an update of the system, `--only model-report`; and the timed targets, `--perf`, holding every build slot. The last is in the night since pull request 116, so that a change that breaks the optimised build shows the next morning and not at a milestone; its build is compiled for testing and with `DEBUG` defined (docs/architecture.md §17). Each run's logs are kept in `.build/nightly/<run>/`, which is cleared when the night starts.

The orchestrator reads the hosted run at every resume and before the first merge of a day, with `gh run list --workflow nightly.yml --limit 3`. The hosted half was red on 2026-11-22 and 2026-11-23, and nobody read it until 2026-11-24.

A red night's cause is read from the run's kept logs, fetched into a new folder of their own with `gh run download <run ID> --name nightly-logs --dir <folder>`, and from each log whole. The failed step's console on GitHub shows only its tail, and the step's count line is no verdict: on 2026-11-23 `--only tsan` ended with "tests 1407 passed, 0 failed" while KnotSoak's test run had failed with five issues, and the orchestrator, reading the count, told Paolo that every test had passed. So the whole log is searched for a sanitizer report (`ThreadSanitizer`), the mark of a failed test (` failed`, `recorded an issue`, `error:`) and a signal (`signal`, `Fatal error`), and the search is never cut with `head`.

Nothing merges until each cause of a red night is named, and cured or ruled. One named cause does not explain the next red night: on 22, 23 and 24 November three nights had three causes.

The local half runs on a night when the screen is locked and no thread builds, as `scripts/nightly.sh --skip mac-ui`, since the Mac UI tests need the screen. It prints each run's status line, and ends in one of three ways:

- **0**, every run ran and passed: "nightly: every run passed".
- **1**, a run failed. It names the runs that failed, and those that did not run, and says to read each run's logs in `.build/nightly/<run>/`.
- **4**, no verdict: no run failed, and at least one did not run to its end for want of a build slot. Its last line names those runs. The orchestrator runs each of them again, by its own command, before it reads the night as green.

## A milestone build

At each milestone tag, the build of that tag makes a seeded synthetic store, `KnotStoreCrashHost seed Packages/KnotKit/Tests/KnotStoreTests/SeededStores/<tag>`, and the result is committed, so that later versions are tested against the stores that earlier milestones made (docs/architecture.md §7).

A milestone build is made with `scripts/milestone-build.sh <level> --commit <sha>`, and with nothing else. It is made from the commit at which `main` first held everything PLAN.md §5 names for the milestone, the gate passed and the soak ran, and not from a later `main`, which by then holds work for the next milestone. A fix that a sitting asks for is built from that commit and the fix. The script builds the Release configuration at the milestone flavour and the level named: the iPhone app with its Watch app and widgets, and the Mac app with its tool, or one of the two with `--products ios` or `--products mac`.

**What it refuses before it builds.** It stops, and says what to do, when the commit named is not a commit of the repository; when `HEAD` is not that commit, naming both commits and their trees; when the worktree has uncommitted changes; when files that git ignores lie under the folders the build reads, `Apps/`, `Packages/KnotKit/Sources/` and the manifests, since the build would read them and the commit does not hold them; when the team's configuration is not linked into `.build/config/Local.xcconfig`; when `.build/config/Worktree.xcconfig` or `Local.xcconfig` sets more than its own two keys, read by their keys alone; when a package's checkout under `.build/SourcePackages` is not at the revision that `Package.resolved` pins, or is changed; when Xcode's saved list of accounts is empty; and when `Apps/Config/Identifiers.xcconfig` does not give the milestone's bundle ID, version, build number and tool file. It then generates the project afresh from the commit's `project.yml`.

**Signing.** The script passes `-allowProvisioningUpdates` only with its own option, `--allow-provisioning-updates`, which is given on Paolo's word, as he gave it on 2026-11-23 for the first milestone. It has no option for registering a device: nothing it runs passes `-allowProvisioningDeviceRegistration`. A failed build prints the error lines at the end of its log, and says that a signing error that names an account, a profile or a device needs Paolo, and that no flag he has not allowed is passed.

**Fresh derived data.** Each product is built in derived data of its own, a new folder `.build/milestone/<level>-<commit>-<product>`, through a build slot, and the script reports the build's time apart from the wait for the slot. It refuses a folder, or a log, that holds an earlier build: a product is never built again in the same folder. To build again, copy the log out if it is evidence, remove the folder and the log by their paths, and run the script again. On 2026-11-23 a build for another destination in the same derived data left the iOS widget unsigned after its catalogue and its profile had changed, and a thread's script installed it.

**The checks, before any install.** For each product, in this order, the script stops at the first failure, names the part, and installs nothing:

1. What the product says it is: its bundle ID, version, build number, flavour and level against the level asked for and `Apps/Config/Identifiers.xcconfig`; each bundle inside it under the app's bundle ID, with the same version and build; and on the Mac, the app's executable and its tool in `Contents/MacOS` as two files, by their exact names.
2. `codesign --verify --strict` on every part, each alone, innermost first.
3. Every part signed by the app's own team, since an ad hoc signature passes the strict check, and on the Mac the tool's app groups the app's. The team is compared in memory and never printed.
4. The app groups each part is signed with, against those its embedded provisioning profile allows; a part that its project's entitlements file gives a group and that is signed with none fails too. The Mac's tool, a bare executable, carries no profile, so only its signature is read. A build that says it has a group and finds no container fails with a typed error (docs/architecture.md §7), and neither a simulator nor a locally signed build can show it.
5. No fakes and no debug launch argument in any Mach-O file of the product; a scan that found no Mach-O file fails.

**What it leaves.** Once a product's checks have run, pass or fail, or its build has failed, every app in its derived data is unregistered from LaunchServices, and the products stay on disk for the copy. The script starts nothing it builds: a milestone build that runs opens the owner's own store. It prints a summary, with each product's path and log, before any install.

**Its logs.** Each build's log is `.build/milestone/milestone-build-<level>-<commit>-<product>.log`, beside its derived data: a milestone's evidence, which a run of `scripts/verify.sh` does not move aside. The log is filtered as it is written, and the logs that earlier runs left there are filtered again when the script starts. The filter, `knot_filter_team` in `scripts/lib/common.sh`, masks the team's ID as `<TEAM>` where Xcode writes it, as a prefix, a setting, an entitlement or the end of a certificate's name, and, since the configuration is linked, the ID itself wherever it stands; a signing identity's SHA-1, after `--sign` and its like, as `<IDENTITY>`; and the name on a certificate as `<NAME>`. The script prints no team ID and no signing identity. Xcode's own logs inside the derived data are not filtered, and nothing is copied from them.

**The install.** `--install`, after every check has passed, runs `scripts/install.sh`: for the iPhone app on every paired device, with `--device` and `--again` passed through, and for the Mac app a copy into the folder that `--mac-folder` names. An install that fails leaves the build whole and checked. The script says so, prints the command that installs it again from its path, from any folder, says not to run `milestone-build.sh` again for it, since it would refuse the folder that holds the build, and for the Mac says to move a partial copy away first. `scripts/install.sh` skips a device that holds the same version and build; `scripts/install.sh --again` installs there too, as a build signed again needs, since it carries the version and build number of the one it replaces.
